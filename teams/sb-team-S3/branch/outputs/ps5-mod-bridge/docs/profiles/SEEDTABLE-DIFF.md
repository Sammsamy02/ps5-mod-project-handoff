## Reading the differences

* The current file's GMalloc seed is the raw allocator pointer the lazy-create function fetches (`symbols.gmalloc_base_slot`); the generator's value is the variable `FMemory::Malloc` and `FMemory::Free` load. Which one the runtime should seed is a console question; the emitter makes either with `--seed-gmalloc`.
* `kHeapLo`/`kHeapHi` belong to the retired heap envelope; the profile has no heap span, so the default is an unbounded range (any non-zero `Blocks[0]` passes) and `--seed-heap-span omit` drops the constants.
* Constants the current file has and the profile cannot supply are not invented: they are left out with a comment. A runtime build that still reads one (the staged unit's V1/V2 validators read `kGMallocInstanceLabel` and `kGMallocVtableLabel`, its pool check reads `kHeapLo`/`kHeapHi`) fails to compile until the constant exists, which is loud by design.
* With `--seed-gmalloc dispatch` the V1 validator (`[GMalloc] == instance`) was written for the `base_slot` variable; the dispatch variable may hold a wrapper over the instance, so V1 may refuse that table at run time.
