# cap02 NOTES — automatic first-launch layout profile (Mac-only)

## Goal restated
First launch of a new game should generate correct field offsets automatically,
per ENGINE not per game, and refuse (fail-closed) on an engine era it has no
measured pack for. Prove the automatic path reproduces Townfall's proven layout
exactly.

- `PATCH/new-files/AutoLayoutPacks.generated.hpp` — engine-level layout packs,
  generated by `tools/build_packs.py` from existing local evidence only.

  `select_pack()` (exact-cell, fail-closed), `generate()` (renders the member +

## How the packs are "two independent sources" (the engine-level claim)
The UE5.6 shipped pack is calibrated on one PS5 image whose every value is an
R11 shipped, launch-14 console-proven layout value. For each row I recorded the
independent mechanical sources that AGREE with the shipped value:
- `image_static_pin`: R11 RuntimeBuildProfile pin (image/static disassembly).
- `epic_5_6_1_generic_compiler`: l23 generic-platform compilation of Epic's own
  5.6.1 declarations (`2026-10-08-l23-layout-generic`), the Itanium ABI route.
- `image_field_evidence`: round-10 image measurement of the 15 added fields.
- Corroboration-only: UE4SS upstream (Re-UE4SS/UEPseudo) 5.06 Win64 defaults.

The 11 rows WITHOUT a second mechanical source in-tree (`legacy_rows` in the
pack) are all R11 shipped + console-proven values; they are admitted by the R11
lineage review and listed explicitly. They split into:
- The 5 `FUObjectArray` fields after the two locks (`UObjectCreateListeners`,
  `UObjectDeleteListeners`, `PrimarySerialNumber`, `bShouldRecycleObjectIndices`,
  `UEP_TotalSize`): the generic-compiler value DISAGREES with the image value
  because the PS5 SDK's lock type is wider than the public Unix pthread mutex
  the l23 route modelled (l23 CALIBRATION.json records exactly this: observed
  72/88 vs image 88/104…). The IMAGE value is correct and console-proven; the
  generic-compiler value is a known platform-dependent miss. Marked
  `platform_dependent_rows`.
- `FWorldContext::ThisCurrentWorld`/`UEP_TotalSize` and the three engine
  vtable slots (`UEngine::LoadMap`/`Tick`, `AGameModeBase::InitGameState`):
  l23 left these UHT-BLOCKED (generated headers absent), so only the image pin
  exists in-tree. `ThisCurrentWorld` is additionally corroborated by UE4SS
  upstream 5.06 (0x2c0 both).
- `UObject::ProcessEvent`: image 0x268 vs generic 0x260; the generic value is
  with `UE_WITH_IRIS=0`, the image build has IRIS on (l23 IRIS-VARIANT.json
  gives 0x268). Config-dependent; recorded in `config_dependent_rows`.

So: every shipped offset is either two-source-agreeing or an R11 console-proven
value with its single-source reason stated. Nothing is guessed.

## UE4 era (the Stellar-Blade-class requirement) — honest status
`packs/src/ue4.26-candidate.json` holds 489 member rows transcribed from UE4SS
upstream's own 4.26 default layouts, but it is **NOT shipped** and the generator
has **no 4.26 pack**, so a 4.26 image is refused (host test T4). Why not shipped:
- UE4SS upstream is a single source and its ABI is Win64/MSVC; the PS5 uses the
  x86-64 Itanium (SysV) ABI. Record layouts are largely ABI-portable but vtable
  slot order is NOT (MSVC vs Itanium differ), so the vtable rows have ZERO
  Itanium sources.
- The second, independent source is Epic's own 4.26 declarations measured for
  x86-64 Itanium (the same route l23 used for 5.6.1). That measurement is not
  in this tree. I started a pinned local fetch of Epic 4.26 headers to run that
  measurement (the method is identical to l23), but removed it to keep strictly
  inside scope/time; the fetch+measure tooling pattern is the l23 one and the
  Epic 4.26.2 tag is reachable (`c3caf7b6…`). Until that second Itanium source
  exists AND a real UE4 PS5 target validates it, shipping a 4.26 pack would
  violate the two-source rule, so it stays a refused candidate. This is the
  correct fail-closed behaviour for the blind test: no guessed UE4 values.

## Open questions for the reviewer / integrator
1. **build_id width**: the ELF `NT_GNU_BUILD_ID` note descsz is 20 bytes
   (`04bb4330a7d71dcefe1cc2c4d19769d5` + 4 zero bytes). R11 recorded the 16-byte
   prefix. The generic reader emits the full 20-byte note value (honest image
   fact). build_id is a provenance tag the gate compares staged-vs-profile, not
   an address, and on the AUTO path both sides come from the same scan, so this
   is self-consistent; but the compiled-R11 header carries the 16-byte form, so
   the SHADOW parses that 16-byte value from R11's own header (shadow MATCH is
   exact). Decide whether the canonical build_id is 16 or 20 bytes before the
   first real new-game launch.
2. **profile-side generator**: the BuildProfile/LayoutPreflight gate reads the
   compiled `rc::runtimeprofile::kProfile`. A genuinely new game needs that
   profile generated from the live image too (sha/size/extent + detected cell).
   That is the remaining piece for a real first launch; cap02 proves every
   input value is image-derivable (`scan_image_identity.py`).
3. **version-store scanner robustness**: my disassembler-free matcher decodes
   only the `C7 /0` + `66 C7 /0` store pair plus a `+8` write; it resolves
   Townfall uniquely. The runtime already has the full patternsleuth
   `scan_version_stores` resolver — prefer wiring that for the live path and
   keep my Python matcher as the Mac cross-check.
