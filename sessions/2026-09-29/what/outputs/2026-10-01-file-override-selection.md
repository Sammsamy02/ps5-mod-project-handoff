# Shared file-override selection

The core now implements one reusable part of file mods: choosing an opaque override source for a logical game request. It is independent of game names, title IDs, engine addresses and physical destination paths. **No game file request has been redirected, and this is not a PS5 ME2/me3 port or an asset translator.**

`choose_file_override` lives in the existing `src/inventory.cpp` module, with its public contract in `include/modbridge/core.hpp`. It reuses the existing relative-path grammar without changing archive inventory behavior. A caller supplies immutable entries `{package_rank, relative_key, opaque_source_index}`, in nondecreasing package rank. Equal ranks mean one package; ranks need not be contiguous. The caller must resolve package dependencies, enabled state and source availability before forming this table.

The caller's policy supplies exact virtual-root aliases, case matching and the winning package. First-package and last-package policies represent the different file-choice rules identified in the retained ME2/me3 source comparison. They do not implement upstream configuration import or automatically infer which policy a mod expects.

| Behavior | Current implementation |
| --- | --- |
| Paths | Relative forward/backslash forms normalize identically; `.` and repeated internal separators normalize; absolute paths, parent traversal, control bytes, colons and trailing dot/space components reject |
| Virtual requests | Only an exact configured `[A-Za-z0-9_-]+:` root followed by a separator is removed; unknown roots reject; table keys are always relative |
| Case | Byte-exact matching preserves non-ASCII bytes literally; ASCII-insensitive matching folds A–Z and rejects non-ASCII as Unsupported |
| Precedence | Explicit first-package or last-package winner; source index zero is valid |
| Collisions | Normalized duplicates and file/descendant overlaps within one package reject the whole table; keys in different packages may override |
| Publication | Selected or passthrough is returned only after complete-table validation; any late failure returns no source |
| Bounds | At most 10,000 rows, 64 roots, 8 MiB combined raw key bytes and 4,096 raw bytes per path; callers may tighten ceilings |
| Work | Weighted key-processing budget covers normalization allowances and charged comparisons; it is not a wall-clock or allocator guarantee |

The APIs open no files, write nothing and return owning scalar choices. The original `choose_file_override` keeps its complete-table validation on each call. The new `prepare_file_overrides` validates once and publishes a `FileOverrideTable` owning normalized winning keys and root aliases. Subsequent `lookup` calls normalize the request and search sorted keys without rescanning the package table. Copies share immutable storage; caller-input mutation/destruction cannot change selections, and moved-from tables safely reject.

Preparation and lookup have separate error ordering and work budgets. The prepared table retains the original raw key/alias byte count, including entries removed by precedence, and adds each raw request before admitting a lookup. Lookup uses the smaller of its requested work budget and the stored preparation ceiling. No borrowed source views, partially validated table or source choice escapes a failed preparation. Request normalization may allocate bounded strings; no allocation-free, exact peak allocator or target timing guarantee is claimed.
