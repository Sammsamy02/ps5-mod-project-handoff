# WebKit Autoloader source identification — 2026-09-30

## Finding

The reported name “WebKit Autoloader v0.5.0” matches the official [`itsPLK/ps5-webkit-autoloader` v0.5.0 release](https://github.com/itsPLK/ps5-webkit-autoloader/releases/tag/v0.5.0), whose tag resolves to source commit `132be85383bc8192fb746cd784f868ca88252395`. That release explicitly adds Relapse support for firmware 7.00–13.60, updates the unified autoloader to v0.1.5 (which pins Payload Manager v0.5.2), and updates elfldr to v0.26. The release installer ELF is 1,950,976 bytes, SHA-256 `83c2128520267515fe2f197db35427bb95b7273934e52ad3c6bf668a4ef27b7f` (GitHub release asset metadata).

For the reported firmware 13.60, this release’s documented default path is Relapse, not the older umtx2 path. The installed app is expected to start the **shared `itsPLK/ps5-elfldr` fork** pinned at commit `bb1e117988217a0239679029601e93c7286394d7`, tag `v0.26-bb1e117`; its released ELF asset is 394,480 bytes with SHA-256 `fa3f0c2b778318000982ada05c01bde70ac875c85e4be6fcc9b5ba836f6d1c3c`. This is a fork of upstream `ps5-payload-dev/elfldr`, and the fork’s bind address is significant: its source binds TCP 9021 to `INADDR_LOOPBACK` (127.0.0.1), not all interfaces. A PC client cannot directly reach that listener over the LAN. Payload Manager runs on-console and connects to `127.0.0.1:9021` itself.

This identification is strong enough to choose the likely source path for design review. It does **not** verify the installed app cache, the ELF actually running, or its exact bytes. The manager’s reported `/version` `0.5.2` identifies the manager response only; neither that nor the user-reported autoloader name proves the console is running these pinned artifacts. Firmware 13.60 is also user-reported, not independently read from the device.

The source distinction matters. The web autoloader’s own build script pins `itsPLK/ps5-elfldr@v0.26-bb1e117`; that is not interchangeable with analyzing only `ps5-payload-dev/elfldr`’s separate `v0.26` release/source commit. In particular, the installed chain’s fork is the one whose `socksrv.c` must be used to decide whether a network client can reach port 9021.

## Framing and socket-path comparison

I compared the checked-out source trees at upstream `ps5-payload-dev/elfldr@54966675d3884ba9c773f0f52646f8f46b92cbbc` and downstream `itsPLK/ps5-elfldr@bb1e117988217a0239679029601e93c7286394d7`. The two `elfldr.c` files are byte-for-byte identical. In `socksrv.c`, the material transport change is the listener bind address: upstream uses `INADDR_ANY`, the WebKit fork uses `INADDR_LOOPBACK`. The fork also comments out notification includes/calls. Its `bootstrap.c` and `main.c` likewise only comment out notifications; `uri.c` adds a zero-length URI guard. None of these changes alter `elfldr_read`, ELF framing, entry setup, or fd duplication. Compare the [upstream reader](https://github.com/ps5-payload-dev/elfldr/blob/54966675d3884ba9c773f0f52646f8f46b92cbbc/elfldr.c#L720), [fork reader](https://github.com/itsPLK/ps5-elfldr/blob/bb1e117988217a0239679029601e93c7286394d7/elfldr.c#L762), [upstream bind](https://github.com/ps5-payload-dev/elfldr/blob/54966675d3884ba9c773f0f52646f8f46b92cbbc/socksrv.c#L306), and [fork bind](https://github.com/itsPLK/ps5-elfldr/blob/bb1e117988217a0239679029601e93c7286394d7/socksrv.c#L306).

Both readers consume an ELF64-derived prefix, not the connection until EOF. They first `MSG_WAITALL` the 64-byte ELF header; set `size = e_shoff + e_shnum * sizeof(Elf64_Ehdr)` (64 bytes, the ELF64 section-header entry size); read through that section-table end; then compute the largest `sh_offset + sh_size` among non-`SHT_NOBITS` sections. The returned extent is `max(size, largest_non_NOBITS_section_end)`, with any excess read by another exact `MSG_WAITALL`. This is the exact behavior the diagnostic receiver design models. Sending exactly that prefix and then calling `shutdown(SHUT_WR)` remains compatible: the loader has all bytes it needs and never requires EOF as its length marker. Keeping the client’s read half open is also compatible with the socket setup, which duplicates the accepted fd onto child stdin/stdout/stderr when `pipe` defaults to `1`; after spawn setup, the server closes its accepted fd, while the child-held fd can continue returning report bytes. A complete client `close()` after send, as both Payload Manager and the unified launcher do, ends the client’s receive path before it can collect that output.

One guard in the receiver design is essential: `elfldr_read` computes its extent from section headers, not `PT_LOAD` headers. The socket path does not call `elfldr_sanity_check` before spawning; `elfldr_load` later copies each `PT_LOAD` range directly from the allocated ELF buffer ([sanity check and load code](https://github.com/itsPLK/ps5-elfldr/blob/bb1e117988217a0239679029601e93c7286394d7/elfldr.c#L113), [spawn path](https://github.com/itsPLK/ps5-elfldr/blob/bb1e117988217a0239679029601e93c7286394d7/elfldr.c#L603)). Therefore the client must reject an artifact if any nonempty file-backed `PT_LOAD` end (`p_offset + p_filesz`, with checked addition) lies beyond the section-derived prefix. The existing exact-prefix plan already requires this check; it should remain mandatory.

For the saved candidate `outputs/native-probe-artifacts/native-probe.elf`, independent local header parsing found a 50,848-byte file with `e_shoff = 50,080`, `e_shnum = 12`, so the initial section-table extent is 50,848. The greatest non-`SHT_NOBITS` section end is 50,073; the greatest `PT_LOAD` file end is 49,376 (the three load ends are 22,116, 33,701, and 49,376). Its loader-consumed prefix is therefore compatible and equals the whole file. This confirms the predicate for this saved artifact only; it is not runtime or loader identity evidence.

## Entry, process return, and stdout evidence

At the pinned `itsPLK/ps5-elfldr` source, `elfldr_payload_args` fills offset `0x00` with a `getpid` stub resolved as `"HoLVWNanBBc"`, and offset `0x28` with the `payloadout` address. `elfldr_prepare_exec` saves the prior RIP at `RSP-8`, then sets RIP to the ELF entry and RDI to the argument structure ([`elfldr.c`](https://github.com/itsPLK/ps5-elfldr/blob/bb1e117988217a0239679029601e93c7286394d7/elfldr.c#L304), [`elfldr.c`](https://github.com/itsPLK/ps5-elfldr/blob/bb1e117988217a0239679029601e93c7286394d7/elfldr.c#L329)). This confirms the resolver-slot incompatibility recorded in the earlier ABI review applies to the actual **forked** listener source too; the first field is not a genuine `sceKernelDlsym` name resolver.

When `pipe` is omitted, the pinned socket server defaults it to `1`; `elfldr_exec` duplicates the accepted socket into the spawned process’s stdin, stdout, and stderr. The spawn routine returns its PID after setup rather than waiting for the payload to finish. The connection handler then closes its own accepted fd; child-side duplicated descriptors can keep the connection open ([`socksrv.c`](https://github.com/itsPLK/ps5-elfldr/blob/bb1e117988217a0239679029601e93c7286394d7/socksrv.c#L259), [`elfldr.c`](https://github.com/itsPLK/ps5-elfldr/blob/bb1e117988217a0239679029601e93c7286394d7/elfldr.c#L443), [`socksrv.c`](https://github.com/itsPLK/ps5-elfldr/blob/bb1e117988217a0239679029601e93c7286394d7/socksrv.c#L320)). This is source evidence for the socket’s stdout/stderr route, not proof that a specific payload returns safely or closes those descriptors on firmware 13.60. A custom entry’s `ret` uses the saved target-process continuation; clean termination is still a separate, unmeasured question.

Both the unified autoloader launcher and Payload Manager 0.5.2 connect to `127.0.0.1:9021`, stream the ELF, and close the socket without reading. The unified launcher reports the number of bytes sent; the manager records successful transmission/history. Neither reads payload stdout or gives a payload result ([unified `launcher.c`](https://github.com/itsPLK/ps5-unified-autoloader/blob/915a65e232e03e293829e34bca18866659b2bcf4/src/launcher.c#L12), [manager `ps5_launcher.c`](https://github.com/itsPLK/ps5-payload-manager/blob/e4e72dc9d831dd09ee8fabc222ad1e7f5139050e/src/ps5_launcher.c#L17)). Therefore the former receiving-client design still describes only a client that can connect to an all-interface `elfldr`; it cannot be applied as a direct PC-to-console socket client for this localhost-only fork. A manager-mediated receiving implementation would require a separately designed manager interface that preserves and collects this socket’s output.

## Similar names kept separate

- `itsPLK/ps5-y2jb-autoloader` is a separate YouTube/BD-J style project; its changelog has a “v0.5” entry and its own custom localhost-only loader. It is not the exact `ps5-webkit-autoloader` v0.5.0 tag described above.
- `ps5-payload-dev/elfldr` is the upstream network-facing loader project. Its v0.26 release/source is not the exact bundled asset identity pinned by this WebKit Autoloader build. The downstream `itsPLK/ps5-elfldr` fork at `bb1e117...` binds to loopback.
- `ps5-unified-autoloader` v0.1.5 is the app payload embedded by WebKit Autoloader; Payload Manager 0.5.2 is nested within that payload. Neither version is the WebKit Autoloader version.

No console connection, exploit invocation, product implementation, or write to the device was made for this research.
