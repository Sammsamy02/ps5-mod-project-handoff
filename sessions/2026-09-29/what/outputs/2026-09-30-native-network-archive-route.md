# Native HTTPS and archive dependency route

Initial source/build assessment for the SDK v0.43 ordinary native application. This recommendation originally preceded dependency cross-builds. Subsequent isolated [Mbed TLS](2026-09-30-native-mbedtls-compile-spike.md) and [curl](2026-09-30-native-curl-compile-spike.md) static builds and SDK links succeeded; neither dependency has executed on-console.

## Recommendation

Reuse the existing manager precedent as the fastest initial route: SDK v0.43 (`ps5-payload-dev/sdk@d9c9519116944a7f1c22d262012c53b80b3520b7`), curl tag `curl-8_18_0` peeled commit `2eebc58c4b8d68c98c8344381a9f6df4cca838fd`, Mbed TLS tag `mbedtls-3.6.7` peeled commit `068ff080b369adfac81509f9b57b2afabaf82dc5`, and libarchive tag `v3.8.7` peeled commit `ded82291ab41d5e355831b96b0e1ff49e24d8939`, plus only codecs required by observed package fixtures. The manager uses curl 8.18.0 + Mbed TLS 3.6.0; for new work use the later 3.6.7 security-fix release. These exact tag refs were checked with `git ls-remote`; release pages identify signed tags. Mbed TLS's official 3.6 LTS support runs through March 2027. Pin release-archive checksums as well as peeled commits. Use Mbed TLS's official release tarball because GitHub-generated source archives omit generated files and submodules. Do not let CMake/autoconf probes execute target binaries: use a cross file/toolchain, supply target capability results where necessary, and inspect all link imports.

A smaller alternative is a narrow direct HTTPS client using Mbed TLS plus SDK BSD sockets. That cuts curl features and dependency surface, but requires owning URL/redirect/chunked/content-length handling, HTTP error behavior, proxy policy, TLS hostname/chain checks and robust download resumption. For an official account/download integration, reuse libcurl and its tested protocol handling unless measured payload cost rules it out.

For archives, start with libarchive's C-only static library and disable unused command-line programs, tests, and optional integrations. Use a fixture-driven format matrix before choosing codecs. For common ZIP + 7z + tar packages, likely external codec set is zlib (deflate), bzip2, liblzma (LZMA/XZ), zstd, and lz4; libarchive has internal implementations for some filters and codecs, so enable only where the required reader actually needs them. Do not assume RAR/RAR5 support is complete: the upstream project documents proprietary-format limitations. Defer writing/unpacking install paths until safe extraction rules and target writer/runtime support are separately proven.

## Dependency and platform requirements

- **libcurl**: current community manager build uses curl 8.18.0 with Mbed TLS 3.6.0, static. Upstream curl officially supports selecting Mbed TLS with `--with-mbedtls` (Autoconf) or `CURL_USE_MBEDTLS` (CMake). For a minimal client, disable unused protocols/features (FTP, LDAP, HTTP/2/3, IDN, cookies, proxy only if product policy explicitly excludes proxies) and avoid zlib unless response content decoding is needed. It needs the target socket/DNS/time/threading APIs and normal C runtime; TLS backend is a separate linked library set.
- **TLS and trust**: certificate validation requires a CA trust set, certificate chain verification and hostname verification. curl documents peer verification and hostname verification as separate controls and defaults to verification; an embedded CA bundle or a validated platform CA source is still required. CA bundle provenance/update policy is unresolved. Never disable peer or host verification in the production profile. Official Nexus sign-in/download behavior, redirects, entitlement, and account flow remain unverified.
- **Mbed TLS 3.6.7**: Its tag README specifies Make/CMake libraries `libmbedtls`, `libmbedx509`, and `libmbedcrypto`, linked in that order. `libtfpsacrypto` is newer development/4.x naming and does not apply to this selected 3.6 release. Use the official 3.6.7 release tarball, which includes generated files. Configure client TLS/X.509 and required crypto/entropy modules. Its `library/entropy_poll.c` selects FreeBSD `getrandom()` only when `__FreeBSD_version >= 1200000`; otherwise it uses `sysctl(KERN_ARND)` when that constant is defined, falling back to `/dev/urandom` via stdio. The checked-in SDK v0.43 target headers define `__FreeBSD_version 1104001`, define `KERN_ARND` and declare ordinary BSD `sysctl()`, while `sys/random.h` has no userland `getrandom()` declaration. Under those headers, the expected compile-time Mbed TLS route is `sysctl(KERN_ARND)` (conditional on `__FreeBSD__` being set as expected by the SDK wrapper). This confirms header/build feasibility of the BSD entropy API path; the console runtime return and import availability still need testing. The manager recipe does not override entropy configuration or exercise RNG/TLS at runtime. Confirm the selected source and successful entropy on-target; compile alone does not establish secure target entropy.
- **libarchive**: upstream CMake supports independently toggling integrations. Candidate relevant external libraries are zlib >=1.2.1, bzip2, liblzma (LZMA/XZ), zstd, and lz4. Disable libxml2, OpenSSL (unless needed for archive hash features), expat, nettle, lzo, ACL/xattr, iconv, and unrelated tools/features if the selected package matrix permits. A `CMAKE_SYSTEM_NAME`/target file may still trigger unsupported platform tests; check which feature probes need explicit answers. Keep one static closure and inspect imports after linking.
- **SDK surface**: local v0.43 review documents BSD socket, poll, address conversion, clock, and ordinary libc imports in the SDK. The current native host already uses those standard APIs. This makes a POSIX-style cross-build credible, but the exact symbols imported by curl/mbedTLS/libarchive and their firmware resolution have not been checked. pthread support is present in public community builds but should be required only if using multi handles/threads; start synchronous/single-threaded.

## Evidence classes

**Upstream precedent.** Pinned Payload Manager source at `itsPLK/ps5-payload-manager@e4e72dc9d831dd09ee8fabc222ad1e7f5139050e` sets `CC=prospero-clang`, `AR=prospero-ar`, `RANLIB=prospero-ranlib`; builds Mbed TLS v3.6.0 using default Make `lib` and copies `libmbedtls.a`, `libmbedx509.a`, `libmbedcrypto.a`; then builds curl 8.18.0 static for `x86_64-pc-freebsd` with `--with-mbedtls`, disabling several unused protocols and proxy support. It downloads `https://curl.se/ca/cacert.pem` and copies it to SDK target `etc/ca-bundle.crt`, without pinning the bundle hash or explicitly passing `--with-ca-bundle` in the configure arguments. That establishes a community build recipe; it does not prove this is the runtime-selected CA path. The recipe does not expose entropy configuration or demonstrate TLS execution. Its SDK checkout is not pinned in its Dockerfile.

**Verified upstream pins.** The peeled refs are `mbedtls-3.6.7` = `068ff080b369adfac81509f9b57b2afabaf82dc5`, `curl-8_18_0` = `2eebc58c4b8d68c98c8344381a9f6df4cca838fd`, and `v3.8.7` = `ded82291ab41d5e355831b96b0e1ff49e24d8939`. Mbed TLS's release page identifies a signed release and support through at least March 2027; its primary `BRANCHES.md` states support through March 2027. The curl and libarchive release pages identify signed tags.

**Compile feasibility.** SDK v0.43 target headers show FreeBSD 11.4 compatibility (`__FreeBSD_version 1104001`), the `KERN_ARND` constant, and declaration for ordinary BSD `sysctl()`; `getrandom()` is not declared in its `sys/random.h`. Thus Mbed TLS 3.6.7's default entropy source can compile through the legacy FreeBSD `sysctl(KERN_ARND)` branch, subject to wrapper macro selection. It is a BSD API dependency, not evidence of an app-defined raw syscall. SDK clang wrappers, libc and C++ runtime plus upstream-supported CMake/Autoconf toolchain inputs give a credible cross-build route. The dependency projects are primarily C, so the supplied runtime is not a blocker. At the initial assessment stage, no native SDK cross-build of curl, Mbed TLS, libarchive or the codec closure had been performed. The later Mbed TLS/curl reports supersede that build-only limitation; libarchive/codec work is separate. CMake feature tests, libc/POSIX gaps, entropy, DNS resolver imports, and static link dependencies remain specific feasibility checks.

**Target-runtime evidence.** The ordinary C status host has executed on the user's PS5. That proves basic SDK application startup and its narrow socket/report behavior only. It does not prove TLS, DNS, certificate verification, Nexus login/download, codec behavior, large-file storage, libarchive, or dependency imports on-console. The later integrated DDS/hash C++ core has now passed seven owned fixtures on two native launches; see [native core evidence](2026-09-30-native-core-console-checkpoint.md). That proves its used allocator/exception/single-thread TLS/parser paths, without granting dependency runtime evidence. Treat each dependency and end-to-end behavior as unverified until target evidence exists.
