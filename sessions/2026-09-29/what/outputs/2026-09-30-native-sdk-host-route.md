# Native SDK host route audit — September 30, 2026

## Decision

Build the next **application** bootstrap with the ordinary community `ps5-payload-dev/sdk` runtime, pinned to the real v0.43 release (`d9c9519116944a7f1c22d262012c53b80b3520b7`). Use a C `main`, normal SDK imports and a small native HTTP server. This is a better source-compatible route toward the console-only Nexus app than extending the deliberately freestanding diagnostic with a five-syscall shim. The manager and unified autoloader already use this application model, and SDK v0.42 explicitly added 13.60 support. This is a practical build decision, not a claim that our new app has run on this console. [SDK usage](https://github.com/ps5-payload-dev/sdk/blob/d9c9519116944a7f1c22d262012c53b80b3520b7/README.md), [v0.42 release](https://github.com/ps5-payload-dev/sdk/releases/tag/v0.42), [v0.43 release](https://github.com/ps5-payload-dev/sdk/releases/tag/v0.43).

The earlier exclusion of SDK CRT was a local design choice for the restricted diagnostic. It is not a user ban on the product using the documented homebrew SDK, and it is not an additional approval gate. Keep that diagnostic's scope and artifact intact; create a distinct application target. The SDK runtime is not a privilege-free runtime: it initializes loader-provided kernel state and invokes its existing patch initialization before `main`. A standard application therefore cannot inherit the diagnostic's claim that it has no such initialization. This audit recommends using the established SDK unchanged; it does not design or implement any new privilege patch, kernel-memory operation, exploit, or arbitrary process operation. [CRT startup](https://github.com/ps5-payload-dev/sdk/blob/d9c9519116944a7f1c22d262012c53b80b3520b7/crt/crt.c#L55).

Read-only audit inputs were the four requested local reports, exact public source archives and the existing cached SDK archive. No console/device contact, payload send, source-code edit, index operation or commit was performed. Only this report was added to the repository.

## What default startup actually needs

The ordinary compiler wrapper supplies `crt1.o`, libc and `kernel_web`/SCE library dependencies by default. LLVM 20+ delegates insertion of CRT objects to clang via the SDK environment. The linker wrapper produces PIE with the SDK script and 16 KiB maximum page alignment. These are application link conventions, not a native page-size measurement. [Compiler](https://github.com/ps5-payload-dev/sdk/blob/d9c9519116944a7f1c22d262012c53b80b3520b7/host/bin/prospero-clang), [linker](https://github.com/ps5-payload-dev/sdk/blob/d9c9519116944a7f1c22d262012c53b80b3520b7/host/bin/prospero-lld).

Startup aligns its stack, clears BSS, establishes syscall forwarding, initializes loader state/logging/runtime linking, opens the payload's imports, invokes constructors and calls `main`. The first argument's getpid-stub form is specifically handled by `__crt_syscall_init`; the diagnostic's resolver-only assumption is not inherited. Default startup requires all the supplied loader fields, not merely the first callback and result slot. [Entry assembly](https://github.com/ps5-payload-dev/sdk/blob/d9c9519116944a7f1c22d262012c53b80b3520b7/crt/_start.S), [syscall compatibility](https://github.com/ps5-payload-dev/sdk/blob/d9c9519116944a7f1c22d262012c53b80b3520b7/crt/syscall.c#L38), [CRT](https://github.com/ps5-payload-dev/sdk/blob/d9c9519116944a7f1c22d262012c53b80b3520b7/crt/crt.c), [loader-state initialization](https://github.com/ps5-payload-dev/sdk/blob/d9c9519116944a7f1c22d262012c53b80b3520b7/crt/kernel.c#L279).

Core required exports include libkernel `__error`, `getargc`, `getargv`, `environ`, module load/unload functions, and libc `__isthreaded`, string functions, allocation/free functions, formatting/error functions, `memcpy` and `_Strerror`. Runtime module setup additionally needs `sceSysmoduleLoadModuleInternal`. Optional program-name/argument discovery in `payload_run` must be distinguished from required exports in the runtime-linker initializer. Ordinary app imports then add the functions used by that app. These are resolved through the existing runtime; the application should not manually traverse symbol tables or add a generic syscall dispatcher. [Logging initializer](https://github.com/ps5-payload-dev/sdk/blob/d9c9519116944a7f1c22d262012c53b80b3520b7/crt/klog.c#L87), [runtime initializer](https://github.com/ps5-payload-dev/sdk/blob/d9c9519116944a7f1c22d262012c53b80b3520b7/crt/rtld.c#L520), [SPRX initializer](https://github.com/ps5-payload-dev/sdk/blob/d9c9519116944a7f1c22d262012c53b80b3520b7/crt/rtld_sprx.c#L437), [dlfcn initializer](https://github.com/ps5-payload-dev/sdk/blob/d9c9519116944a7f1c22d262012c53b80b3520b7/crt/rtld_dlfcn.c#L195).

SDK v0.42 declares 13.60 support; v0.43 and the later audited source both contain an explicit `0x13600000` firmware case. The manager and unified README/build files inspected do not offer an independent per-firmware support matrix. SDK support is therefore directly relevant evidence, but not proof of every installed library, supplied loader field or application lifecycle on this particular console. [13.60 source case](https://github.com/ps5-payload-dev/sdk/blob/d9c9519116944a7f1c22d262012c53b80b3520b7/crt/kernel.c#L557).

## User-process dlsym versus NID

Public PS5SDK documentation describes a module-handle plus ordinary symbol-name interface, and its `dynlib_resolve_symbol` forwards that symbol string unchanged to a caller-supplied resolver. Its macros stringify C function names. This establishes public SDK-level name semantics; it does not establish the machine implementation or permission policy of firmware-13.60 syscall 591. [Exact PS5SDK documentation](https://github.com/PS5Dev/PS5SDK/blob/a2e03a2a0231a3a3397fa6cd087a01ca6d04f273/docs/dlsym.md), [resolver](https://github.com/PS5Dev/PS5SDK/blob/a2e03a2a0231a3a3397fa6cd087a01ca6d04f273/crt/dlsym.c), [macros](https://github.com/PS5Dev/PS5SDK/blob/a2e03a2a0231a3a3397fa6cd087a01ca6d04f273/ps5/dlsym.h).

The recommended SDK defines syscall 591 as `SYS_sprx_dlsym`, but its startup does not implement a plain-name-to-591 adapter. Its separate `kernel_dynlib_dlsym` explicitly converts names to NIDs for its own internal lookup. Loader `pt_resolve` uses NID strings when locating exports. Those internal symbol-table lookup arguments cannot be substituted for a public function-name resolver's arguments simply because both are called dlsym. Likewise, the actual fork's slot 0 is a getpid stub, not an ordinary name resolver. [Number definition](https://github.com/ps5-payload-dev/sdk/blob/d9c9519116944a7f1c22d262012c53b80b3520b7/crt/syscall.h#L40), [SDK internal resolver](https://github.com/ps5-payload-dev/sdk/blob/d9c9519116944a7f1c22d262012c53b80b3520b7/crt/kernel.c#L1121), [fork payload arguments](https://github.com/itsPLK/ps5-elfldr/blob/bb1e117988217a0239679029601e93c7286394d7/elfldr.c#L304).

I found no public official Sony specification or firmware-13.60 syscall implementation establishing whether raw 591 accepts ordinary names, NIDs, or both under this launch profile. Earlier public PS4 name-resolution demonstrations are platform/version comparison evidence, not that target contract. A custom 591 shim would still require testing its names, handles and error boundary. The chosen standard SDK application does not require us to solve that custom adapter first: normal imports use the SDK's established runtime path. Do not invent an automatic name/NID fallback.

## Concrete next bootstrap

1. Add a separate `native-host` application target using the verified v0.43 archive and existing LLVM 21.1.8 wrappers. Retain normal startup/default libraries; use the SDK's normal linker script and C `main`. Do not add application syscall assembly, a custom resolver, a patched SDK, or a privileged bootstrap routine. Record archive, dependency, ELF and source hashes in a new manifest. The diagnostic remains its own artifact. [Ordinary sample build](https://github.com/ps5-payload-dev/sdk/blob/d9c9519116944a7f1c22d262012c53b80b3520b7/samples/hello_stdio/Makefile).
2. Cross-build only static libmicrohttpd 1.0.1 for the first native HTTP bootstrap, following the manager's tested dependency route. Skip curl/TLS/frontend tooling until the native lifecycle works. Embed a tiny HTML status page and expose bounded `GET /version`, `GET /report` and an owned `POST /shutdown`. Bind loopback on a distinct fixed port, for example 8085, through MHD's explicit address option; avoid conflicting with manager 8084. External inspection can be an explicit development option later. PS5 browser navigation to loopback gives a console-local UI. No browser launch or shell-icon installation is required in this first checkpoint.
3. `/report` identifies application build/hash provenance, launch profile, schema and startup phase; reports ordinary imported `getpid`, `getuid`, `geteuid`, and `sysconf(_SC_PAGESIZE)` results with their API/error boundary. Do not label them raw kernel carry/errno measurements or capability proof. A successful imported API call is native evidence for that API only. The main program does not need to inspect loader kernel fields or perform raw dlsym calls.
4. Own process lifecycle is selected by the build/launch contract: this app is launched exclusively as its own child through the identified socket-spawn route. Shutdown stops accepting new work, completes its response, stops and joins MHD workers, closes owned files/descriptors, then calls the normal SDK-imported `_exit` with a fixed small status. This avoids falling through to the injected-program continuation or relying on the CRT's context-detection heuristic after `main`. `_exit` is declared in the SDK header and exported by its libkernel stub. Its actual target behavior remains a runtime hypothesis; no custom termination syscall is needed. A shared-process/plugin launcher must reject this artifact. [Declared `_exit`](https://github.com/ps5-payload-dev/sdk/blob/d9c9519116944a7f1c22d262012c53b80b3520b7/include/freebsd/unistd.h#L321), [export](https://github.com/ps5-payload-dev/sdk/blob/d9c9519116944a7f1c22d262012c53b80b3520b7/sce_stubs/libkernel_web.c#L222), [CRT termination distinction](https://github.com/ps5-payload-dev/sdk/blob/d9c9519116944a7f1c22d262012c53b80b3520b7/crt/crt.c#L157).
5. Locally verify app request/report/shutdown state transitions with a host build of the application logic, cross-link the PS5 ELF, inspect its entry/imports/load extents/alignment, and retain an unstripped artifact for review. Static evidence must distinguish application code from the unchanged SDK/runtime. Do not apply the freestanding diagnostic's no-CRT import rules to this target. No PS5 instruction execution on macOS is a valid runtime test.
6. A later authorized console validation has narrow, concrete pass conditions: a known artifact launches, its new HTTP `/report` proves `main` was reached and returns complete schema, ordinary imports report their outcomes, controlled shutdown finishes, and a subsequent app launch can bind the same owned port. Process-exit evidence must be recorded separately; endpoint disappearance alone is insufficient. A bind failure must produce a distinct error and terminate the owned app, never kill an existing process by name.

If that works, add SDK-native curl/mbedTLS and verified CA handling for Nexus network work, an on-console file/cache backend, then integrate shared archive/format modules incrementally. No native game/runtime conversion capability follows merely from an HTTP server. The final app keeps all required analysis/conversion on-console; local build/test scaffolding is not a supported-mod runtime dependency.

This route replaces the custom-syscall adapter as the next product checkpoint. Firmware and installed-byte assumptions stay explicit, but source uncertainty is no longer a reason to endlessly defer an ordinary, reviewable application build. Public-source compatibility plus the running manager make this a reasonable testable hypothesis; only the later native report and lifecycle validation can confirm it on the user's console.

Use fixed routes, strict bounded HTTP requests, checked nonblocking setup, monotonic deadlines/poll and bounded partial sends. A loopback default and a separately labeled temporary LAN development artifact support different inspection paths; neither requires a PC for the final supported-mod workflow. Signal suppression must be checked through the chosen normal API rather than assumed from header presence. This subtask did not implement the application or change the root's design spec.

At the exact manager pin, the normal frontend sends a **raw file body** with `POST /manage:upload?filename=<URL-encoded filename>` and `Content-Type: application/octet-stream`; it does not use multipart/form-data. The server writes chunks to `/data/pldmgr/payloads/<filename>.tmp`, then imports into a derived payload directory and writes metadata. A successful upload returns HTTP 200 body `OK`; upload errors return HTTP 500 body `Error during upload\n`. There is no request-provided expected digest in that upload handler. Import may replace older files in the derived directory, so a later development transfer should use a new, clearly owned basename and inspect the returned stored path before launch. [Frontend upload](https://github.com/itsPLK/ps5-payload-manager/blob/e4e72dc9d831dd09ee8fabc222ad1e7f5139050e/frontend/src/App.jsx#L272), [upload handler](https://github.com/itsPLK/ps5-payload-manager/blob/e4e72dc9d831dd09ee8fabc222ad1e7f5139050e/src/http_server.c#L386), [storage import](https://github.com/itsPLK/ps5-payload-manager/blob/e4e72dc9d831dd09ee8fabc222ad1e7f5139050e/src/payload_mgr.c#L326).

Launch is the frontend's ordinary GET request to `/loadpayload:<encoded path>`. The server validates an allowed path or resolves the safe basename; path failure gives HTTP 400 `Invalid payload name\n`, transport failure HTTP 500 `Failed to launch payload\n`, and successful transport HTTP 200 `OK`. `ps5_launch_elf` opens the stored file, connects to `127.0.0.1:9021`, reads 8,192-byte chunks, loops through short sends, then closes both socket and file. It adds history only when the read/send loop has no reported error. There is no payload result read, PID return, import-resolution acknowledgment, `main` acknowledgment or child-exit acknowledgment. For the new metadata app, its own complete `/report` must supply the separate native execution evidence.
