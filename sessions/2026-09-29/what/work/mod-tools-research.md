# Native PS5 portability of representative PC mod loaders

Research only, checked against official upstream repositories and engine documentation on 2026-09-29. No loader, game, console, or compatibility shim was tested. “Potential” below is an engineering inference, not a claim of working PS5 support. No native PS5 release/support claim was found in the examined official documentation for Mod Engine 2, me3, SKSE/F4SE, REFramework, BepInEx, or MelonLoader.

## Conclusion

A reusable Nexus-facing manager is plausible, but manager reuse and mod-runtime reuse are different problems. A manager can manage downloads, profiles, dependencies, conflicts, staging and rollback across many games. Loading PC mods in native console games requires verified game/platform adapters. A jailbroken host may supply access needed to develop such adapters; it does not make PC game executables, DLL ABIs, game object layouts, or cooked assets identical to console builds.

Do not promise “majority of games” or automatic Windows-DLL translation on the basis of these loaders. None of the examined upstreams establishes that breadth on native PS5. A game can support data replacement while not supporting that game's native-code plugins.

## Mod Engine 2: source-level findings

ME2 is discontinued and archived. Its README directs future work to [me3](https://github.com/garyttierney/me3). The old README lists Dark Souls III and Elden Ring as supported; the archived launcher and mod-loader source also explicitly contain Armored Core VI targets, illustrating that README checklists should not be used as the sole source for exact scope. [Official README](https://github.com/soulsmods/ModEngine2/blob/main/README.md), [launcher source](https://github.com/soulsmods/ModEngine2/blob/main/launcher/launcher.cpp), [mod-loader source](https://github.com/soulsmods/ModEngine2/blob/main/src/modengine/ext/mod_loader/mod_loader_extension.cpp).

The extension connector is a C++ interface with virtual methods for game-qualified direct hooks, scanned hooks, fixed-address or signature-based patches, configuration, logging and a Lua state. External extensions export `modengine_ext_init`, then receive this connector. Lifecycle methods are `on_attach`, `on_detach` and `id`. The public helper for module-symbol hooks calls `GetModuleHandleW` and `GetProcAddress`. The interface passes STL/sol2 types and even contains TODOs about ABI compatibility. A declared stable API between ME2 releases is not a platform-independent native plugin ABI. [Extension API](https://github.com/soulsmods/ModEngine2/blob/main/include/modengine/extension.h), [extension loading](https://github.com/soulsmods/ModEngine2/blob/main/src/modengine/extension_set.cpp), [ABI note](https://github.com/soulsmods/ModEngine2/blob/main/include/README.md).

The loading and scanning infrastructure is tied to Windows. Extensions use `LoadLibraryW` and process-module enumeration. The scanner uses Windows memory queries/protection APIs, reads a PE image header, and obtains the image base from the Windows process environment. Hooks are installed with Microsoft Detours; a scanned call hook explicitly assumes an x64 near-call instruction. [Extension loading](https://github.com/soulsmods/ModEngine2/blob/main/src/modengine/extension_set.cpp), [memory scanner](https://github.com/soulsmods/ModEngine2/blob/main/include/modengine/util/memory_scanner.h), [hook installation](https://github.com/soulsmods/ModEngine2/blob/main/src/modengine/hook_set.cpp).

The launcher locates named Steam Windows executables and launches them with `modengine2.dll` using `DetourCreateProcessWithDllW`. Its build configuration uses an `x64-windows` dependency path and requires the MSVC frontend when compiling with Clang. These mechanisms need replacement on a native console target. [Launcher](https://github.com/soulsmods/ModEngine2/blob/main/launcher/launcher.cpp), [build configuration](https://github.com/soulsmods/ModEngine2/blob/main/CMakeLists.txt).

Most importantly, the file-mod implementation is more than an OS-file API hook: it changes internal archive paths to loose-file paths, then redirects the filesystem request. The first stage hooks game-private archive-path functions; its source uses DS3 fixed RVAs and Elden Ring/AC6 machine-code signatures, plus game-specific audio resolver hooks. The second stage hooks `kernel32.dll!CreateFileW`. Game string structures and function prototypes are reconstructed explicitly. Porting the second stage does not locate or correctly invoke the console's first stage. [Game-specific registration](https://github.com/soulsmods/ModEngine2/blob/main/src/modengine/ext/mod_loader/mod_loader_extension.cpp), [archive override logic](https://github.com/soulsmods/ModEngine2/blob/main/src/modengine/ext/mod_loader/archive_file_overrides.cpp), [string/prototype definitions](https://github.com/soulsmods/ModEngine2/blob/main/src/modengine/ext/mod_loader/archive_file_overrides.h).

Useful reuse: configuration/profile concepts; multiple ordered mod roots; file override lookup/cache logic after adapting path/string behavior; extension lifecycle; a separation of host hooks from game adapters. Not established reuse: unchanged DLL binaries, Windows loader/scanner, Windows Detours integration, signatures/RVAs, reconstructed game layouts, or asset compatibility on PS5.

## Current successor: me3

The [official me3 README](https://github.com/garyttierney/me3) lists Windows, Linux via Proton, and macOS via CrossOver, with five FROM SOFTWARE targets: DS3, Sekiro, Elden Ring, AC6 and Nightreign. The [official introduction](https://github.com/garyttierney/me3/blob/main/docs/index.md) calls it ME2's successor. Linux setup includes a separate `bin/win64` location; the [default Cargo target](https://github.com/garyttierney/me3/blob/main/.cargo/config.toml) is `x86_64-pc-windows-msvc`. These are evidence of running Windows-target runtime components alongside the Windows game under compatibility software, not a native-console port.

Prefer current me3 profile semantics to basing a new design solely on archived ME2. Its versioned TOML profile distinguishes asset override `packages` from native `natives`, associates supported games, and supports load-order constraints, optional native initialization/finalization, and profile save selection. [Configuration reference](https://github.com/garyttierney/me3/blob/main/docs/configuration-reference.md), [schema](https://github.com/garyttierney/me3/blob/main/schemas/mod-profile.md). Reusing these semantics can simplify a PS5 manager, but its native entries still describe DLLs and its packages still describe the supported games' DVDBND hierarchy.

SKSE/F4SE sources: [SKSE official compatibility page](https://skse.silverlock.org/), [F4SE official compatibility page](https://f4se.silverlock.org/), [SKSE plugin loader](https://github.com/ianpatt/skse64/blob/master/skse64/PluginManager.cpp), [SKSE plugin ABI/version rules](https://github.com/ianpatt/skse64/blob/master/skse64/PluginAPI.h), [SKSE game-private addresses and Windows TLS](https://github.com/ianpatt/skse64/blob/master/skse64/GameAPI.cpp), [F4SE plugin manager](https://github.com/ianpatt/f4se/blob/master/f4se/PluginManager.cpp). Upstream compatibility with one Windows runtime/storefront does not establish compatibility with another platform. The official pages describe the restrictions of console-like locked-down store applications, but do not prove that a hypothetical jailbroken port is impossible.

REFramework sources: [README/install and Proton instructions](https://github.com/praydog/REFramework), [Lua introduction](https://refdocs.praydog.com/), [engine SDK and hooks](https://refdocs.praydog.com/api/sdk.html), [build dependencies](https://github.com/praydog/REFramework/blob/master/CMakeLists.txt). Its Lua API calls RE engine methods and reads reflected game objects. Windows import translation cannot create the matching console reflection and call/hook ABI. Scripts dependent on draw/VR/renderer features need those bindings ported too.

BepInEx/MelonLoader sources: [BepInEx scope/platform table](https://github.com/BepInEx/BepInEx), [BepInEx native IL2CPP installation](https://docs.bepinex.dev/master/articles/user_guide/installation/unity_il2cpp.html), [MelonLoader desktop/support requirements](https://github.com/LavaGang/MelonLoader), [Unity Doorstop runtime model](https://github.com/NeighTools/UnityDoorstop), [Il2CppInterop bridge](https://github.com/BepInEx/Il2CppInterop), [Unity scripting backend explanation](https://docs.unity.com/en-us/engine/6000.3/manual/scripting/compilation-and-code-reload/script-compilation/backends/intro). BepInEx's native Linux support is real evidence of portable host components, unlike Proton-only support; native Linux support still does not establish PS5 support. Also distinguish managed .NET `.dll` files from native Windows PE `.dll` files.

Assets sources: [Epic cooking/packaging documentation](https://dev.epicgames.com/documentation/unreal-engine/packaging-your-project), [Epic packaging/signing/encryption reference](https://dev.epicgames.com/documentation/en-us/unreal-engine/packaging-projects?application_version=4.27), [Unity AssetBundle platform constraints](https://docs.unity.com/en-us/engine/6000.0/manual/assets-and-media/assets-managing-runtime/assetbundles-section/platforms). Epic explicitly explains that cooking makes platform-specific content and console packaging requires a source build; Unity likewise says AssetBundles are platform-specific. Thus “no native code” is a favorable property, not proof of cross-platform compatibility.

## Practical architecture (proposed, not an existing working port)

1. Keep the manager independent of the game runtime: catalog/downloads, archive extraction, staging, profiles, dependencies, conflict reporting and reversible deployment. Use a title/build compatibility database and explicit supported mod categories.
2. Give each game adapter an identity tuple including title/region, native PS5 versus PS4 game running on PS5, exact update/build fingerprint and relevant engine revision. Declare asset formats, deployment path, loader dependencies, script/runtime API coverage and verified mod categories. Do not infer support from game name alone.
3. Provide separate deployment modes for asset/data replacements, engine-script mods and native modules rebuilt for the console. Support the modes that have been verified for each adapter. A framework-dependent package must resolve a compatible console framework, not just have its files copied.
4. Build a small platform host for filesystem/loading, memory/hooks, lifecycle/logging, and optional input/render integration. Design a versioned C ABI with opaque handles and explicit sizes across module boundaries; avoid assuming ME2's C++ STL/vtable ABI can cross toolchains/platforms unchanged. Source-available native plugins are a much more practical early target than arbitrary closed Windows binaries.
5. Implement the game layer separately: console-build function locations and call conventions, object/string/allocator layouts, engine reflection or scripting bridge, archive/asset resolution, and version gates. Share an engine-family layer only after its invariants are demonstrated on the console builds.
6. Gate each adapter on evidence: clean launch, a small observable file override, one script or native plugin only if that mode is claimed, negative checks for wrong build/dependencies, restore/rollback, then broader mod combinations. Track verified compatibility at game-build × mod-version × mod-category granularity.

## Why a general Windows API shim is insufficient

There are at least three distinct boundaries: loading/executing a Windows module; binding its framework/OS API calls; and satisfying its assumptions about the host game's private binary. A shim can help the first two for a bounded plugin, but cannot automatically supply correct game addresses, byte signatures, structures, object ownership, vtables, allocations, engine methods or content formats. ME2 and SKSE source demonstrate these third-boundary dependencies directly. REFramework and IL2CPP frameworks add engine metadata and managed/native interop dependencies. Rendering-dependent plugins introduce another large integration layer.

Proton success is relevant evidence that Windows mods can operate when the Windows game remains their host under a Windows compatibility environment. It is not evidence that those same mods can be attached to the separate native PS5 game binary. Treat arbitrary binary translation as a research track for individually constrained plugins; treat per-game/engine adapters and rebuilt native modules as the main architecture.

“Support a majority” needs a defined game list and measurable mod categories. A broad manager UI can exist before broad loading support; communicate the actual verified runtime coverage separately.
