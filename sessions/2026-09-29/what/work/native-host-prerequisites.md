# Native PS5 host prerequisites — source audit

Internal research note, September 29, 2026. Read-only examination of community upstream sources; no dependency installation, payload build, console connection, or runtime verification. This is evidence for architecture discussion, not an approved implementation specification. The objective remains automatic translation across PC mod categories without per-mod hardcoding, with Stellar Blade selected by the user as the first hardware test target. The libraries below are shared infrastructure for potential reusable translation/runtime backends and do not establish universal translation as achievable.

## Evidence level

The SDK and PacBrew sources provide concrete native build recipes and example payloads. Package presence proves that a recipe exists, not successful execution on the user's claimed 13.60 environment. The examined [library build script](https://github.com/ps5-payload-dev/pacbrew-repo/blob/main/ci-libs.sh) builds and installs cross packages on the development host; it does not run console tests. OpenSSL's recipe explicitly disables its tests. No 13.60 runtime assurance is inferred from these files. The currently working console loader and its process/privilege context remain material inputs.

## Filesystem and deployment primitives

The [kernel stub source](https://github.com/ps5-payload-dev/sdk/blob/master/sce_stubs/libkernel_web.c) exposes `open`, `read`, `write`, `close`, `stat`, `lstat`, `mkdir`, `unlink`, `rename`, `fsync`, `chmod`, and `fchmod`. These are linker/import stubs rather than independent filesystem implementations. The [stub build](https://github.com/ps5-payload-dev/sdk/blob/master/sce_stubs/Makefile) makes `.so` stubs with `.sprx` sonames; the payload resolves them at runtime. The [directory-listing sample](https://github.com/ps5-payload-dev/sdk/blob/master/samples/list_files/main.c) uses POSIX directory/stat functions and temporarily changes its process root vnode through SDK kernel helpers.

Inference: a host can be investigated using ordinary POSIX file operations, but availability of a symbol does not establish write permissions, writable game mounts, atomic same-filesystem rename behavior, directory synchronization, or durability after interruption. Console testing must characterize the actual project-owned storage path and separately the selected game's deployment path. `fsync` and `rename` imports do not guarantee a reliable transaction scheme on every mount. Payload process credentials, jail/root state, and mounted game content matter independently.

## Standalone payload versus in-game module

The [SDK README](https://github.com/ps5-payload-dev/sdk) documents ELF payload loaders; it does not equate payload execution with native game attachment. The [shared-object sample](https://github.com/ps5-payload-dev/sdk/blob/master/samples/hello_so/Makefile) builds a host ELF and a chain of native `.so` dependencies. The SDK [runtime loader](https://github.com/ps5-payload-dev/sdk/blob/master/crt/rtld.c) selects distinct `.sprx` and `.so` loaders. Its [dlfcn implementation](https://github.com/ps5-payload-dev/sdk/blob/master/crt/rtld_dlfcn.c) loads modules beneath the payload's root context and supplies `dlopen`/`dlsym`/`dlclose`; `RTLD_TRACE`, `RTLD_NOLOAD`, `RTLD_NEXT`, and `RTLD_SELF` are unsupported in the inspected implementation.

The [native `.so` loader](https://github.com/ps5-payload-dev/sdk/blob/master/crt/rtld_so.c) reads ELF metadata, maps segments, relocates native symbols, and uses a kernel helper when marking memory executable. Its relocation switch handles the specific x86-64 ELF types `JMP_SLOT`, `64`, `GLOB_DAT`, and `RELATIVE`, rejecting other relocation types. The SDK `dlopen` path calls module initialization; loading is not a guaranteed nonexecuting inspection operation. This is useful evidence for a host's own compatible native extensions. It is not a PE/DLL loader, Windows API layer, or facility that automatically establishes execution inside a different game process. Executable mapping and unloading need independent tests under the working loader; a game runtime backend also needs verified game-thread/lifecycle access, ABI marshalling, and engine symbols.

## Minimal host choices supported by this evidence

Research choice, conditional on architecture approval: investigate a standalone C/C++ ELF host with SDK libc, static libc++, curl/OpenSSL plus deployed CA bundle, one JSON parser (Jansson is a simple C choice), and libarchive. SDL's software display/controller backend with ImGui's SDL renderer is the smallest evidenced UI combination here. Keep Lua 5.4 as an optional script-language backend; consider LuaJIT only where the mod API and executable-memory behavior justify it. Compatible host extensions can use the SDK's native ELF loader after its supported relocation and lifetime behavior are verified.

This foundation is relevant to Nexus transport, mod inspection, translation orchestration, and eventual engine/game runtimes. It provides no evidence of a universal translator. Native PC plugins still require a Windows/PE/ABI compatibility route or recompilation plus console engine bindings; asset/data transformations require understood target formats and load rules; script frameworks require their host APIs. Neither a package repository nor generic Lua/ELF loading substantiates automatic Skyrim first-person plugin translation, automatic pak conversion, or all-mod coverage.
