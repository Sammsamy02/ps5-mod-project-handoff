# UE4SS native-console feasibility research

Research date: 2026-09-29. Scope: official UE4SS documentation/source and a candidate debugger's upstream claims, with no implementation or device test. The user's claimed PS5 firmware 13.60 jailbreak is outside this note's verification scope. No PS5 compatibility is established.

## Finding

The upstream project currently exposes a Win64 build target. A native PS5 integration would be a port of UE4SS's operating-system, binary-discovery, hooking, and Unreal ABI bridge, followed by validation for each console game build. A Nexus-connected manager can distribute files and metadata, but that does not supply this bridge.

## Primary evidence

- **Platform configuration:** `UE4SS_PLATFORM_TYPES` contains only `Win64`; its definitions include `PLATFORM_WINDOWS`, `PLATFORM_MICROSOFT`, `OVERRIDE_PLATFORM_HEADER_NAME=Windows`, and `UBT_COMPILED_PLATFORM=Win64`. The target also sets x86_64. [ProjectConfig.cmake](https://github.com/UE4SS-RE/RE-UE4SS/blob/main/cmake/modules/ProjectConfig.cmake#L9-L12), [Windows definitions](https://github.com/UE4SS-RE/RE-UE4SS/blob/main/cmake/modules/ProjectConfig.cmake#L47-L49).
- **Loader and lifecycle:** the entry point includes `Windows.h`, implements `DllMain`, resolves its path with `GetModuleFileNameW`, creates a Windows thread, and uses Windows thread enumeration and APCs. These are source-level dependencies rather than a packaging preference. [main_ue4ss_rewritten.cpp](https://github.com/UE4SS-RE/RE-UE4SS/blob/main/UE4SS/src/main_ue4ss_rewritten.cpp).
- **Runtime dependencies:** the main shared library links `PolyHook_2`, `d3d11`, `opengl32`, `dbghelp`, `psapi`, `ws2_32`, `ntdll`, and `userenv`, and selects the Microsoft dynamic CRT. Its program installs PE import-table hooks on `kernel32.dll`'s `LoadLibrary` functions. [UE4SS/CMakeLists.txt](https://github.com/UE4SS-RE/RE-UE4SS/blob/main/UE4SS/CMakeLists.txt#L123-L147), [UE4SSProgram.cpp](https://github.com/UE4SS-RE/RE-UE4SS/blob/main/UE4SS/src/UE4SSProgram.cpp#L292-L315).
- **Native mods:** upstream looks in `Mods/<mod>/dlls/` for `main.dll` or `<mod>.dll`, loads it with `LoadLibraryExW`, and looks up `start_mod` and `uninstall_mod` exports. The creation guide returns a C++ `CppUserModBase*` across that boundary, so a port must validate the compiler/runtime object ABI as well as the exported names. [CppMod.cpp](https://github.com/UE4SS-RE/RE-UE4SS/blob/main/UE4SS/src/Mod/CppMod.cpp#L13-L55), [C++ mod guide](https://docs.ue4ss.com/dev/guides/creating-a-c%2B%2B-mod.html). The installation documentation explicitly keeps a native-mod template synchronized to a release for ABI compatibility. [Installing a C++ mod](https://docs.ue4ss.com/dev/guides/installing-a-c%2B%2B-mod.html).
- **Lua layer:** a Lua mod is source in `Mods/<mod>/scripts/main.lua`, enabled through `mods.txt`. Scripts use UE4SS bindings to locate and manipulate live Unreal objects, invoke methods, and access fields. Lua modules containing native Windows DLLs are a separate dependency. [Creating a Lua mod](https://docs.ue4ss.com/dev/guides/creating-a-lua-mod.html). The repository builds the Lua interpreter from source as `LuaRaw`, making it a candidate for reuse after platform review. [LuaRaw build](https://github.com/UE4SS-RE/RE-UE4SS/blob/main/deps/first/LuaRaw/CMakeLists.txt).
- **Per-game assumptions:** the project warns that it is not guaranteed to work with every game. Its compatibility guide requires signatures for globals/functions such as `GUObjectArray`, `FName::ToString`, `StaticConstructObject_Internal`, and `GMalloc`. [README](https://github.com/UE4SS-RE/RE-UE4SS/blob/main/README.md), [Fixing missing AOBs](https://docs.ue4ss.com/guides/fixing-compatibility-problems.html). Games with engine changes can need `UE4SS_Signatures`, `MemberVariableLayout.ini`, and `VTableLayout.ini`; these may become obsolete after updates. [Custom Game Configs](https://docs.ue4ss.com/dev/custom-game-configs.html).
- **Thread and hook behavior:** `ExecuteInGameThread` depends on a working `ProcessEvent` or `EngineTick` hook. `RegisterHook` targets a loaded `UFunction` by its full name. Thus running a Lua interpreter alone does not establish gameplay integration. [ExecuteInGameThread](https://docs.ue4ss.com/dev/lua-api/global-functions/executeingamethread.html), [RegisterHook](https://docs.ue4ss.com/dev/lua-api/global-functions/registerhook.html).
- **Build-source limit:** the Unreal bridge is a submodule named `UEPseudo`; the README says linked Epic/GitHub access is needed. This research did not access that restricted submodule or console SDK material. [Submodules](https://github.com/UE4SS-RE/RE-UE4SS/blob/main/.gitmodules), [Build requirements and instructions](https://github.com/UE4SS-RE/RE-UE4SS/blob/main/README.md#build-requirements).

## Porting implications — engineering inferences

1. Replace DLL/proxy initialization with an evidenced native in-process module loading and lifecycle mechanism. Abstract paths, logging, threads, synchronization, input, dynamic-library loading, crash reporting, and UI. A first headless probe can omit the desktop GUI, but the dependency graph still needs audit.
2. Replace Windows/PE module discovery and import hooks. Provide console-native executable-region enumeration, signature scanning, and hook installation with correct page protection, instruction relocation, and cleanup.
3. Validate every boundary to the console Unreal build: calling conventions, types and alignments, string representation, allocator behavior, UObject/FName/property layouts, vtables, and function parameter/return marshalling. Sharing an instruction set or engine version does not establish this ABI.
4. Develop and validate a profile for one exact title/update: engine fork/version, identifiers, globals, function addresses, layouts, timing, and game-thread hooks. Windows signatures and layouts are evidence to compare, not console defaults.
5. Preserve the Lua API where possible. Pure Lua script logic and source-based parsers/binding utilities are plausible reusable pieces, subject to validation. Existing PC native DLL mods need source-level ports/rebuilds against the new interface. Lua mods that import native DLLs or hardcode PC paths, keyboard input, game class names, or signatures need additional adaptation.

**Windows translation inference:** a Windows compatibility environment could potentially run Windows authoring tools or a Windows build of a game, if that environment itself exists and meets their requirements. It does not automatically make a Windows UE4SS DLL share the native console game's process, object layout, or function ABI. A hybrid bridge would still have to solve the native interop problems above.

## Bounded research probe

Before a mod-manager product, choose one exact, owned Unreal title/build and identify the actual supported device execution environment. Record upstream UE4SS revision, console/game build identifiers, toolchain, module format, and available documented loading/debugging facilities. Do not assume the claimed firmware implies a working native-game module loader.

**Candidate probe backend, not a verified runtime:** the `ps5debug-NG` upstream documentation claims process metadata/maps, target ELF loading, and six-register SysV calls. It explicitly says its `CMD_PROC_INTALL` RPC-install handler is a stub returning a zero handle. Its firmware table includes 13.60, but these remain upstream claims until checked on the user's device and exact target. [ps5debug-NG README](https://github.com/Pharaoh2k/ps5debug-NG#primary-features), [installer source](https://github.com/Pharaoh2k/ps5debug-NG/blob/master/installer/source/main.c). These facilities may support the probe below; they do not provide UE4SS bindings, complete Unreal C++ ABI marshalling, or general PC DLL compatibility.

Evaluate in successive gates:

1. **Native runtime gate:** a minimal native module executes within the chosen target process, writes a timestamped log, runs a Lua source script, and exits or unloads cleanly. Success establishes loading and Lua only.
2. **Read-only Unreal gate:** resolve and validate object/name discovery; obtain the full name and one known property of a live object from Lua. Repeat across multiple starts and a map transition without invalid memory reads. Log the precise engine and layout profile used.
3. **Hook/ABI gate:** route one harmless callback onto the game thread, invoke one validated reflected getter, then register/unregister a known event callback. Confirm correct parameters, return value, cleanup, and continued gameplay through reload/transition.
4. **Mod gate:** adapt one small pure Lua mod with no native dependencies, show an observable reversible change, restore its original value, and disable the mod without corrupting state. Record that compatibility only for the tested title/build.

Stop if a gate lacks evidence; keep support marked experimental and title/build-specific. Generic Lua execution, a booting GUI, successful downloading, or a single startup log cannot substantiate broad UE4SS or PC-mod compatibility.
