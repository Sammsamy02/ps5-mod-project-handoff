# Universal native-console mod translation: primary-source research

Research only, checked 2026-09-29. No implementation, dependencies, accounts, or console/device access. This preserves the requested goal: automatically translate Nexus mod packages across installed native PS4/PS5 titles, including assets, scripts, native plugins, Skyrim camera mods, UE4SS and ME2-dependent mods. Stellar Blade is the first test title, not the product's coverage limit. Firmware 13.60 execution/injection prerequisites are separate and are not established by these sources.

## Feasibility argument

A universal product can have one automatic ingest/classification pipeline and shared translation backends for complete runtime/format categories. It does not need a bespoke installer or handcrafted rule for each downloaded mod. However, file loading, OS/ABI compatibility, and correspondence between different game builds are separate problems. The sources below establish reusable machinery for the first two and concrete reasons the third needs its own verified knowledge. They do not establish a working PS4/PS5 implementation or universal coverage.

Proposed research architecture (inference/design, not an implemented system):

1. **Identify the target exactly.** Distinguish the installed PS4 title running through backward compatibility from a native PS5 title. Fingerprint title, region, update, executable and relevant asset schemas; detect engine/runtime revisions and game customizations. Do not infer compatibility from the title name alone.
2. **Automatically classify the whole mod package.** Parse archives, magic bytes, install manifests, dependency declarations, executable imports/exports, and asset/script schemas. A package can contain several categories simultaneously. Resolve dependency versions and install ordering before translation.
3. **Create a shared intermediate representation.** Preserve dependency graph, provenance and target requirements. Represent resource replacements and record edits; script operations and bindings; native code's imports, calls, callbacks, memory accesses, patches and hook preconditions. Binary-only native modules may need lifting/instrumentation rather than only source recompilation. Unknown effects remain unresolved requirements rather than being silently installed.
4. **Use reusable category backends.** Engine asset serializers and target platform cooking/conversion; script VM and extension APIs; native PE loading, Windows API compatibility, calling-convention/callback bridges, and game-object/hook translation. These are broad backends reused across mods. Native frameworks such as SKSE, UE4SS and ME2 also need their expected host behavior represented; loading their DLL is not the same as providing that behavior.
5. **Discover and validate game-build correspondences.** An automatic discovery subsystem can reuse reflection, type metadata, symbols when available, structural binary matching, signatures and observed behavior. Cache the resulting verified mappings for an exact build. This is game/build knowledge, not a per-mod hardcoded installer. An engine-wide backend supplies common rules, but must recognize game-specific serializers, custom engine changes and functions without equivalents.
6. **Validate effects, then optimize.** Check package/reference integrity and native hook preconditions; compare mod behavior and state transitions against an oracle; measure frame-time, memory and load-time changes. Cache asset translations by source/target hashes, precompute bindings and compile hot call bridges once the signatures are known. Cross-title and cross-category tests are required before widening coverage claims.

This architecture is a plausible research direction. The unproven core is automatic semantic correspondence: deriving the correct target object layout, function, hook site and effect from a source mod and a different native build. No reviewed primary source demonstrates a generic solver for all such cases.

## Concrete stress case: Improved Camera SE

The maintainer's [ImprovedCameraSE-NG README](https://github.com/ArranzCNL/ImprovedCameraSE-NG/blob/main/docs/README.md) describes a first-person Skyrim SE mod, requires SKSE and Address Library, lists Windows/MSVC build requirements, and advertises PC game versions 1.5.97–1.6.1179. This is a useful native-plugin test case rather than an interchangeable asset package. The README's advertised range is not a current compatibility guarantee: the [SKSE official site](https://skse.silverlock.org/) now lists different builds for specific PC game versions, including AE 2.3.1 for game 1.7.104, GOG AE 2.2.6 for 1.6.1179, SE 2.0.20 for 1.5.97, and VR 2.0.12 for 1.4.15.

The actual [Hooks.cpp](https://github.com/ArranzCNL/ImprovedCameraSE-NG/blob/main/ImprovedCamera/source/skyrimse/Hooks.cpp) installs camera, first-person, input and ragdoll hooks, replaces vtable entries and generates x86 trampoline stubs. Hook addresses combine `REL::RelocationID` with offsets inside functions; `UpdateCamera` uses IDs 49852/50784 plus `0x1A6`. Its callback directly reads `TESCamera.currentState.id`. Other patches rewrite instructions and expect an actor pointer in a particular register. A generic import shim does not intercept that direct member read or identify the equivalent target call site. To preserve behavior, a translator must resolve object access and internal patch semantics too. Relevant source lines: 63–105, 141–209, 351–388, 505–578.

[Addresses.cpp](https://github.com/ArranzCNL/ImprovedCameraSE-NG/blob/main/ImprovedCamera/source/skyrimse/Addresses.cpp) calls internal engine functions through paired IDs, e.g. `Get3D` uses 19308/19735. [SkyrimSE.cpp](https://github.com/ArranzCNL/ImprovedCameraSE-NG/blob/main/ImprovedCamera/source/skyrimse/SkyrimSE.cpp) queries Windows executable version resources and module information, then recognizes explicit PC version families. [plugin.cpp](https://github.com/ArranzCNL/ImprovedCameraSE-NG/blob/main/ImprovedCamera/source/plugin.cpp) checks a configured game-version range and the presence/version of `skse64_loader.exe`. Emulating those checks may satisfy initialization, but does not supply the actual engine functions behind the IDs.

[CommonLibSSE-NG](https://github.com/CharmedBaryon/CommonLibSSE-NG) explicitly targets Skyrim SE, AE and VR and provides abstractions for their differing ABIs/layouts. Its [Runtime Targeting guide](https://github.com/CharmedBaryon/CommonLibSSE-NG/wiki/Runtime-Targeting) distinguishes address relocation, member-offset relocation, and virtual-function relocation. It explains that changed member layouts require accessors and changed vtable layouts require different virtual-function slots. Its documented VR limitations include incompletely reverse-engineered `PlayerCharacter` members. This is positive evidence that shared runtime abstraction is achievable, and that it relies on known game semantics rather than a loader alone. It does not claim PlayStation mappings.

The author's [Address Library Database](https://github.com/meh321/AddressLibraryDatabase) stores identifiers paired with offsets per supported game version and separately stores names; it describes importing names from version-specific IDA databases. This is a relocation database for identified builds, not an address translator that inherently knows a console executable. The [Skyrim VR Address Library](https://github.com/alandtse/skyrim_vr_address_library) is an existing partial automation example: it records SSE-to-VR mappings with confidence statuses ranging from unknown and tool suggestions to manual verification and bit-identical results. Automatic candidate discovery and verified correspondence are explicitly different states.

## What a Windows ABI/API backend can solve

The official [Wine source README](https://github.com/wine-mirror/wine/blob/master/README.md) defines Wine as a Windows binary loader plus Windows API implementations using Unix equivalents. This supports the idea of a reusable Windows compatibility backend rather than rewriting every Windows mod's OS calls. It documents supported host operating systems and kernel-thread requirements; it does not establish PlayStation support or native-console-game interoperability. Wine normally preserves the program's own Windows build and object assumptions. Running a PC game under Wine therefore is not evidence that a PC plugin can attach to a separately compiled console game.

The upstream [libffi manual](https://github.com/libffi/libffi/blob/master/doc/libffi.texi) provides runtime-described calls and closures for supported ABIs. It requires the function pointer, argument count/types and return type; a layer above it must handle type conversion. Structures must be described, multiple-ABI support is platform-specific, and closures require executable allocation support. Consequently libffi can help implement known native-call/callback bridges, but does not discover the target function or the meaning/layout of an arbitrary engine pointer. Passing an actor pointer through a correct call sequence does not make PC code's direct loads and virtual dispatch compatible with a different actor layout.

Microsoft's [PE specification](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format) documents sections, machine type, imports/exports, base relocations, TLS, and exception metadata. A PE loader must support the module's requirements, not merely copy its code section. Imports can be mapped to compatibility services, and ordinary relocation can correct module-base changes. It cannot on its own relocate an undocumented patch at a semantically equivalent location inside another executable. The same instruction-set architecture also does not establish compatible object layouts or engine services.

For binary-only modules, two potentially reusable strategies deserve experiments: preserve a guest object/memory model with translated boundary objects, or lift/rewrite guest accesses and calls into the target model. Both require identity, lifetime, ownership, virtual dispatch and concurrency semantics to be correct. Source availability simplifies rebuilding but does not eliminate the need for correct game bindings.

## Cooked assets: bounded claims from official engine documentation

Epic's [Content Cooking](https://dev.epicgames.com/documentation/en-us/unreal-engine/cooking-content-in-unreal-engine) describes cooking as conversion to platform-specific formats. Epic's [Packaging Your Project](https://dev.epicgames.com/documentation/en-us/unreal-engine/packaging-your-project) states that assets are compressed/optimized, unused data is omitted, and Pak files contain cooked content. Therefore a change of archive container alone does not prove platform compatibility. If a target conversion needs information omitted from the distributed cook, source data or reconstruction may be needed; the docs do not justify claiming every cooked asset can or cannot be converted.

Epic's [Working with Cooked Content](https://dev.epicgames.com/documentation/en-us/unreal-engine/working-with-cooked-content-in-the-unreal-engine) is explicitly scoped to Windows. It describes cooked assets as read-only in the editor, possible `.uasset`/`.uexp`/`.ubulk` splits, required preservation of reference paths, and known issues for some asset types. This is evidence against a guaranteed universal “unpack, open, re-cook” workflow. It is not evidence that all raw data is irrecoverable. Exact title/engine-version/platform asset samples are still necessary; these general current docs do not identify Stellar Blade's particular console package formats.

## Exact missing evidence before claiming “all mod types work”

- A verified console execution path on the exact firmware/model, including access needed to mount replacement resources, load the runtime, hook the installed native game, support required executable memory/callbacks, and recover cleanly. Firmware 13.60 is unverified in this brief.
- Exact installed title/update/build fingerprints and corresponding accessible source/target binaries or adequate metadata for testing mappings; PS4 and native PS5 builds tested separately.
- Demonstrated automatic classification and dependency resolution on mixed packages, framework dependencies, installers and binary-only modules, with no manually authored per-mod translation rules.
- For native plugins: automated, validated function/call-site matching; object/member/vtable/RTTI mapping; allocation and lifetime behavior; emitted-code and instruction-patch interpretation; ABI, exception/TLS, threading and graphics/input requirements. Improved Camera's documented hooks offer concrete acceptance tests.
- For assets: exact serializer/custom-version, compression, encryption/access, references, shader/material and platform payload knowledge; evidence the required source information exists or can be reconstructed; correctly accepted output in the target engine.
- For scripts and extension frameworks: the required VM semantics, registration/events/object bindings, timing, extension APIs and all transitive dependencies actually running in the target build.
- End-to-end tests showing the intended mod effect in native console gameplay, including reloads, saves, input, camera/animation state changes, conflicting mods and performance. Loading a package or DLL is insufficient evidence of equivalent behavior.
- A declared mod/runtime coverage universe and regression corpus spanning unrelated games, engine families and every supported mod category. Stellar Blade alone can validate a first backend; it cannot validate the universal claim. A finite test corpus supports measured coverage, not every future unknown package.

The user's all-runtime/all-mod objective should remain explicit. If a missing prerequisite prevents a specific package from translating, the system must identify the unresolved requirement honestly while continuing to expand shared backends. Describing a selective installer as universal translation would not meet that objective.
