# UE4SS dependency and source-access audit

Research date: 2026-09-29. Internal research only; no implementation, toolchain installation, compilation, account access, proprietary source download, external contact, or device test. This supplements `work/ue4ss-research.md`. The product objective remains automatic translation across Nexus mod types. The ordering below concerns prerequisites for an Unreal translation backend, not a proposal to replace that objective with a curated installer.

Latest user steering: Stellar Blade is the first validation title; the exact console title/update identifier is not supplied in this audit. The requested product remains universal and optimized, without individual-mod hardcoding. This dependency note therefore concerns reusable engine/runtime/format prerequisites. Title-specific configuration remains a possible compatibility exception, not the product definition.

Sources were public upstream documentation and source pages, mostly the moving `main` branch. A live root commit SHA could not be retrieved in this environment; the dependency pins below are the values visible in the reviewed manifest, not a reproducible whole-repository snapshot. Some less prominent wrapper files were unavailable through the browsing tool, so their build settings were not guessed.

## New findings that affect the dependency decision

### Source access has separate gates

1. **Public UE4SS is not its entire recursive source tree.** [`.gitmodules`](https://github.com/UE4SS-RE/RE-UE4SS/blob/main/.gitmodules) maps `deps/first/Unreal` to `git@github.com:Re-UE4SS/UEPseudo.git`, and maps `deps/first/patternsleuth` to the public `trumank/patternsleuth` repository. The [build instructions](https://github.com/UE4SS-RE/RE-UE4SS/blob/main/README.md#build-instructions) explicitly require linked GitHub/Epic accounts to pull the Unreal pseudo-code submodule. A public ZIP of the parent tree does not contain the submodule's source. This audit did not request or inspect UEPseudo; its internal platform support, exact license, dependencies, and suitability for a console ABI remain unverified.
2. **Epic/GitHub linkage is the engine-source access process.** Epic's [source-access instructions](https://www.unrealengine.com/en-US/ue-on-github) require an Epic account, agreement acceptance, GitHub OAuth linkage, and acceptance of the EpicGames organization invitation. This is a source-access prerequisite reported by Epic and UE4SS, not a request that the user perform it now.
3. **Console engine extensions are a further permission boundary.** Epic's [console-development guide](https://dev.epicgames.com/community/learning/knowledge-base/B9xk/getting-started-with-console-development-for-unreal-engine-and-epic-online-services) says console platform extensions are not included by default, need approved console-developer confirmation and approval, and are delivered through Epic Developer Portal rather than GitHub. The [PS5 documentation page](https://dev.epicgames.com/documentation/unreal-engine/development-for-playstation-5-in-unreal-engine) separately requires console permissions/NDA conditions. Sony describes development-tool access after partner-registration approval and the GDPA in [its partner guide](https://sonyinteractive.com/en/news/blog/showing-your-game-to-playstation/).

Inference: a linked Epic/GitHub account alone does not establish access to PS5 platform code, SDK headers, runtime libraries, or documentation. Conversely, these official engine-building prerequisites do not prove that every possible independent runtime bridge must use the official engine or SDK. An alternative bridge would still need an evidenced target toolchain, runtime interface, and ABI; this audit did not establish those.

### Host compiler support is not a console target

The earlier note's Windows-host wording needs qualification. The current [README](https://github.com/UE4SS-RE/RE-UE4SS/blob/main/README.md#cross-compiling-windows-binaries-on-linux) documents Linux-host Windows cross-compilation with xwin or msvc-wine. It uses `Game__...__Win64` and Rust `x86_64-pc-windows-msvc`. The [xwin toolchain](https://github.com/UE4SS-RE/RE-UE4SS/blob/main/cmake/toolchains/xwin-clang-cl-toolchain.cmake) explicitly sets `CMAKE_SYSTEM_NAME Windows`, x86_64, the Windows MSVC compiler target, and Microsoft's dynamic CRT. xwin packages Microsoft CRT and Windows SDK headers/libraries; it is not a source of console equivalents.

[Root CMake](https://github.com/UE4SS-RE/RE-UE4SS/blob/main/CMakeLists.txt) requires CMake 3.22, C++23, and enables `ASM_MASM`. [VersionChecks.cmake](https://github.com/UE4SS-RE/RE-UE4SS/blob/main/cmake/modules/VersionChecks.cmake) sets MSVC minimum 19.43/toolset 14.43 and Rust minimum 1.73; it skips the MSVC-version check for clang-cl. [ProjectConfig.cmake](https://github.com/UE4SS-RE/RE-UE4SS/blob/main/cmake/modules/ProjectConfig.cmake) still lists only Win64. [UE4SS/CMakeLists.txt](https://github.com/UE4SS-RE/RE-UE4SS/blob/main/UE4SS/CMakeLists.txt) selects `/MD` or `/MDd` dynamic CRT and links Windows system libraries.

Inference: a console backend needs a different target configuration and target C/C++ runtime choices, including availability of the used C++23 library facilities, exception/unwind behavior, symbol visibility, assembly support, and ownership rules across native-mod boundaries. Changing the host OS or bypassing a version check supplies none of these. No target compiler/CRT combination was compiled or validated.

## What an automatic translator cannot obtain from an archive alone

The actual [UObject binding implementation](https://github.com/UE4SS-RE/RE-UE4SS/blob/main/UE4SS/src/LuaType/LuaUObject.cpp) depends on `Unreal/*` headers, iterates reflected properties, uses parameter offsets, handles Unreal-owned container values, and invokes `ProcessEvent`. An archive containing Lua source may expose script logic, API calls, hardcoded paths and declared module names. It does not inherently contain the console game's engine fork, layouts, function addresses, allocator ABI or missing native bindings.

A Windows DLL archive also does not inherently contain its original C++ source, all transitive dependencies, build settings or a matching console engine profile. Source-based recompilation can only be evaluated when that source and its dependencies are actually supplied or accessible with appropriate permissions. Binary translation would require its own evidenced Windows API/loader/runtime and game-ABI bridge; finding portable decoder/JIT libraries does not supply that bridge automatically. Archive dependency inventory can be automated; missing source or runtime information cannot be manufactured by an inventory operation.

Likewise, this UE4SS dependency audit provides no Skyrim runtime adapter and does not establish whether a PC `.pak` can be used unchanged. Those require their own target-specific evidence. Keep them within the universal-translation objective, with explicit distinct backend/dependency requirements, rather than treating UE4SS as the common dependency for all Nexus games.

## Focused dependency order — research recommendation, not implementation plan

1. Establish the exact Stellar Blade console title/update and available execution environment before selecting a console compiler or claiming native runtime access. Record module format, available runtime interfaces and target ABI evidence. This resolves which dependency builds would even be meaningful.
2. Resolve source-access scope for the Unreal bridge separately from console-extension/toolchain permissions. If UEPseudo cannot be audited, retain that as an unresolved dependency; do not infer its console portability from public headers that consume it.
3. Evaluate the smallest independently testable language/decoder pieces first: bundled Lua, fmt/helper/string requirements, and Zydis. Preserve exact versions and avoid building the whole monorepo just to test these.
4. Review process-image discovery/scanning and hook OS backends against the chosen runtime. Separate offline PE/ELF parsing, instruction emission and executable-memory services. Only then assess the Unreal ABI/reflection bridge and Lua object bindings.
5. For automatic native-mod translation, inventory source availability and transitive native dependencies, then validate the relevant ABI boundary. For script translation, inventory API/native-module dependencies and target-game object identities. These are inputs for reusable backends and automated analysis, not a recommendation for individual-mod hardcoding. Universal translation research must account for missing source/profile information rather than hiding it as an installer concern.

Still unknown without introspection of the selected Stellar Blade console build and its execution environment: engine fork/version and configuration, object/property/vtable layout, symbols/resolvers, accepted executable module format and lifecycle, libc/C++ runtime/toolchain, allocator ownership, dynamic-module support, executable-memory capabilities, and mod source/dependency availability. No source finding here closes those unknowns.
