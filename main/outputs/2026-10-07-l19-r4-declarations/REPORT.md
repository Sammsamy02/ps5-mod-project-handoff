# R4 local profile-derived declarations

This isolated slice generates declarations from the frozen R3 authenticated profile. All game offsets, sizes, virtual slots, identity, version, and independently resolved runtime axes come from profile data. Neither the generator nor binder supplies guessed target values. No R3 source/profile/artifact/checkpoint, original mod, saved staged pair, console setting, or remote system was changed.

`generated/stageable-known-subset/` contains 60 member facts and the same five slots. It omits all seven known member fields belonging to the two classes without proved totals. This subset stages through the actual binder without publishing maps, but the actual required-profile checks still refuse the four unknown facts and the omitted required fields. This subset is a local verification draft, not a complete configuration or a deployment candidate. Strict completeness mode refuses without creating output; the generator also refuses existing output directories.

## Generator and evidence validation

`generate_declarations.py` takes the profile, source-selection, focused final receipt, exact selected schema, actual selected-target width census, repository root, and isolated output path. It checks the frozen profile/source-selection linkage, every selected source and external evidence hash, the census receipt pin, its genuine source hashes, and the target object hash before rendering. It does not repeat the prior native investigation or imply fresh console/image authentication. Its explicit trust input is the frozen R3 authenticated profile receipt.

The canonical selected schema is parsed directly for supported members/aliases and virtual classes. Duplicate canonical member aliases, unsupported names, unresolved facts claiming provenance, invalid numeric/source types, missing or narrower compiled widths, unsupported identity, unsafe metadata tokens, and non-aligned virtual offsets refuse. Each class with a proved total is checked using its actual compiled accessor footprint, and native measured width minima remain separate. FField.Owner native physical storage remains eight bytes; its selected public wrapper footprint is 16 bytes. The unknown exact FField total remains unknown.

NonShipping and Stats are independently serialized from the two independently resolved profile axes. Tests cover Shipping with Stats on and Development with Stats off; neither axis is inferred from the other.

## Current startup integration

The actual selected R3 launcher selects `outputs/2026-10-04-zcode-team/worker-pad-defer/staging/program-wpd1/UE4SSProgram.cpp`. Its lines 968-980 read activation-owned `ue4ss/MemberVariableLayout.ini` and `ue4ss/VTableLayout.ini`, or the corresponding filesystem pair, and call StageNativeLayoutTexts/Files. The compiled RuntimeBuildProfile supplies expected facts for preflight; it does not currently populate the staged declarations. The saved 17/1 pair is therefore still insufficient even after compiling the richer profile.

With the current loader, using complete declarations requires supplying a new layout pair in the activation-owned configuration or filesystem inputs. This slice only writes isolated drafts. A PRX-only alternative is feasible as a later source change: generate typed/serialized declaration data from the same profile and have a generic native startup loader select and stage that one profile-backed bundle. It must avoid reading/staging the older bundle first. Such a loader does not exist in R3, has not been implemented here, and would need actual initializer/authentication/order tests and a new source freeze/build. It can preserve original PC mod and existing external asset bytes by selecting the compiled declarations without merging them.

Old custom engine maps conflict even when values happen to agree: CheckEmpty refuses replacement of any existing/cached member or virtual map. A second staged bundle also refuses for that loaded lifetime. The actual tests prove these rules. The generator never merges old custom offsets or treats old staged declarations as proof.
