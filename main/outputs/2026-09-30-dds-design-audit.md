# DDS/BC design audit — 2026-09-30

## Decision

A small read-only DDS header and layout reader fits the current analyzer, but the present API must not claim complete inspection from its capped byte span. Separate format recognition, header parsing, layout calculation, payload availability, and normal-form eligibility. A well-formed header with an unsupported or unknown pixel format is not automatically a malformed DDS; it is a recognized container whose payload meaning/layout is unresolved. Similarly, bytes after an exactly calculated BC payload are an opaque trailer, not evidence that the last mip contains padding.

This audit relies on Microsoft's DDS documentation and Microsoft DirectXTex's `DirectXTexDDS.cpp` loader source. DirectXTex is useful compatibility evidence, not a normative definition of every real-world writer.

## Verified facts and corrections

- The basic file is 4-byte `DDS ` magic + 124-byte `DDS_HEADER` (128 bytes total). A pixel-format `DX10` marker adds a 20-byte extension (148 bytes total). Microsoft's guide gives these minimal file/header-size checks, and states writers vary in other header details. The existing research's “header flags are not reliably populated” is reasonable as compatibility guidance, but the strict subset should distinguish required structural sizes/signature from optional/loosely populated flags rather than require every conventional flag. [DDS programming guide](https://learn.microsoft.com/en-us/windows/win32/direct3ddds/dx-graphics-dds-pguide), [DDS_HEADER](https://learn.microsoft.com/en-us/windows/win32/direct3ddds/dds-header), [DDS_HEADER_DXT10](https://learn.microsoft.com/en-us/windows/win32/direct3ddds/dds-header-dxt10)
- DirectXTex maps `mipMapCount == 0` to one level before loading, with no special requirement that a mip-count flag be set for that one level. This means the proposed row “Treat count as one level when no mip chain declared” should say more precisely: effective mip count is one, record the raw count and flags, and do not infer that an omitted/zero count declares a full chain. DirectXTex's `DDS_FLAGS_PERMISSIVE` additionally clamps overlong legacy mip counts to computed maximums; default mode does not promise that compatibility behavior. [DirectXTex DDS loader](https://github.com/microsoft/DirectXTex/blob/main/DirectXTex/DirectXTexDDS.cpp)
- The typed DXGI BC family distinctions and block sizes in the research are correct: BC1/BC4 are 8 bytes per 4×4 block; BC2/3/5/6H/7 are 16. Preserve the exact DXGI enum, since typeless, UNORM/SNORM, sRGB, and BC6H signed/unsigned are distinct. For color metadata, replace `linear_or_unspecified` with a value such as `no_explicit_srgb_tag` (or `unknown` where format identity is unknown). A non-sRGB/typeless enum does not prove a linear transfer function or primaries; a typeless enum specifically leaves view interpretation to later use. [BC formats](https://learn.microsoft.com/en-us/windows/win32/direct3d11/texture-block-compression-in-direct3d-11), [DXGI_FORMAT](https://learn.microsoft.com/en-us/windows/win32/api/dxgiformat/ne-dxgiformat-dxgi_format)
- **1D:** DirectXTex parses DX10 1D dimension metadata and requires height 1 when the header height flag is present. But Direct3D format support tables mark BC formats unavailable for Texture1D. Thus a DX10 BC/1D combination may be parseable as header facts, but it is outside the BC normalizer and must not be reported as an accepted/usable BC resource. Record it as `unsupported_topology` (or structurally contradictory if a stricter selected profile decides BC-on-1D is invalid); do not silently turn it into a 2D texture. A non-BC 1D resource is still outside the BC-only normal form. [DirectXTex loader](https://github.com/microsoft/DirectXTex/blob/main/DirectXTex/DirectXTexDDS.cpp), [DXGI format support table](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/hardware-support-for-direct3d-12-0-formats)
- **3D:** BC6H and BC7 documentation explicitly supports Texture3D (and cube/arrays); the DXGI support tables likewise expose 3D support for BC formats. The prior research's BC6H/BC7 3D claim is sound. DirectXTex decodes DX10 3D metadata only if the legacy header volume/depth flag is present and rejects arraySize > 1. A 3D DDS layout is mip-major: each mip contains all its depth slices, with depth halving to a minimum of one. Do not represent depth slices as unrelated array items. [BC6H](https://learn.microsoft.com/en-us/windows/win32/direct3d11/bc6h-format), [BC7](https://learn.microsoft.com/en-us/windows/uwp/graphics-concepts/bc7-format), [DDS volume layout](https://learn.microsoft.com/en-us/windows/win32/direct3ddds/dds-file-layout-for-volume-textures), [DirectXTex loader](https://github.com/microsoft/DirectXTex/blob/main/DirectXTex/DirectXTexDDS.cpp)
- **DX10 arrays and cubes:** `arraySize` in the extension is a count of array elements/cubes, not cube faces. A DX10 cube flag is valid only on a 2D resource; DirectXTex multiplies the count by six for subresource handling. File data order is array item (cube face as a 2D item), then mip; a 3D item is one volume whose mip holds its depth slices. Preserve the original cube flag, array count, and face ordering. Legacy cube face flags identify faces; DirectXTex's regular load path requires all six and returns unsupported for a partial cube, while Microsoft's D3D11 overview says D3D11 does not support partial cubemaps. A partial legacy cube is therefore a recognizable legacy declaration that is unsupported for this normalizer, not a reason to invent absent faces. [DDS cube layout](https://learn.microsoft.com/en-us/windows/win32/direct3ddds/dds-file-layout-for-cubic-environment-maps), [DX10 header](https://learn.microsoft.com/en-us/windows/win32/direct3ddds/dds-header-dxt10), [DirectXTex loader](https://github.com/microsoft/DirectXTex/blob/main/DirectXTex/DirectXTexDDS.cpp)
- **Legacy BC identifiers:** DXT1/2/3/4/5 and ATI1/ATI2 map as researched. DirectXTex also recognizes BC4U/BC4S/BC5U/BC5S and a set of historical DXT5 channel-swizzle aliases (`A2D5`, `xGBR`, `RxBG`, and others) as BC3 payloads. Do not imply the proposed alias list is exhaustive across DirectXTex. For v1, either explicitly support a short enumerated alias subset and keep all raw FourCC bytes, or classify additional known aliases as recognizable-but-unsupported until their channel semantics are represented. DXT2/DXT4 do imply premultiplied alpha; DXT1's alpha behavior depends on block data and should remain unknown at the container level. The nonstandard numeric FourCC is explicitly ambiguous between D3DFORMAT and DXGI_FORMAT in Microsoft's docs; don't map it based on an assumed namespace. [DirectXTex legacy map](https://github.com/microsoft/DirectXTex/blob/main/DirectXTex/DirectXTexDDS.cpp), [DDS programming guide](https://learn.microsoft.com/en-us/windows/win32/direct3ddds/dx-graphics-dds-pguide)
- **Compatibility variants:** DirectXTex has explicit opt-in `DDS_FLAGS_PERMISSIVE`. It tolerates legacy header sizes 24/0, pixel-format sizes 24/0, mostly-zero pixel format records with a recognized FourCC, DX10 dimension zero as assumed 2D, arraySize zero as one, and some overlarge legacy mip counts by clamping. The default path rejects several of those. Its public flags also document known bad DXTn mip tails (`DDS_FLAGS_BAD_DXTN_TAILS`) and `DDS_FLAGS_IGNORE_MIPS`. These are strong reasons to expose a strict canonical subset and a separate “known compatibility variant / ambiguous layout” result, rather than branding every noncanonical file invalid or enabling undocumented repairs. [DirectXTex flags](https://github.com/microsoft/DirectXTex/blob/main/DirectXTex/DirectXTex.h), [DirectXTex DDS loader](https://github.com/microsoft/DirectXTex/blob/main/DirectXTex/DirectXTexDDS.cpp)
- **Padding and trailers:** Microsoft recommends calculating BC pitch as `max(1, ceil(width/4)) * blockBytes`, and notes runtime pitch may differ (some other formats can be DWORD- or byte-aligned). For a BC-only neutral reader, each row is a tight sequence of blocks, and each mip/array element is contiguous; do not apply uncompressed row-pitch guesses. Current Microsoft DDS docs do not define arbitrary trailing bytes as part of the last subresource. Therefore classify bytes beyond computed BC payload as `trailing_opaque` with exact range/hash, preserve them only if a later explicit lossless container requires it, and do not call them legal padding. A short body is truncated/incomplete. The DirectXTex load APIs take a total memory size, but their metadata decoder alone only establishes metadata; passing a prefix to either is not evidence that a payload load was complete. [DDS pitch guidance](https://learn.microsoft.com/en-us/windows/win32/direct3ddds/dx-graphics-dds-pguide), [DirectXTex DDS loader](https://github.com/microsoft/DirectXTex/blob/main/DirectXTex/DirectXTexDDS.cpp)

## Recommended supported subset

The first normalizer should accept only canonical-size legacy/DX10 headers with known BC encoding, nonzero dimensions, consistent dimension/cube/depth declarations, a valid effective mip count, a fully calculable BC layout, and all declared payload bytes available. Supported topology: 2D (single, array, full cube, cube array) and 3D single-volume; 1D is header-inspectable but not normalizable with BC. Accept BC1–BC7 only where that encoding is explicitly enumerated; retain typed/typeless identity. Legacy DXT1–5, ATI1/ATI2 plus BC4S/BC5S are straightforward aliases; retain the source FourCC and alpha conventions. Avoid image decode, alpha inference from blocks, channel semantic inference, console tiling, and encoder claims.

These are analyzer operations only. A parser pass or byte-identical host round trip establishes neither target writer support nor game/build acceptance. Planner requirements must continue to gate those claims on validated, scoped capabilities.

## Invalid, incomplete, unsupported, and opaque outcomes

Use distinct outcomes (names can adapt to the repository vocabulary):

| Outcome | Examples | Meaning |
|---|---|---|
| `recognized_complete` | Valid supported header/layout; enough bytes for declared BC payload | Layout facts may be complete. Normal form only if no unsupported feature blocks it. |
| `recognized_header_payload_incomplete` | Header or extension truncated; computed BC payload extends beyond the true input length | Need more bytes or input is truncated; never normalize/hash absent bytes. |
| `recognized_opaque_or_unsupported` | Unknown FourCC/DXGI, known non-BC format, BC/1D, partial legacy cube, or compatibility-only header dialect | DDS/header facts may be recorded, but BC payload layout/normal form isn't asserted. `format`/topology requirement is unresolved or unsupported. |
| `recognized_with_trailer` | Complete computed BC layout plus trailing bytes | Subresources are bounded; trailer remains separately opaque. Do not silently drop or attach it to the last mip. |
| `invalid_structure` | Bad magic/header size in strict mode, impossible dimension, zero extent, contradictory required flags/topology, checked arithmetic overflow, impossible mip count, truncated header | Concrete structural contradiction or insufficient bytes; precise issue range/reason. |

Unknown format should not fall through the current generic parser exception path (`binary_structure_incomplete`). A valid DDS header whose format cannot be sized is still a useful recognized container fact; describe its payload as opaque/unknown-length and avoid claiming file-level structural completeness. A structurally sound but unsupported compatibility variant should likewise not be conflated with invalid bytes.

## Minimal integration interface

Current `inspect_binary(span, path)` cannot know whether the supplied bytes are the whole entry. `inventory.cpp::Inventory::add` does know the full expanded `size` and streamed SHA-256, but passes only `b` (up to `max_inspection_bytes`) into inspection and adds a generic `inspection_cap` afterward. `inspection.cpp` initializes `facts.inspection_complete=true`, then turns every thrown exception into `binary_structure_incomplete` and `inspection.complete`; the default generic branch creates `kind=data` plus `format.data_semantics`. Those defaults cannot safely stand in for DDS header/layout/payload completion.

Minimum interface change: add an optional context to inspection, e.g. `InspectionInput { span bytes; uint64_t total_size; string_view whole_sha256; bool prefix_only; }`, and route by `DDS ` magic before the extension fallback. Return `kind: dds_texture` with independent facts: `header_status`, `layout_status`, `input_total_size`, `payload_expected_end` if computable, `payload_bytes_available`, `payload_complete`, `subresources_hashed`, and `trailer_range` if established. Keep `inspection_complete` meaning all requested inspection work actually completed; it must be false for a prefix-only payload when requested subresource evidence is absent. Keep whole-entry SHA-256 from inventory separate from DDS subresource digests. Only create per-subresource hashes/neutral blocks when full spans are available (a later bounded streaming `read_at` visitor is preferable to raising the 8 MiB cap).

Prefer a typed local return from `inspect_dds` (`status`, facts, issues, requirements) serialized at the seam, or a JSON result that carries explicit state. Do not use exceptions for ordinary `unknown_format`, `unsupported_topology`, `trailing_bytes`, or `payload_truncated` cases. Reserve `issues` for concrete structural/range failures and identify their severity; add unresolved preparation requirements such as `format.dds.payload_layout` / `inspection.complete` for unknown format, cap, or missing parser capability. Since `Inventory::add` currently marks global `inventory_complete=false` whenever entry `inspection_complete` is false, that is conservative and acceptable; it does mean a known capped asset keeps package analysis incomplete. Do not call the entire inventory complete just because whole-file hashing succeeded.

A neutral block container should be a later explicit operation, not an automatic side effect of `inspect_binary`. It may store ordered opaque byte slices + metadata, with per-slice offsets/sizes/hash and no image semantics. For legacy-preserving output retain exact original header bytes and trailer; for normalized output define a versioned header and tight BC payload order. A `write_dds_lossless` claim is meaningful only if every header byte, payload byte, and trailer byte is retained and compared; it should not be implied by parsing alone.

## Tests worth carrying into the design

- 128/148-byte minimal headers; exact header and pixel-format sizes; truncated magic/header/DX10 extension.
- BC edge dimensions 1×1, 4×4, 5×7; `ceil(width/4) * ceil(height/4)` block rows and 8/16-byte sizes.
- Raw mip count 0, count 1 without mip flag, count > max, missing legacy flags, and DX10 extension with strict/permissive-only header variants. Record compatibility mode rather than silently clamping.
- DX10 1D BC header (metadata-only unsupported), 2D BC, BC6H/BC7 3D, 3D arraySize >1, arraySize zero, cube flag on non-2D, cube count N and N*6 face items.
- Legacy all-face cube versus partial mask; preserve exact face bits and never synthesize faces.
- DXT2/4 premultiplied evidence; DXT1 alpha left unresolved; explicit sRGB vs typeless vs UNORM/SNORM distinctions; unknown/reserved alpha mode bits preserved.
- Known non-BC DXGI and unknown DXGI/FourCC: recognized header with unsupported/opaque payload, not generic malformed DDS. Numeric FourCC stays ambiguous.
- Exact expected payload, one-byte truncation, incomplete capped prefix with full size/hash, exact payload plus trailer; ensure trailer hash/range is separate.
- Fuzz/arithmetic boundaries for dimensions, mips, arrays, cube multiplication and offsets. Assert no allocation before checked size/limit validation.
- Inventory integration: full file under cap, DDS over cap, same input with different prefix sizes, and no fabricated `subresources_complete`/normal-form result.

Hand-authored fixture byte layouts with independently computed offsets and hashes are sufficient for the first contract. Add DirectXTex-produced examples as compatibility evidence later, while keeping the parser dependency-free and not using DirectXTex as the target acceptance oracle.
