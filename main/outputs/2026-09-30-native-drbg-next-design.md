# Next native entropy/CTR-DRBG checkpoint — design proposal

Design only. The next checkpoint should retain the existing 32-byte raw API contract, then seed the pinned Mbed TLS CTR-DRBG and request 32 private output bytes once. With one explicitly registered source returning 32 bytes per successful poll, the pinned SHA-512 accumulator needs two polls for the default seed. Including the raw prerequisite, the expected total is three OS calls within one shared limit of four. Narrow native raw32 evidence arrived during this design and is summarized below; the proposed DRBG integration remains unbuilt and unexecuted. Implementing or executing this design is separate work; this document does not assert DRBG deployment/execution, secure entropy quality, HTTPS readiness, or completion of the private manager.

The separate raw checkpoint now provides a reviewed, matching native identity and its strict return/errno/length result. A desktop fixture or the existing 64-byte feasibility probe cannot replace that evidence. The new DRBG artifact still collects its own raw prerequisite and must establish a fresh native identity. A passing raw result establishes the observed API response shape under the owned profile, rather than measuring randomness or establishing every future syscall's duration. Any runtime failure remains non-installable and must leave ordinary report/shutdown available when startup returns.

The source and budget contract is:

1. Create one private budget before the raw phase, with limit four and used count zero. Check and reserve one slot before invoking the existing native one-call raw observer. Its call consumes that reservation; require its returned call count to match one. Every later callback checks and reserves from this same object immediately before its sole OS call. Never reset or reconstruct the budget between phases, and count errors/EINTR against it.
2. Run the raw observer with its private 32-byte buffer and full-capacity volatile cleanup. Retain the existing metadata. If its strict classifier does not pass, skip Mbed TLS seed/generation, report the dependency as unavailable with reason `raw_prerequisite_failed`, and keep the returned native host responsive. Reuse no raw bytes; the raw buffer has already been cleared.
3. The Mbed TLS source callback sets `*olen=0` before any possible failure. Its output, length pointer, source state and private storage are valid distinct owned objects. It accepts sufficient bounded callback capacity, including the library's expected 128-byte gather buffer, but always supplies only 32 bytes. Invalid arguments/capacity or exhausted budget return `MBEDTLS_ERR_ENTROPY_SOURCE_FAILED` before touching the OS.
4. Use a private 32-byte staging buffer for the single standard SDK call `sysctl({CTL_KERN,KERN_ARND},2,buffer,&length,NULL,0)`, initializing length to 32. Clear errno immediately before the API and retain return code, errno and resulting `size_t` length immediately after it. No retry, device-file source, clock/PID seed, `rand`, cached sample or remote fallback is permitted.
5. Apply the same strict precedence as the raw checkpoint: nonzero return, nonzero captured errno, zero count, short count, oversized count, otherwise exact 32. Every rejected result sets no successful output length and returns a source error immediately. Never trust an oversized count for copying, reading or wiping. A failure's captured in/out length does not attest bytes written.
6. Only an accepted result is copied from staging into the callback output; set `*olen=32`, wipe the entire staging capacity, and return zero. Clear the full staging capacity on every returned failure too. For valid callback storage, clear its bounded capacity on failure independently of the untrusted API length. Record only metadata in source state. The source's strong declaration is an integration assumption, not an entropy-quality test result.
7. Budget exhaustion is a distinct policy failure. Preserve the last actual API observation; do not fabricate an errno or return code for a denied call. Track callback entries separately from actual OS calls so a denied entry is not mislabeled as an executed syscall. Latch failure and never attempt a fallback or a second seed in the same startup checkpoint.

Strict errno-zero acceptance is a deliberately conservative checkpoint policy. A successful Unix API return does not generally make errno authoritative as an error indication. Thus `rc=0, errno!=0` means this strict policy rejected the result, not that the syscall returned failure. The proposed callback must explicitly test this case; the earlier feasibility callback does not. Any optional restoration of a caller's errno happens only after captured metadata is retained, and cannot change the policy decision.

The main thread then performs this fixed sequence after a passing raw prerequisite:

1. Initialize an entropy context and a CTR-DRBG context once. Track initialized contexts for cleanup; both initializers return void.
2. Check the return from one `mbedtls_entropy_add_source(..., threshold=32, MBEDTLS_ENTROPY_SOURCE_STRONG)` call.
3. Call `mbedtls_ctr_drbg_seed(..., mbedtls_entropy_func, ..., fixed_nonsecret_personalization, length)` exactly once. Use a short fixed application/checkpoint personalization string covered by source identity; it is not a secret, entropy fallback, or replacement for nonce material. Do not change the default entropy or nonce lengths.
4. Only after seed returns zero, call `mbedtls_ctr_drbg_random` once for exactly 32 bytes into private caller-owned output. Preserve its return code. Do not inspect, encode, hash, log, compare, persist or publish the generated content in production.
5. On every returned outcome, free initialized contexts, then explicitly clear the full caller-owned context storage, generated output, staging storage and callback/budget state before HTTP readiness. Use a reviewed non-elidable owned wipe for this post-free storage; an otherwise dead final ordinary `memset` is insufficient. Snapshot only needed counters/status into the metadata result before wiping source state. A failed seed must still be followed by `mbedtls_ctr_drbg_free`, as the pinned API requires.

The arithmetic follows pinned `entropy.c:302–322` and `ctr_drbg.c:466–520,555–584`: every extraction gathers first; thresholds and at least one full strong accumulator block must both be satisfied. The first 32-byte poll meets the threshold but provides only half the 64-byte strong block. A second successful poll completes it. Default seed entropy length 48 meets `32 * 3 / 2`, so default nonce length is zero and there is only one entropy extraction. Immediately after a successful seed, the reseed counter is zero; one 32-byte random request with prediction resistance off does not trigger another extraction. Thus the expected native successful path is raw one + seed two + generation zero = three OS calls. Do not add a standalone entropy extraction before seed: that would require two more polls and exceed the combined total-four budget.

The budget limits attempts and callback progression, not syscall wall time. With this fixed callback, every success supplies positive exact progress, and every invalid response or budget denial terminates the library gather instead of returning zero-length success. Mbed TLS's much larger internal gather-loop limit is therefore not the intended safety bound. Any single `sysctl` can still block. The existing host starts its listener/lifetime clock after startup observations; socket and lifetime deadlines do not interrupt a blocked raw/seed phase. Monotonic elapsed time records only returned operations, with null timing on invalid clock samples. Do not claim a hard syscall timeout, bounded startup availability, or responsive shutdown while the main thread is blocked. A missing report remains an undiagnosed readiness failure, including possible eager import or native execution faults. Do not relaunch another owned payload merely because readiness was not observed.

Cleanup evidence must be precise. The existing raw staging wipe uses volatile writes; preserve its optimized retained stores. For library-owned erasure, inspect the actual new artifact's `mbedtls_platform_zeroize` and its referenced primitive. In the earlier retained feasibility ELF, that function loads the volatile `memset_func` pointer and makes an indirect call; it does not import `explicit_bzero` or `memset_s`. This was a read-only disassembly observation of the old artifact, not proof about the new build. An owned `MBEDTLS_PLATFORM_ZEROIZE_ALT` implementation is a possible separately reviewed choice if the new primitive is unsuitable; such a choice must be applied consistently and added to provenance. It does not repair control-flow paths that bypass any zeroizer.

The pinned upstream temporary paths have these limits:

| Path inspected | Cleanup fact and limit |
| --- | --- |
| `entropy_update` | Its temporary digest buffer goes through cleanup on the inspected paths. |
| `entropy_gather_internal` | Callback errors go through the 128-byte buffer wipe. An `entropy_update`/digest error at `entropy.c:228–230` directly returns and bypasses that wipe. Caller context cleanup cannot erase this expired callee-local array. |
| `mbedtls_entropy_func` | Normal source/error exit paths clear its 64-byte intermediate; caller output is copied only after complete success. Disabled NV/thread paths are outside this selected operation. |
| CTR-DRBG reseed helper | It first zero-initializes the 384-byte seed. A first entropy callback error returns without the final wipe. With this selected `mbedtls_entropy_func`, failure copies no partial seed output, so that initialized seed remains zero on this path. A failing nonce call could bypass cleanup after prior seed material, but this design's nonce length is zero. Do not generalize to other callbacks/configurations. |
| CTR-DRBG derivation/update/generation | Inspected temporary-buffer cleanup labels clear their normal retained paths; generation can partially write caller output before a later error, so always clear the entire owned 32-byte destination. |
| Context freeing | AES and SHA-512 context frees use the library zeroizer. MD free invokes the relevant digest free and clears its owning context. Entropy free clears its source entries but does not erase application source state. CTR-DRBG free clears its context and then restores nonzero lifecycle defaults. Explicit caller erasure after free is therefore needed for a literally zeroed owned context. |

The defensible claim is that the application clears its specified owned buffers/state on every returned path, with library cleanup behavior and known bypasses separately documented. Do not claim comprehensive all-memory erasure, erased kernel buffers/registers/allocator remnants, or secure cleanup of every upstream fault path. A later source patch to route the upstream digest error through cleanup would be independent identified dependency work and review, not an undocumented part of this configuration-only proposal.

Alternatives have distinct costs. Reusing the NO_DEFAULT-only feasibility archive avoids a rebuild but leaves the upstream platform poll implementation present and carries the old 64-byte callback contract; it is unsuitable as the final identified checkpoint. A 64-byte native source would need another independently observed API-length gate. A SHA-256 accumulator changes seed/nonce/call accounting and security configuration without solving the single-syscall deadline. A helper thread or child/process watchdog could improve availability only after separate ownership, synchronization, worker TLS and termination proof; neither is assumed here. A direct fixed-source CTR-DRBG seed adapter would bypass the accumulator/add-source behavior this gate intends to verify. Keeping the proposed default SHA-512 path with fixed32 source polls provides the next narrow integration evidence at the cost of two seed-source calls and a separately configured archive.

Even a passing native checkpoint proves only this ephemeral owned entropy/DRBG path. Controlled trusted-chain success, hostname and untrusted-chain rejection, production CA provenance/update behavior, DNS/resolver/thread and HTTP bounds, long-lived RNG/reseed policy, and official Nexus account/download integration remain subsequent work. Game writers, installation and representative game validation remain outside this gate and unsupported until their own evidence exists. Finished-app operations still must run on the PS5; external clients here are development observation tools.
