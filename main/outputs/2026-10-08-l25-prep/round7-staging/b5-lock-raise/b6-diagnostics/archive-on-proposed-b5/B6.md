# B6 diagnostics build (staged on top of B5) -- 2026-10-12

Status: STAGED ONLY. Not applied to the candidate tree, not built, no console contact. Every claim below is
**Mac-only** unless it says otherwise; there is no console-proven claim in this document (no launch happened).
Nothing here edits a mod, a harvest tool, evidence, the candidate tree or the original tree.

## Plain summary (for the user)

- The Townfall minimap froze the pad/keybind thread because one lock was never given back. B5 fixes that. B6 does
  not fix anything. It adds **eyes**, so that if a lock is ever stuck again, or the game slows down, the very next
  log tells us who, where, and for how long, instead of us guessing from a silent log.
- What the new log lines say, in plain words:
  - `[LOCKLEAK]` "a mod function ended (or failed) while still holding the lock". Names the mod and the function.
    Once per mod, then at most every 30 seconds.
  - `[LOCKWAIT]` "something waited more than a quarter second for the lock", and, from the game thread, "this wait
    has not ended yet", with the line number of who has been holding it and for how long.
  - `[PERF]` once a second: how many milliseconds each mod's Lua spent on the game thread, how many
    `FindFirstOf`/`FindAllOf` calls and how long they took, widgets built, how many jobs are waiting, lock waits.
  - `[MEM]` is now also printed once a second from the same place, so it cannot go silent when a lock is stuck.
  - The per-widget "widget constructed" line is limited to 5 per second, plus one summary line.
  - The file-write helper now says WHY a write failed (the error number and its text) once per mod, and the
    "write-area dir ... usable=" line now says why it is or is not usable.
- It is built to change nothing the game or the mods can see. It only counts and prints. I checked that mechanically
  (see "Why it should not change behaviour").
- Honest size note: this is not tiny (about 900 added lines, mostly one self-contained block that is tested on its own).
  If you want a smaller B6, the optional parts that can be dropped without touching the rest are listed in "Open
  risks / choices".
- Tests that ran on the Mac with the real Lua code: 157 + 23 checks in the main and pump tests (passed on the
  run before the Mac ran short of memory; see "Test results" for the exact state), 11 of 11 deliberately-broken
  versions caught, 12 of 12 gate self-tests. Real contention, real Lua errors that skip destructors, and a held lock
  while the pump runs are all in there.
- Next step for you / the reviewer: decide whether to build B6 straight after B5 or only after the two clean Townfall
  launches. Nothing needs the console until then.

## What B6 changes (4 files, no new #include, no new file)

1. **`b6diag::ActionsLock`** (LuaMod.cpp:480, inside the CORE block 184-678) replaces `std::lock_guard<std::recursive_mutex>`
   / `std::unique_lock` on `LuaMod::m_thread_actions_mutex` at **all 46 sites** (45 guards + the dispatch scope member,
   list in `SITES.txt`). It locks exactly like before (`try_lock`, and if that fails the normal blocking `lock`), plus
   - a **per-thread depth counter** (`LuaMadeSimple::diag_scope_enter/exit`), the leak detector's input;
   - a **wait record** (only on the slow path, so an uncontended lock reads no clock): who is waiting, since when;
   - a **holder record** (outermost scope of a thread only): the site line, game or other thread, since when.
2. **[LOCKLEAK]** (LuaMadeSimple.cpp:92-183 + LuaMod.cpp `on_leak`). Lua is C here, so a Lua error is a longjmp
   that skips the guard's destructor; the depth stays too high for good. The library compares the depth with the
   depth at the entry of the innermost registered function / `call_function` at four places:
   - just before a Lua error is raised (`throw_error_impl`, LuaMadeSimple.cpp:1697) -> `kind=raise` (names the function through `lua_getinfo`);
   - when a registered function returns (`process_lua_function`, :1828-1837) -> `kind=return`;
   - when a pcall in `call_function` comes back with an error (:1516) -> `kind=pcall`;
   - when the game-thread pump sees the **same** depth above zero in two consecutive pumps and no dispatch is running
     (LuaMod.cpp pump block) -> `kind=pump`. This is exactly the signature of the B4 failure.
   The report goes to the host through `DiagHooks`; it never throws. Mod name = the mod's main Lua state, registered in
   the `LuaMod` constructor (LuaMod.cpp:1679).
3. **[LOCKWAIT]**: the slow path logs when an acquisition waited more than 250 ms (`steady_clock`, at most 5 lines per
   10 s plus a summary). The pump also scans the wait records every second, so a lock that **never** comes back is
   still reported while it is stuck, with the holder's site line and how long it has held (this is what the old
   code could not do, because it only logged after the wait ended).
4. **[PERF] + pump-side [MEM]** from the existing 1 Hz game-thread pump (`r3_marshal_pumped` block, LuaMod.cpp:6111) and,
   with its own 1 Hz gate, from `VmtEngineTickDrain` (LuaMod.cpp:6198). Both calls sit **before** the dispatch lock, make
   **no Lua call**, take **no tracked lock** (queue sizes are read under a plain `try_lock`; a busy lock prints `q=busy`).
   Per-mod game-thread Lua time comes from timing the outermost `call_function` on the game thread
   (LuaMadeSimple.cpp `DiagCallFrame`); `FindFirstOf`/`FindAllOf` have a small RAII timer (LuaMod.cpp:2423, 2475).
   The old [MEM] path (in `ExecuteInGameThread`) stays; it skips printing in a second where the pump already printed.
5. **Widget log** (LuaMod.cpp:3181): at most 5 verbatim lines per second; the rest are counted and one
   `[l22] widget/object construct summary: N constructed ..., M log lines suppressed` line follows (also flushed by the pump).
6. **Shim** (LuaPathShim.cpp): `try_original` records errno and message of the backend failure (io.open returns
   `nil, message, errno`); `io_open_wrapper` logs `[SHIM] write-fail mod=.. path=.. errno=.. strerror=.. backend=.. dir=.. retry_errno=.. -> spill`
   once per mod when the sandbox write falls back to the in-memory spill; the `[SHIM] write-area dir` line gets `why=`
   (OS error text and code, `created`, or `already existed`).

## Open risks / choices (please read)

1. **Not compiled on the console toolchain.** The CORE, glue, pump and shim slices are compiled on the Mac and run. The rest
   (the 46 one-line swaps, the registration call, the two pump call sites, the `FindFirstOf` timers, the widget gate) is only
   checked by text and the gates. A type error would show at the first real compile. One class I already hit and fixed:
   `int64_t` is `long` on the console and `long long` here, so every shared counter in the glue uses the file's own
   `b6diag::i64`.
2. **Only lock scopes that use `ActionsLock` are counted.** A different lock leaking is invisible to `[LOCKLEAK]`.
   `[LOCKWAIT]` is the backstop for those only when the wait goes through `ActionsLock`.
3. **Function name is best-effort.** It comes from `lua_getinfo(..., "n")`. After a longjmp the "innermost registered function"
   base can be stale until the next function entry; a stale base can only hide a leak, never invent one (reasoning in
   `LuaMadeSimple.cpp:92-183` comments and the host test cases (d)(e)(g)). `fn=?` is normal for `kind=pcall` and `kind=pump`.
4. **`[LOCKLEAK] kind=pump` needs two pumps with the same depth.** A legitimate hold longer than 1 s on the game thread outside a
   dispatch would also print it once per 30 s. I did not find one in the code, but it is a heuristic; the other three kinds are exact.
5. **Queue depths** are read with a plain `try_lock` on the game thread. If the game thread itself leaked the mutex (the B4 case),
   `try_lock` succeeds (recursive) and the depths print; if another thread holds it, `q=busy`.
6. **`strerror`** is new in the shim unit. The port's patched `lauxlib.c` already calls it, so it should not be a new PRX import,
   but check the import contract; if it shows as new, delete the `strerror=` field (the `backend=` field has the same text).
7. **The engine-tick pump (`engine_tick_hook`) is not instrumented**, only the marshal and the VMT pumps (the two that run on the console).
8. **Marker collision** with the lock-fix design's `[LOCKLEAK] repaired ...` / `[LOCK] ...` lines: see `MARKERS.md`.
9. **Size.** About 895 added lines in 4 files. If a smaller build is wanted, these can be cut independently:
   the shim part (LuaPathShim.cpp, ~64 lines), the widget rate limit (~20), the `FindFirstOf/FindAllOf` timers (~10 plus the 5 counters),
   the per-mod Lua time (the `call_begin/call_end` hooks and `DiagCallFrame` timing, ~30). The lock tracker, `[LOCKLEAK]`,
   `[LOCKWAIT]` and the pump line are the core and share the same block.
10. **Cost on the console (estimates, not measured).** Per lock: two thread-local operations; per outermost lock: one clock read
    and one game-thread-identity call; per registered Lua function call: two thread-local reads; per game-thread top-level callback:
    two clock reads; per `FindFirstOf/FindAllOf`: two clock reads. Measure with the first `[PERF]` rows.

## What to look for after a B6 launch (for the report)

- `[LOCKLEAK]`: expect none after B5. Any line names the mod, the function and the kind.
- `[LOCKWAIT]`: expect none or a few. A `still waiting` line with `holder_line=` -> look the number up in `SITES.txt`.
- `[PERF]` every second: `lua_ms` per mod (watch the minimap), `q=busy`, `find_*` ms, `widgets=`, `leaks=`, `pump_depth=` (must stay 0).
- `[MEM] ... src=pump`: present every second even if the lock is stuck.
- `[SHIM] write-fail`: one per mod, with the errno.
- Console-proven labels apply only to lines from that launch's decoded log.
