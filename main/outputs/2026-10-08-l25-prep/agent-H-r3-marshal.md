## 1. What the R3 marshal is, what it hooks instead of EngineTick, which thread runs it

**What was compiled out.** `UE4SS_R3_MARSHAL_MODE` defaults to 1 in-file (`outputs/2026-10-08-l22-runtime/profile/units/UnrealInitializer.cpp:196-199`; same in `typescan-r3/candidate/src/UnrealInitializer.cpp:197-199`). Under it, the initializer refuses its two `RegisterEngineTickPreCallback` registrations (`HookedEngineTick` "GameThreadInitializer" + `QueryHarnessEngineTickDispatch`) and the FName-ctor verification detour, and instead sets the cross-TU flag `R3MarshalGate::pump_pending=true` (`UnrealInitializer.cpp:2204-2219`; refuse log at :2216-2217, "deferring game-thread pump to R3 marshal" at :2218 in the typescan copy :2227-2230). These are exactly the two crash-session log lines.

**What replaces the EngineTick detour.** Not a vtable patch, not ProcessEvent, not a patched tick — a **UFunction::Func pointer swap on a "carrier" UFunction** (post-hook thunk):
- Arming: `arm_funcptr_marshal_drain` (`LuaMod.cpp:4970-4996`) calls `carrier->RegisterPostHook(&funcptr_marshal_hook, nullptr)` (:4991 arm at :4994 "[R3] FuncPtr-marshal armed on carrier ...").
- Registration core: `ThunkDetail::Register` (`outputs/2026-10-08-r5-source-integration/source/ScriptHookThunks.cpp:124-159`) saves the current `UFunction::Func` as `original` (:142) and publishes a thunk via `function->SetFuncPtr(thunks[index])` (:155) — one pointer store into already-RW heap memory, no detour/mprotect/syscall.
- Carriers: ranked natives "Actor:ReceiveTick", "AnimInstance:BlueprintUpdateAnimation" (`r3_marshal_calibration_consumer`, `LuaMod.cpp:5138-5177` — these are BlueprintImplementableEvents, so `r3_marshal_carrier_precheck` :4935-4958 refuses them by construction) plus the **Blueprint-override event carrier family** actually used: overrides of `/Script/Engine.Actor:ReceiveTick`, `/Script/Engine.AnimInstance:BlueprintUpdateAnimation`, `/Script/UMG.UserWidget:Tick` found by GUObjectArray scan (`r3_marshal_arm_event_carriers`, `LuaMod.cpp:5054-5127`, base list :5060-5064). The engine calls these per frame on the game thread via ProcessEvent → UFunction::Invoke → Func, so the thunk (Dispatch → original → FirePostCallbacks, `ScriptHookThunks.cpp:48-80, 77-79`) fires there.
- Arming call site: `r3_marshal_calibration_consumer()` is the first statement of `LuaMod::on_program_start()` (`LuaMod.cpp:7933`), which `UE4SSProgram::on_program_start()` calls before `start_lua_mods()` (`UE4SSProgram.cpp:1565-1567`), itself called at the top of the event-loop thread (`UE4SSProgram.cpp:1593`, thread spawned at :710).

**The pump body.** `funcptr_marshal_hook` (`LuaMod.cpp:4789-4867`): first invocation publishes the game-thread identity via the initializer bridge `R3MarshalPublishGameThreadIdentity` (`UnrealInitializer.cpp:2493-2534`; publication is mutex-arbitrated — the publishing thread BECOMES the game thread) and logs once "[R3] marshal is the game-thread pump ..." (:4817). Then every carrier invocation on the published game thread drains `process_simple_actions(m_game_thread_actions)` + `process_delayed_actions<kFuncPtrMarshalExecutor>` + pending NotifyOnNewObject callbacks (:4842-4845).

**Thread that executes the pump: the game thread**, by definition — but only when the engine itself invokes a carrier UFunction on it (ReceiveTick/BlueprintUpdateAnimation/UserWidget:Tick overrides). Arming/scanning runs on the UE4SS event-loop thread ("UE4SS-UpdateThread", `UE4SSProgram.cpp:710, 1586-1587`); `r3_marshal_lazy_arm` rescans at most once per second (`LuaMod.cpp:5180-5201`).

Note: `R3MarshalQueryHarnessDispatch` (`UnrealInitializer.cpp:2536-2547`) is declared in `LuaMod.cpp:109` but **never called in this build** — the query-harness half of the old EngineTick pump is not routed onto the marshal; only identity publication + action drain are.

## 2. Does the pump run with HookLoadMap=false and HookInitGameState=false?

**Yes — those two settings do not gate the pump at all.** The pump_pending deferral block sits solely inside `if (UnrealConfig.bHookEngineTick)` (`UnrealInitializer.cpp:2118` block; refusal/pump_pending at :2215-2219). `bHookLoadMap` (:2109) only assigns `UEngine::LoadMapInternal`; `bHookInitGameState` (:2244) only assigns `AGameModeBase::InitGameStateInternal`. The marshal carrier arm + drain path (`StaticFindObject` + Func swap + `funcptr_marshal_hook`) never touches LoadMap/InitGameState. The only LoadMap coupling is the one-shot deferred LoadMap re-arm inside the first proven drain (`try_deferred_loadmap_arm`, `LuaMod.cpp:4733-4777`) — a delivery nicety for `RegisterLoadMapPreHook/PostHook` callbacks, not a pump dependency; if refused it fails loudly once (:4776) and the pump is unaffected.

Crash-session settings confirm all three were true (`harvest .../UE4SS-settings.ini:63-73`: HookLoadMap=true, HookInitGameState=true, HookEngineTick=true, HookUObjectProcessEvent=true) and the logs prove the LoadMap/Tick/InitGameState/ProcessEvent address walks all ran (`UE4SS.log:583-598`).

**Caution for the A/B: `HookEngineTick=false` is the one switch that would kill the pump** — the refusal block would never run, `pump_pending` stays false, `funcptr_marshal_usable()` returns false (`LuaMod.cpp:4247-4261`), nothing arms the marshal, and every `ExecuteInGameThread` closure strands (see Q3).

## 3. How PS5Pad L3+R3 reaches the Lua keybind dispatch; is the pump provably running in the crash session?

Chain (cited):
1. `PS5Pad.ini` maps `L3+R3 = F7` (`harvest .../PS5Pad.ini:36-43`, [Bindings] block; 3718 bytes), parsed by `ConfigureRetainedPS5PadInput` (`worker-pad-coexist/.../NativePadInput.cpp:18-55`) which deferred-attaches the source even when the open fails (:27-54, `pad_input_deferred` diag :37-38).
2. Polling: `PS5PadSource::poll` (`outputs/2026-10-08-l22-runtime/candidate/PS5PadSource.cpp:119-177`) runs from `Handler::process_event` (`input-handler-coexist/Handler.cpp:96-174`, source call :113) which runs in the UE4SS event loop (`UE4SSProgram.cpp:1739`), i.e. the **UE4SS-UpdateThread, not the game thread**. Rising-edge conjunction match at :154 (`(data.buttons & b.buttons) == b.buttons`), delivery only if `allow && subscribed[b.key]` (:164), emitting `pad_l3r3_edge*` (:157-163) and `pad_l3r3_f7_dispatched` (:169-170).
3. 4. **The callback body needs the game-thread pump.** `ExecuteInGameThread` (`outputs/2026-10-08-l22-runtime/diagnostics/src/LuaMod.cpp:5381-5557`) sees `funcptr_marshal_usable()` true (pump_pending) and tags the closure `kFuncPtrMarshalExecutor` (:5411-5414), queueing it into `m_game_thread_actions`/`m_pending_game_thread_actions` (:5541-5551). That queue is drained **only** by `funcptr_marshal_hook` on the published game thread (:4842) — the old EngineTick/ProcessEvent drains are unregistered in this world (`engine_tick_hook`/`process_event_hook` registrations are exactly what R3 refused/deferred). So: L3+R3 → F7 keydown fires on the update thread; **the menu opens only if the R3 marshal pump is armed and firing.**

## 4. Fallbacks if the pump never runs; per-cycle diagnostics

- **No timeout, no alternate thread.** If no carrier arms, closures queue indefinitely by design ("lazy semantics", `LuaMod.cpp:5497-5516`; `funcptr_marshal_usable` comment :4249-4254). The only re-arm path is the rate-limited lazy rescan `r3_marshal_lazy_arm` (:5180-5201, ≤1 GUObjectArray scan/s) triggered from `funcptr_marshal_usable()` calls on the ExecuteInGameThread/WithDelay enqueue paths (:5411, :5650, :5860, :6031, :6114, :6258).
- **Loud failure points are all at ARM time, not per cycle**: carrier precheck refusals (:4935-4958), RegisterPostHook failure (:4992), the once-per-process "[R3] marshal arm failed: ... closures will queue until a carrier arms" (:5177), the once "[R3] marshal is the game-thread pump ..." on first publication (:4817), and the one-shot deferred LoadMap arm outcome (:4758/:4776).
- **Per-cycle diagnostic event: NONE exists.** `funcptr_marshal_hook` emits nothing per fire; `m_funcptr_marshal_last_fire_ms` (:4827) is internal-only state for the staleness rescan. The only per-drain observable is per-closure: "[l22] ExecuteInGameThread queued method=..." (:5554-5557) and "[l22] ExecuteInGameThread drained state=... ref=... (callback entry) / callback returned" (:4299-4307) via `L22Diagnostics::observe` (`outputs/2026-10-08-l22-runtime/diagnostics/include/L22Diagnostics/Logging.hpp:10-15` — always-on, not gated). Supplier-diag sink mechanics: `diagnostic_event` (`outputs/2026-10-08-l24-package/lineage/diagnostic.c:145-154`) → harvested `supplier-diag.jsonl`.

## Quick answers

1. **Mechanism**: R3 marshal replaces the EngineTick detour with a UFunction Func-pointer-swap post-hook ("carrier": BP overrides of ReceiveTick / BlueprintUpdateAnimation / UserWidget:Tick). The engine's own game-thread invocation of the carrier runs `funcptr_marshal_hook`, which publishes the game-thread identity once and then drains the Lua game-thread action queues. Arming happens on the UE4SS-UpdateThread at `LuaMod::on_program_start`; draining happens on the game thread.
2. **HookLoadMap=false / HookInitGameState=false do NOT disable the pump** (only `HookEngineTick` gates `pump_pending`; keep it true). The crash sessions died before the arm point regardless of those settings.
3. **L3+R3 → F7 keydown fires on the UE4SS-UpdateThread via the Handler; the Lua callback wraps everything in `ExecuteInGameThread`, which only the game-thread marshal pump drains.** In the l22/l23 crash sessions the pump is provably NOT running (no arming/pump logs; teardown inside type-system init before `on_program_start`), and the pad never opened (pad_input_deferred 0x80920004; no `pad_first_state_read`/`pad_l3r3_edge`).
4. **No timeout/alternate-thread fallback exists**; closures queue forever. No per-cycle diagnostic is emitted today; the recommendation above adds one throttled `r3_marshal_pumped` supplier-diag event.
