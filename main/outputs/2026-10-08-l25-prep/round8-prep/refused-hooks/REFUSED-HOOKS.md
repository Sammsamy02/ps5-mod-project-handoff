# Refused hooks: the complete parity-gap list (round 8, refused-hooks track)

## Plain verdict

1. **The list is longer than "3 + 12".** The PS5 runtime has **20 Lua hook families that do not work like on PC**, not 15. They fall into two kinds:
   - **Loud refusals (the Lua call throws an error):** RegisterHook / UnregisterHook on a *Blueprint* function (the minimap's 3), and the frame-delay calls `ExecuteInGameThreadAfterFrames` / `LoopInGameThreadAfterFrames`.
   - **Silent refusals (the call says OK and the callback never fires):** LoadMap (2), InitGameState (2), BeginPlay (2), EndPlay (2), ProcessConsoleExec (2), CallFunctionByNameWithArguments (2), ULocalPlayerExec (2), the two console-command handlers, NotifyOnNewObject, RegisterCustomEvent. These are the "12" in the self-test, plus 6 more the self-test does not even look for.
2. **The self-test's GAPS counter cannot see them.** It only counts a registration as a gap if the call throws an error containing the word "refus". None of these calls throw. The earlier console run (comparison only) shows them all as `PASS registered` / `PASS ret=nil`. So the next run will print `GAPS 0`, which is wrong. Fix staged (below).
3. **Nothing in the logs says "refused" for the silent ones.** The B4 log has exactly one line for the whole family (`D:780`, a startup summary) and one for LoadMap (`D:922`). The minimap's 3 refusals leave no line at all. A uniform `[REFUSED]` log line is staged (not applied).
4. **Data-only routes: none is "ready". Two are good candidates, each with a precondition the first version of this report missed.**
   - (a) Blueprint-function RegisterHook by swapping the function's `Func` pointer (the mechanism that already runs the 66 pump carriers on the console). **Precondition: the function must first be found.** `RegisterHook` looks the function up by its path (`LuaMod.cpp:5992`) and no console line shows that a Blueprint path ever resolved. The carriers avoid path lookup and scan the object array. So this route needs a scan-based resolver plus the branch change (details in the R01 section). **We do not know which of the two throws (`:5994` not found, or `:6043` cannot hook) the minimap hit.** The staged `[REFUSED]` line tells them apart on the next launch.
   - (b) LoadMap through the private vtable copy. That copy is refused today (item 5). The slot (`0x4F8`) rests on **one** static inference, not two independent sources (item 7 below).
   - Partial or approximate: BeginPlay/EndPlay (via the Blueprint events), NotifyOnNewObject, custom events, InitGameState. **Detour-only (stays out until Phase B):** exact Pre-hooks of InitGameState/BeginPlay/EndPlay, and `CallFunctionByNameWithArguments`.
5. **Hypothesis for why the vtable pump is refused (Mac-only, not console-proven).** The copied-vtable pump is refused (`[EU-VMT] arming refused: non-text-ent`, `D:623`; the log gives no entry number). A static replay on the exact image (sha 3b6cfad4, matches the B4 log) suggests the cause: the 512-entry scan runs past the end of the GameEngine vtable into the next table. Real table ends at entry 178; the scan extent is 508 and sees 126 non-code words inside (`evidence/vtable_extent_check.out`). **This depends on how the runtime tells "code" from "not code"**: its classifier (`rc_seed::classify_seed_address`) is not in the tree, so I used the executable segment of the image (which starts at address 0) as a stand-in. With a stricter stand-in many entries inside the real table fail too (`evidence/vtable_extent_sensitivity.out`), so the extent rule alone might not be the whole story. The staged log line (entry number and value on refusal) is how the next launch confirms or kills this hypothesis.
   - **What it would unblock if true:** the Tick pump and the LoadMap Lua hooks (R05/R06).
6. **Frame delays (R21/R22) are NOT unblocked by the extent fix** (correction after review). Three more things must change in `LuaMod.cpp`: (1) the two throw gates (`:6782-6784`, `:7009-7011`) fire whenever the marshal world is on (`funcptr_marshal_usable()` is just `R3MarshalPumpPending()`, `:4669-4683`), and that flag stays true even after the vtable pump arms (`UnrealInitializer.cpp:2941`, comment `:2948-2951`); (2) the vtable drain (`VmtEngineTickDrain`, `:5542-5600`) only runs `process_delayed_actions<kFuncPtrMarshalExecutor>`, which skips frame-based actions (`:4891-4905`; frame counting is EngineTick-only, `:4915-4926`); (3) the frame-delay path must not call `ensure_engine_tick_hooked()`, a detour attempt. Console-comparison (earlier session, not a verdict): pass2 log lines 1279/1281 show the refusal text from this exact branch.
7. **Two-source rule for the LoadMap slot is NOT met yet.** Slot `0x4F8` comes from `ENGINE-SLOT-FACTS-v2.json`, which itself says `live_validation: false` and "Method identity is an inference from named native callers". The live line `D:616` (`GameEngine::LoadMap address 0x3c4d460`) is the runtime reading the same profile offset, so it proves the table content, not that the slot is LoadMap. My own replay reuses `0x4F8` too. A second, independent identification is still needed (see R05).

Labels used below: **console-proven** = cites a line of the B4 launch log (`D` = `evidence/launch-l26-B4-launch1-20261012/decoded/ue4ss.decoded.log`). **Mac-only** = code reading or static analysis. **comparison** = an earlier session, never used as a verdict. The ueselftest never ran in B4 (0/168), so nothing about the 168 checks is console-proven for this session.

## Why they are refused (the two root causes)

**Cause 1: no detours on game code (execute-only text).** Every hook the original UE4SS builds with a code detour is skipped: LoadMap, InitGameState, BeginPlay, EndPlay, ULocalPlayerExec, CallFunctionByNameWithArguments, ProcessConsoleExec, and the StaticConstructObject seam behind NotifyOnNewObject. In the R3 marshal world one `if` skips the whole block at startup: `C:LuaMod.cpp:8871-8885` (the `else` runs to `C:9701`). Console-proven: `D:621` "[R3] refused: EngineTick pre-callback registrations", `D:780` (the startup summary naming exactly this list: "InitGameState/BeginPlay/EndPlay/StaticConstructObject/ULocalPlayerExec/CallFunctionByNameWithArguments/ProcessConsoleExec/custom-event script hooks stay unregistered for this process lifetime"), `D:668` (StaticConstructObject detour failed), `D:920-922` (the only retry, LoadMap, refused).

**Cause 2: the two ProcessInternal settings are 0.** `HookProcessInternal=0` and `HookProcessLocalScriptFunction=0` (`UE4SS-settings.ini:61-62`; the ini comment says "both keys REQUIRED 0"). With them off, `ProcessInternalInternal` is never filled in (`C:UnrealInitializer.cpp:3084` gates the whole derivation, which reads game code bytes), so, once the function is found, `RegisterHook` on a Blueprint function matches neither branch and falls to the error branch (`C:LuaMod.cpp:6017`, `6043`). Whether the minimap's calls got that far, or died earlier at the path lookup (`:5994`), is undecided (see R01). With `ProcessLocalScriptFunction` unavailable (`D:764`), the "script hook" that serves custom events and Blueprint hooks is never registered (`C:9691-9694`; no "Enabling custom events" in `D`).

**The settings are not the fix.** Setting them to 1 would make the runtime read game code (faults on execute-only text) and the delivery would still need a detour (`script_hook` is a ProcessLocalScriptFunction post-callback, `C:8610`, `UP:6293`, `UP:7219-7221`). Likewise `HookBeginPlay`/`HookEndPlay`/`HookLocalPlayerExec`/`HookCallFunctionByNameWithArguments`/`HookProcessConsoleExec` are `false` (`UE4SS-settings.ini:65-68,74`), which leaves those addresses unresolved, but turning them on does nothing while the block above is skipped. `HookLoadMap=true` and `HookInitGameState=true` do resolve their addresses (`D`: "GameEngine::LoadMap address 0x3c4d460", "GameModeBase::InitGameState address 0x33db2b0"), which is what makes the vtable route possible.

**PC for comparison.** Upstream ships all ten `Hook*` settings at 1 (`assets/UE4SS-settings.ini:216-226` in the vendored upstream) and installs each as a detour (`UP:6450` LoadMap, `UP:6520-6607` InitGameState/BeginPlay/EndPlay, `UP:6626` StaticConstructObject, `UP:6728-6925` Exec families, `UP:7219` custom events). Upstream's Blueprint hook is a **post-body** callback only (all Lua callbacks of a Blueprint hook run in `script_hook`, a post-callback, `UP:6293`); a `Func` swap can give a real pre and post, so it is a superset there. The vendored upstream cannot be checked against its `Hooks.cpp` (the Unreal submodule is not in the tree); the detour claim rests on the runtime's own comment `C:LuaMod.cpp:8838-8851` and the log lines above.

## Details by route

### R01/R02: Blueprint-function RegisterHook via `Func` swap (P1) (rewritten after review)

- **Where the call dies is not known.** `RegisterHook` does two things in order. First it looks the function up by its path (`StaticFindObject`, `C:LuaMod.cpp:5992`) and throws if nothing is found (`:5994`). Only then does it check the function (`:6003` native branch, `:6017` script branch, `:6043` error branch). Both throws are caught by the minimap's `pcall`, so the B4 log has no line for either. What B4 does prove (console-proven): the minimap's hook path reached the runtime (`D:994`, the pawn class name was read at 06:59:34); no hook registered (only `D:807`, `D:818`); and there is no `[StaticFindObject] long-name part ... not in FName pool` line anywhere in `D` (that error line is what the lookup prints when a name part is missing from the name pool, `UObjectGlobals.cpp:493-499`). So the "name part missing" sub-case did not happen. The remaining cases are: lookup found nothing after walking the outer chain (`:5994`), or lookup found the function and the hook was refused (`:6043`). (Mac-only: reading code and the absence of a line.)
- **Why path lookup of a Blueprint function is doubtful on the console.** The runtime's own comments say so: `C:LuaMod.cpp:5686-5693` ("on console the StaticFindObject lookups cannot resolve at all (GATE-1 numbered duplicates ...) 'not interned'") and `:5855-5860`. Since then the lookup was rewritten ("layer 3", in the B4 build; `UObjectGlobals.cpp:456-560`), and it works for engine paths: `/Script/Engine.PlayerController:ClientRestart` resolved and hooked (`D:807`, `D:818`) and the carrier base functions (`/Script/Engine.Actor:ReceiveTick` etc.) resolved (`D:914`). **No log, in B4 or in the three earlier decoded sessions I searched, shows a `/Game/...` Blueprint function resolving or failing** (searched for `Registered script hook`, `no UFunction with the specified name`, `long-name`). Also, `FUObjectHashTables unavailable, object lookups use GUObjectArray` (`D:763`): the lookup walks names and the object array, no hash table.
- **What exists for the swap itself (console-proven):** `UFunction::RegisterPreHook/PostHook` swap the function's `Func` pointer to one of 256 static thunks that call the original (`ScriptHookThunks.cpp:123-155`, capacity `ScriptHookThunks.hpp:7`, both in `outputs/2026-10-08-r5-source-integration/source/`). It does not require the native flag. The pump carriers already do exactly this to Blueprint script overrides: `D:908-913` armed (the first six shown), `D:914` "66 override(s) found", `D:918` "marshal hook first invocation (carrier fired)". Native `RegisterHook` through the same thunks: `D:807`, `D:818`, `D:893-894`. The carriers find their functions by scanning the whole object array for Function objects and walking their super-struct chain (`C:5761-5818`), not by path.
- **What the fix needs (design only), in order:**
  1. **A resolver that does not depend on path lookup.** Split the path at the last `:` into class path and event name. Scan the object array once for Function objects (the same loop as `r3_marshal_arm_event_carriers`, `C:5761-5818`) whose name equals the event name (looked up pool-only with `FNAME_Find`; a miss means no such function exists) and whose owner chain matches the class name. Bucket the result by name so the three minimap calls cost one pass (the scan reads ~155k objects in other uses, `D:2208`, `D:2215`). Run it only when the path lookup returns nothing. Cost per pass is not measured. Needs no new offsets.
  2. **The branch change in `RegisterHook` (and `UnregisterHook`).** Native flag clear plus a second signal that the function is script (non-empty script bytes, or `Func` equal to the `Func` of `/Script/CoreUObject.Object:ExecuteUbergraph`, a plain data read; the existing disabled block reads it at `UnrealInitializer.cpp:3092`, only the jump-follow after it reads code) goes to the thunk path (`C:6003` style) instead of falling to `:6043`.
  3. **One console probe** (needs the user's OK per console action): hook one Blueprint event from zzdiag, count hits, check that parameters read correctly from a script frame (unproven), and check the minimap's three events fire at all.
- **Coverage limit (Mac-only, the runtime's own comment `C:LuaMod.cpp:5698-5705`):** calls made from other Blueprint code use the local-script path and bypass `Func`. A hook on an event that is only ever called Blueprint-to-Blueprint will not fire. Whether the minimap's three events are engine-called is unknown; the probe tells.
- **Risk:** medium. Thunk slots: 66 used by carriers at startup, 190 left. Everything stays data-only; the no-detour gate is unaffected. If the lookup is the failing step, the branch change alone would change nothing: step 1 comes first.
- **Also:** with the call succeeding, the lock-leak trigger disappears from this site, but B5/B6/B7 must stay.

### R05/R06: LoadMap through the private vtable copy (P1)

- **The slot has one source, not two (correction).** UEngine::LoadMap is vtable byte offset `0x4F8` (profile `layout.vtable.UEngine::LoadMap`, 1272). The only identification is a **static inference** in `outputs/2026-10-07-l19-r4-engine-slots/ENGINE-SLOT-FACTS-v2.json` (it says `live_validation: false` and "Method identity is an inference from named native callers, parameters, dedicated LoadMap configuration and body semantics"). The live line `D:616` "GameEngine::LoadMap address 0x3c4d460" (= static `0x384d460` + base `0x400000`) is the runtime reading the same profile offset: it checks the table content, not what the function is. My replay agrees with both (slot 159 -> `0x384d460`, slot 98 Tick -> `0x2fac8c0` = `D` "GameEngine::Tick address (vtable: 0x33ac8c0 ...)") but reuses `0x4F8`, so it is not independent either. **A second source must be produced before Lua is called from this slot:** the staged log-only LoadMap entry (`round5-staging/world-fix/04-event-map-logger.patch`) should fire exactly at a map change, with a map name that matches the World change the runtime already sees. That is an in-game observation of the slot's behaviour and would count as the second source.
- **An existing data-only map-change signal was left out of the first version:** `[FL-MAP] order=n map='...' phase=loaded src=marshal-watch`, `C:LuaMod.cpp:5110-5135` and `:5240-5247`: a bounded 1 Hz World-identity check on the proven pump. It only logs (it does not call Lua) and its comment calls it "the ONLY source that can deliver in the current console world". There is no `[FL-MAP]` line in the B4 log (the check did not fire, or the world did not change after it armed). It is the nearest existing source for a "post" LoadMap delivery: it could be extended to deliver `RegisterLoadMapPostHook` callbacks at up to 1 s late, with no vtable work. It cannot deliver "pre" (the map name before loading).
- **The mechanism is written and host-tested:** `VmtTickPumpCore.inc` copies the GameEngine vtable, replaces one slot, and publishes with one aligned vptr store; the original table is never written. A staged patch adds a LoadMap entry to the same copy (`round5-staging/world-fix/04-event-map-logger.patch`, design in `agent-IO-eventmap.md`), but it only logs.
- **The blocker (hypothesis, Mac-only):** `[EU-VMT] arming refused: non-text-ent` (`D:623`; `[ST] pump vmt REFUSED`, `D:658`). The scan (`kMaxEntries=512`, `UnrealInitializer.cpp:2156-2176`) takes "last code pointer in 512 entries" as the table size, then refuses if any non-code word is inside. On the image the GameEngine table seems to end at entry 178 (entry 179 is a raw constant `0xffff...ffd8`, the next table's offset-to-top). The scan reaches entry 507 with 126 non-code words inside (`evidence/vtable_extent_check.py/.out`). **Sensitivity (new, `evidence/vtable_extent_sensitivity.py/.out`):** the replay counts any relocated pointer inside the executable segment as code, and that segment starts at address 0 (`LOAD0`, the same range the runtime comment describes: "inside the executable LOAD0 text"). Entries 175 (`0x120`) and 184 (`0xe0`) pass only because of that. If the runtime's classifier is stricter, dozens of entries inside the real table fail as well and a different fix is needed. The runtime's classifier source (`rc_seed::classify_seed_address`) is not in the tree, so this stays a hypothesis until the refusal line prints the entry number and value.
- **Fix shape (not applied):** log the entry number and value on any refusal (first, so one launch settles it); then stop the extent at the first non-code, non-zero word after the Tick slot (or use the relocation table).
- **Then for R05/R06:** extend the staged LoadMap entry to queue the Lua pre/post callbacks (pre before calling the original, post after, passing the return value through as PC does). It runs on the game thread, once per map change, with the existing dispatch-scope guard. Calls Lua from inside the engine's LoadMap, so it depends on the lock work (B5/B6/B7): the Lua call must not run while the actions lock is held.
- **Risk:** medium. It replaces one object's vptr (one engine instance). Needs the user's OK per console action for any test.

### R21/R22: frame delays (P2) (corrected after review: not solved by the extent fix)

- **What the runtime does now (Mac-only, code):** `ExecuteInGameThreadAfterFrames` and `LoopInGameThreadAfterFrames` throw whenever `funcptr_marshal_usable()` is true (`C:6782-6784`, `:7009-7011`). ### R04: NotifyOnNewObject (P2)

- **Route 1 (preferred): the engine's own create-listener.** `FUObjectCreateListener` has 3 virtuals (`agent-Z8-listener-layout.md:136-141`), a listener body already exists (`FClassCreateListener::NotifyUObjectCreated`), but the registration today is a direct append to the engine array, which CLAUDE.md section 3 forbids. Needs the engine's own `AddUObjectCreateListener` address pinned from **two independent sources** with a prologue-signature admission, mirroring the delete-listener ops (`add=0x8841A0 remove=0x884240`, `D:564-565`). That create op is not in the tree (`IT-LOOKUP-SPEED.md:144-152` calls it the "missing half"). The notification arrives while the object is still being built, so the Lua callback must be queued and delivered on the pump after a serial-number check (the delete listener already exists for that).
- **Route 2 (no new pin): poll the new tail.** Each pump tick, look only at object-array slots added since the last tick and test their class. Data reads only. Exact only if the array does not recycle freed indices (`bShouldRecycleObjectIndices`, profile offset 148); that must be read and proven first.
- **Risk:** Route 1 medium (new binary pin, listener ABI risk, the same family as the l25 stall); Route 2 low risk but misses fast create-and-destroy objects and costs a little per tick.

### R09-R12: BeginPlay/EndPlay (P2, approximate)

`AActor::BeginPlay/EndPlay` are per-class virtuals: no single instance to swap, and writing the game's own vtables is not data-only under the owned-memory rules. The data-only substitute is the Blueprint events `ReceiveBeginPlay` and `ReceiveEndPlay`, which the native code calls through the engine's event path (the same path the carriers use for `ReceiveTick`: base function plus every Blueprint override, found by the carrier scan, `D:914` "66 override(s) found"). Differences from PC: the event runs inside `BeginPlay`, so a "pre" callback runs late; actors whose class never raises the event (or whose dispatch the engine skips when there is no script, unverified) are missed. EndPlay's reason argument is a parameter of the event. Needs the same probe as R01 to confirm it fires on this engine.
