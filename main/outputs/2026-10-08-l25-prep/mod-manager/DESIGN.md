## 0. Scope and hard laws

The manager owns exactly three console write surfaces and nothing else:

| Surface | Remote path | Law |
|---|---|---|
| mod files | `/data/modbridge/roots/PPSA33286/ue4ss/Mods/<Mod>/...` | byte-exact staged copies |
| pad profile | `.../ue4ss/PS5Pad.ini` | always GENERATED (keymap-gen.py), never hand-edited |
| admission manifest | `.../loadlist.txt` | always synthesized (sidecar law), uploaded LAST |

NEVER touched by this tool: `ue4ss/UE4SS-settings.ini` (1947 B pinned),
`ue4ss/MemberVariableLayout.ini`, `ue4ss/VTableLayout.ini`, the resident
PRX, `ploader.ini`, `autoload.txt`, `shared/UEHelpers/UEHelpers.lua`
(already resident, loadlist row 9962; MANIFEST: "never re-upload").
The scope is enforced in code: the deploy plan is rejected if any row's
remote path is not one of the three surfaces above.

**Console-off guard.** `--apply` is refused unless BOTH pass:
1. `--i-know-console-is-on` is given (explicit operator acknowledgment),
   checked BEFORE any network call;
2. a reachability probe succeeds (read-only `curl GET
   http://<ip>:8084/processes_list`, 5 s connect timeout).
The console is documented OFF in this session, so every `--apply` is
expected to refuse with a clear message; dry-run is the default and
performs zero console contact. Tests exercise the probe against a
guaranteed-dead loopback address (`127.0.0.1:9`) only.

**Dry-run default.** All commands are safe to run offline: they write only
inside the manager root (store/staging/receipts). `deploy` and `rollback`
print the full upload plan (path, `wc -c`, sha256) without touching FTP.

## 1. State model

```
mod-manager/                     (or any --root; tests use a sandbox root)
  modmanager.py                  the tool
  config.json                    OPTIONAL overrides (absent = built-in
                                 defaults: console endpoints, sibling tool
                                 paths, priority list, ladder)
  store/
    manifest.json                per-mod provenance (below)
    <Mod>/                       PRISTINE staged tree -- byte-exact copy
                                 of the original source, nothing else ever
                                 written here
  staging/
    PS5Pad.ini                   generated by keymap-gen.py for the
                                 current enabled set
    loadlist.txt                 synthesized console-side manifest
    artifacts/<Mod>/enabled.txt  0-byte admission artifact for mods that
                                 ship none (OUTSIDE the pristine tree)
    live-loadlist.fetch.txt      live console manifest fetched under
                                 --apply (sidecar-law input)
    readback/                    fetched-back copies for cmp verification
  receipts/
    deploy-<UTC>/, deploy-dry-<UTC>/, rollback-*/
      loadlist.txt               what was (or would be) uploaded
      PS5Pad.ini                 the pad of that deploy
      prev-loadlist.txt          console state BEFORE the apply (live fetch)
      prev-PS5Pad.ini            console pad BEFORE the apply (live fetch)
      ledger.json                mods enabled, per-file rc/readback results
    last/                        CONSOLE-state tracker; refreshed ONLY on
                                 successful --apply (dry-runs never
                                 overwrite it) -- this is the offline
                                 "last known receipt" base
```

`manifest.json` entry per mod (schema 1):

```json
{
  "name": "LineTraceMod",
  "source": "/abs/original/source",     "source_kind": "dir | zip",
  "source_zip_sha256": null,            "source_tree_sha256": "<digest>",
  "installed_utc": "2026-10-10T...Z",   "enabled": true,
  "files": [{"rel": "Scripts/main.lua", "size": 2642, "sha256": "807d..."}],
  "enabled_txt_shipped": false,         "bytes_total": 2642,
  "preflight": {"tool": "host-lua-harness runner.lua (io-shim)",
                 "verdict": "LOADS-CLEAN", "detail": ""},
  "conflicts_last_seen": []
}
```

`source_tree_sha256` = sha256 over `"<rel>\0<size>\0<sha256>\n"` lines of
the ORIGINAL source files (zip provenance additionally pins the zip's own
sha256). This is the pin audit re-verifies the store against.

**Sources accepted by `install`:**
- a mod dir containing `Scripts/main.lua` (TREE-B/TREE-A shape; the mod
  name defaults to the dir basename),
- a zip wrapping the above (extracted to a temp dir; wrapper dirs OK),
- a diag-style FLAT dir with `main.lua` directly inside (the zzdiag-v3/
  v7/v11 archive shape): staged at `Scripts/main.lua` with bytes
  untouched -- layout normalization only -- and ONLY main.lua is staged
  (sibling receipts such as `LOADLIST-ROW.txt` are evidence, not mod
  files). Pass `--name zzdiag` to pin the console-side mod dir name.

**Resident vs managed.** TownfallItemSpawner is the resident baseline
CONTROL: it participates in keymap generation (its binds are pinned rows)
but its loadlist rows come from the live/base composition and are never
managed here (uninstalling the baseline through a mod manager would be a
mistake, not a feature). `config.json resident_mods` names it and points
at the retained console copy.

**ueselftest note.** No receipt in this worktree contains a "ueselftest"
mod (checked: zero hits across outputs/). It is modeled as an ordinary
installable mod: when its archive exists, `install <dir> --name ueselftest
--enable` gives it the same row shape as zzdiag
(`file<TAB>lua_mod<TAB>ue4ss/Mods/ueselftest/Scripts/main.lua<TAB><wc -c>`
+ `enabled.txt 0`). No special-casing exists in the code.

## 2. The never-edit-mods law -- where it is enforced

1. **At install (write time).** Every file is copied byte-for-byte; the
   staged copy's sha256 is compared to the ORIGINAL source's sha256
   immediately after the copy, per file. Any mismatch aborts the install
   (the half-staged tree is removed). The store never contains anything
   except these verified copies.
2. **At audit (read time).** Every staged file's size+sha256 is
   recomputed and compared to `manifest.json`; the tree digest is
   re-derived. Any drift (someone edited the store) is a VIOLATION
   (audit exit 2) naming the file, with the remedy "reinstall from the
   original source" -- never "fix the file in place".
3. **By construction (write surface).** The manager's only generated
   artifacts are `staging/PS5Pad.ini` (from keymap-gen.py), the
   synthesized `loadlist.txt`, and 0-byte `enabled.txt` admission
   artifacts that live OUTSIDE the pristine tree when the mod ships none.
   Mods that DO ship `enabled.txt` (MiniMap/ModMenu) have theirs staged
   verbatim like any other file.
4. **Pre-flight reads the store copy**, so what is verified is exactly
   what would be uploaded.

## 3. Admission re-pin procedure (size-exact MFA)

MFA admission is SIZE-EXACT: every loadlist row's byte count must equal
`wc -c` of the exact uploaded bytes, checked all-or-nothing at
`module_start` (`modforge_activation.c` size gate); a mismatch fails the
whole activation with `mfa_activate_failed code=-8` and the game silently
continues unmodded. The actual row formats (verbatim from the receipts):

```
file<TAB>config<TAB>ue4ss/UE4SS-settings.ini<TAB>1947
file<TAB>config<TAB>ue4ss/MemberVariableLayout.ini<TAB>588
file<TAB>config<TAB>ue4ss/VTableLayout.ini<TAB>216
file<TAB>config<TAB>ue4ss/PS5Pad.ini<TAB>3718            <-- re-pin target
file<TAB>lua_mod<TAB>ue4ss/Mods/<Mod>/Scripts/main.lua<TAB><bytes>
file<TAB>lua_mod<TAB>ue4ss/Mods/<Mod>/<sidecar>.lua<TAB><bytes>
file<TAB>lua_mod<TAB>ue4ss/Mods/<Mod>/enabled.txt<TAB>0
```

**When PS5Pad.ini changes size** (any change to the enabled set changes
the generated bytes, because the inputs-sha256 header changes):

1. Regenerate: `keymap-gen.py --mod <resident>+<enabled store mods, in
   priority order> --pin-pad <console-proven 3718 B profile> --ladder
   pairs10 --out staging/PS5Pad.ini`. The generator self-validates
   (mirror parser: reserved buttons, chord containment, 128-row and
   16384-B laws) and hard-fails on violation.
2. Chain-check: `keymap-gen.py --check staging/PS5Pad.ini --mod ... --
   expect-size <N>` where N = `wc -c` of the regenerated file -- this is
   exactly the number the loadlist row will pin.
3. Synthesize the loadlist with the pad row REPLACED IN PLACE:
   `file<TAB>config<TAB>ue4ss/PS5Pad.ini<TAB><N>`. Row position is
   preserved from the live/base manifest (the pad row stays among the
   config rows); only new mod rows are appended at the end (the
   documented zzdiag/spawner append position).
4. Upload order law: mod files FIRST, then PS5Pad.ini, then loadlist.txt
   LAST -- the manifest references the other files and MFA reads it at
   module_start, so the console must never hold a manifest naming files
   that are not there yet. (This is also why a mid-deploy failure leaves
   admission consistent with the PREVIOUS state.)
5. Binary-safe text discipline on the pad (LF, no BOM, trailing newline
   kept; generator output is pure ASCII by construction) and readback
   `cmp` of EVERY uploaded file (fetch + byte-compare). Text files need
   no `SITE SELF` toggle (the ftpsrv decrypt hazard is executable-only).
6. Determinism: regenerating the SAME enabled set yields byte-identical
   output (FV key-identity hashing, no timestamps) -> same size -> NO
   re-pin needed. Verified by test T12 (empty-set round-trip) and the
   pinned 1728 B constant for {spawner, LineTraceMod} in test T5.

**Offline vs online base.** Deploy synthesis starts from: the LIVE
console loadlist (fetched under --apply; sidecar law -- never
blind-write), else `receipts/last/loadlist.txt` (last known console
state), else the documented BASE_COMPOSITION constant (12 lines / 447 B,
TEST-PLAN.md). Rows of manager-installed mods and the pad row are
replaced/added/dropped; EVERY other row is preserved verbatim and in
order ("keep live values" reconciliation rule).

## 4. Conflict policy

Detection reuses FV's own extractor (keymap-gen.py imported as a module;
no duplicate parser): every enabled participant's `main.lua` binds are
extracted (direct + table-driven, comments stripped) and grouped by key
identity (`MODIFIERS+KEY`).

- **Install time:** every shared identity is printed as an FV-style WARN
  (`shared key: F7 fires for TownfallItemSpawner, zzdiag -- UE4SS binds
  are non-exclusive; every callback fires`) and recorded in the manifest
  (`conflicts_last_seen`). Conflicts can only involve ENABLED mods +
  residents, because disabled mods are not in the pad set.
- **Deploy time:** REFUSAL (exit 2) while any conflict is unresolved.
  Resolution paths: `disable` one of the mods, or explicitly accept the
  co-fire semantics with `--allow-cofire` (UE4SS binds are non-exclusive
  notifications, so two mods on one key is legal but must be a reviewed
  decision, not a silent default).
- **Pool exhaustion** (a wanted key stays UNMAPPED -- the 10-slot pairs10
  ceiling): deploy refuses with `--allow-unmapped` as the documented
  acceptance path (the generated ini carries the WARN block either way).
- **Pre-flight failures** (e.g. BPModLoaderMod FAILS-AT :117): deploy
  refuses while such a mod is enabled (`--allow-preflight-fail` exists
  for a reviewed override). Mods are never edited to make them pass.

Gate order in deploy: preflight -> keymap regen+check -> conflicts ->
synthesis -> (apply) uploads. All gates run before any FTP write.

## 5. Rollback

Two mechanisms, both receipts-based:

1. **Receipt pair restore (`rollback`).** Every successful `--apply`
   stores the console state it found (`prev-loadlist.txt` +
   `prev-PS5Pad.ini`, both live-fetched before upload) in
   `receipts/<ts>-deploy/` and mirrors them to `receipts/last/`.
   `rollback --apply` re-uploads that pair (pad first, loadlist LAST),
   readback-cmps both, and writes a rollback receipt. Manager state
   (enabled mods) is untouched -- the next deploy re-asserts it.
2. **Deterministic regeneration.** Disabling the offending mod and
   regenerating reproduces the previous pad bytes EXACTLY (FV hashes the
   key identity only), so rollback of the pad needs no stored copy in
   the common case; the receipts exist for the loadlist row set and as
   forensic proof.

`rollback` refuses when `receipts/last/` lacks the prev pair (no
successful apply has happened in this store) -- rolling back to an
imagined state is worse than refusing.

## 6. Audit (`audit [--console] [--verbose]`)

Mirrors and extends FV `--check`:

1. **Store integrity:** per-file size+sha256 vs manifest + tree digest
   (the never-edit law re-verified; drift = VIOLATION, exit 2).
2. **Loadlist consistency:** every managed row's byte count vs the staged
   file's `wc -c`; exactly one pad row; pad row == regenerated pad size;
   no stray rows belonging to installed-but-unmanaged mods.
3. **FV --check** with `--expect-size` = the pinned pad row (the full
   MFA chain offline: parser rules, reserved buttons, containment,
   orphans, unmapped keys, shared-key disclosures).
4. **Drift report:** with `--console` (and the console reachable), the
   LIVE loadlist is fetched read-only and every NON-managed row is
   compared to the synthesis -- a row that changed outside the manager
   is reported as drift (WARN). Offline, the same comparison runs
   against `receipts/last/loadlist.txt`.

Exit codes: 0 clean / 1 warnings / 2 violations (matches FV conventions).

## 7. Three-pass console acceptance plan

Run AFTER the console is back, per the standing session laws (one launch
per clean boot; harvest after each; never replay a failed configuration;
crash -> preserve logs -> reboot). Each pass = one manager deploy (or
rollback) + one launch + one `harvest.py --label mm-gg-<pass>`.

**Pass 1 -- ADMISSION (did MFA accept the exact bytes?).**
- Manager: `deploy --apply` (with the required flag + live probe);
  confirm the upload plan showed only the three legal surfaces and every
  readback cmp passed (ledger.json).
- Launch, main menu 90 s, clean exit.
- Evidence: UE4SS.log has `[l22] Lua mod started: <Mod>` for EVERY
  enabled mod; NO `mfa_activate_failed` / `code=-8` anywhere; the
  spawner control markers still fire (co-residency law). Failure here =
  admission owner (row size vs uploaded bytes -- re-run audit, never
  relaunch on the same state).

**Pass 2 -- FUNCTION (do the mapped chords reach the mods?).**
- In-game (save loaded): press each auto-assigned chord from the
  DEPLOYED PS5Pad.ini (the receipt copy is the source of truth) once,
  spaced.
- Evidence: `[l22] keybind callback entry key=<K>` for each mapped key +
  the mod's own functional markers (per TEST-PLAN rungs, e.g.
  LineTraceMod `Doing line trace`). Failure with no keybind entry = pad
  owner (verify the row, the containment law, the re-pin); failure after
  the entry = marshaling owner (per the FM table).

**Pass 3 -- ROLLBACK/REGRESSION (does removal restore the prior state?).**
- Manager: `disable <Mod>` (or `rollback --apply` for the hard path),
  deploy, next launch.
- Evidence: the mod's start line ABSENT, no new keybind entries for its
  keys, spawner control unaffected, klog clean; re-enabling + deploy
  reproduces the pass-1 pad byte-identically (determinism law, no re-pin
  drift) and pass-1 admission evidence repeats.
- Only after pass 3 is the manager's lifecycle (install -> deploy ->
  disable/rollback -> redeploy) accepted end-to-end.

## 10. End-to-end wiring: overlay + keymap + loadlist (agent HK, 2026-10-10)

The manager now composes THREE tools into ONE install/deploy flow:
itself, FV keymap-gen.py, and GK's pak-overlay/overlay_builder.py
(currently extended by HI; subprocess-coupled only, per the stable
contract in `pak-overlay/mod-manager/INTEGRATION.md` -- one JSON document
on stdout, exit 2 = refusal with `code`+`detail`, never retried).

### 10.1 The one-command flow

```
python3 modmanager.py install <dir-or-zip> --enable   # lua OR asset trio
python3 modmanager.py deploy                          # ONE plan document
python3 modmanager.py deploy --apply --i-know-console-is-on
```

- `install` recognizes a third source shape, `assets`: a dir (or zip)
  with `.utoc`+`.ucas` files and no lua. Files are staged byte-exact
  under the never-edit law like any other mod; preflight records
  NOT-APPLICABLE (no lua to harness). `.pak` files are staged too, but
  warned: the builder is IoStore-only (`pak-overlay/UNSUPPORTED.md`).
- When the mod carries `.pak/.utoc/.ucas`, install runs an OVERLAY
  ADMISSION dry-run: `overlay_builder.py --paks-dir <game_dump_root>
  --index <overlay_index> --state-dir <staging>/overlay-state install
  --mod <ModName>--<utocstem>=<store path>.utoc --dry-run`. The builder's
  full plan/ledger JSON is captured verbatim into
  `receipts/install-<ts>/overlay-plan.json` and summarized in the
  manifest entry (`overlay.verdict` PLANNED/REFUSED/UNAVAILABLE/ERROR,
  `overlay.mod_ids`). A refusal at install is a WARNING + record, not an
  abort -- the conflict only matters when the mod is enabled.
- Overlay-owned files NEVER get loadlist rows and are NEVER uploaded
  under `ue4ss/Mods/` (scope law unchanged: the three console surfaces
  are exactly what they were). Asset-only mods contribute zero rows.

### 10.2 New config (config.json keys; also CLI --game-dump-root/--overlay-index)

`game_dump_root` (local paks-dir mirror of the game dump -- the planning
target), `overlay_index` (base index name, e.g. `pakchunk0-ps5.utoc`),
`overlay_state_dir` (default `<root>/staging/overlay-state`; keeps the
dump mirror free of manager state), `overlay_builder` (path; default the
sibling pak-overlay tool), and optional `overlay_base_ucas_size` /
`overlay_base_container_header` passthroughs for dumps whose base .ucas
is not local. Unset + enabled asset mods => deploy refuses with the
exact remedy (configure or disable).

### 10.3 Keymap wiring completed

`_post_state_change` (after every install/enable/disable/uninstall) now
runs regen AND `--check` (the same FV chain deploy gates on); any
VIOLATION aborts the state change (staging must never be inconsistent).
Pad-size drift is re-pinned into the loadlist pad row at the same moment
(`synthesize_loadlist` pins `wc -c` of the fresh pad; the MFA row is
printed). Determinism is unchanged (T12 round-trip still passes).

### 10.4 Unified deploy plan (ONE document)

`deploy` prints and saves (`receipts/deploy-<ts>/deploy-plan.json`) a
single `deploy-plan` document composing every prep-owned surface:

| field | content |
|---|---|
| `uploads` | ordered console uploads (order law; loadlist LAST), bytes + sha256 each |
| `pad` | size/sha + the exact re-pinned MFA row |
| `loadlist` | bytes/sha + which base (live-fetch / last-receipt / base-composition) |
| `overlay` | status, desired mods, journal mods, builder dry-run plan (derived index/sidecar shas), verify verdict |
| `rollback` | receipts/last prev pair (console) + the journal backup path (overlay rollback ref) |

Never in the document: PRX, settings, ploader (surfaces note is embedded
in the doc itself).

### 10.5 Conflicts block deploy end-to-end (both families)

- FV shared-key conflicts -> refusal + `--allow-cofire` (unchanged).
- Builder package-ID/chunk/virtual-path conflicts (`mod_conflict_rejected`)
  -> refusal naming the code, the conflicting ids, and the remedy:
  disable one mod, or `--allow-overlay-conflict` (the builder's
  later-wins policy as an explicit reviewed decision).
- Journal STALE/DRIFT (game update / foreign write / source drift) ->
  refusal pointing at `overlay_builder.py verify`.
Gate order: preflight -> keymap regen/unmapped -> FV conflicts ->
overlay composition+verify -> FV --check -> synthesis -> uploads. All
gates run before any upload planning (test-asserted).

### 10.6 --apply overlay semantics (Mac-local; console Phase B)

After console surfaces upload + readback-verify, the manager publishes
the overlay LOCALLY against the game dump mirror (real builder
install/uninstall, not dry-run) and enforces the determinism law: the
real publish's derived-index/sidecar shas must equal the dry-run plan's;
then `verify` must return OK. Failures refuse with the note that console
surfaces are already consistent (loadlist is uploaded LAST). Console
shipping of the overlay trio remains Phase B (builder doc): NOT this
tool. `rollback` still restores only the console prev pair; the overlay
rollback ref (journal backup path) is surfaced in the plan document and
the builder's own uninstall path.

### 10.7 Audit/list

`audit` adds an overlay section (builder `list` + `verify`): journal
mods not in the enabled set = pending-removal warning (next deploy
re-derives without them); STALE/DRIFT = warnings with the reconcile
remedy; REFUSED overlay admission on an enabled mod = warning.
`list` gains an `overlay` column (PLANNED/REFUSED/...).
