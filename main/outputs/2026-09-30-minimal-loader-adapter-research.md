# Minimal loader adapter research — 2026-09-30

The pinned SDK establishes how its first argument is overloaded and how it forwards ordinary syscalls through a libkernel stub. **It does not establish a complete minimal normal-process resolver for the freestanding diagnostic.** Its existing name resolver and automatic termination detector both use kernel-memory access. Keep them excluded. A small adapter can be designed and fixture-tested, but the ordinary syscall 591 path and actual stub error tail remain target-contract uncertainties.

This research read public primary sources and local files only. No console/device contact, payload transmission, production-source edits, staging, or commits occurred. The user now identifies the launch tool as “webkit autoloader v0.5.0”; that is a useful identification lead, not proof of the loader binary currently serving port 9021. The comparison below remains elfldr v0.26 until the actual chain is identified.

## Exact source contract

Source identities: SDK source-review commit `f7fd02e6e195902a449b5e664917be8c01888b34`; elfldr v0.26 commit `54966675d3884ba9c773f0f52646f8f46b92cbbc`. Links use line numbers from downloaded raw files. Temporary source copies and SHA-256 manifest are under `/tmp/minimal-loader-source/`.

Provenance clarification: the reviewed SDK commit is a post-release revision, not the v0.43 tag. The release commit is `d9c9519116944a7f1c22d262012c53b80b3520b7`. Original source pins, URLs and hashes remain historical evidence; see [SDK provenance correction](2026-09-30-native-sdk-host-route.md#release-identity-correction-and-impact).

The six-field LP64 structure is 48 bytes. Offset 0 is declared `int (*)(int, const char *, void *)`; offset 40 is `int *payloadout`. The four intermediate fields provide kernel-access state and must remain unused by this diagnostic. [SDK argument structure](https://github.com/ps5-payload-dev/sdk/blob/f7fd02e6e195902a449b5e664917be8c01888b34/crt/payload.h#L20).

In elfldr, offset 0 receives the resolved `getpid` address (`HoLVWNanBBc`). The loader places a saved instruction pointer on the stack, sets entry RIP, and passes args in RDI. Its socket ELF path uses the spawned-process function. [Argument construction](https://github.com/ps5-payload-dev/elfldr/blob/54966675d3884ba9c773f0f52646f8f46b92cbbc/elfldr.c#L329), [entry setup](https://github.com/ps5-payload-dev/elfldr/blob/54966675d3884ba9c773f0f52646f8f46b92cbbc/elfldr.c#L371), [socket dispatch](https://github.com/ps5-payload-dev/elfldr/blob/54966675d3884ba9c773f0f52646f8f46b92cbbc/socksrv.c#L133).

SDK startup calls slot `(1, "sceKernelDlsym", &p)` and, on nonzero return, retries handle `0x2001`. Only `p == slot` selects resolver mode; then it resolves `getpid` using the same handles. Otherwise it treats the original slot as `getpid`. It rejects a null stub and adds `0x0a`. This is compatibility recognition, not pointer validation: failure to self-resolve does not prove an arbitrary pointer is a stub. The routine itself does not initialize kernel-access fields or patch privileges. [SDK syscall initialization](https://github.com/ps5-payload-dev/sdk/blob/f7fd02e6e195902a449b5e664917be8c01888b34/crt/syscall.c#L38).

The forwarder maps C arguments `(number, a1, …, a6)` to RAX=number, RDI=a1, RSI=a2, RDX=a3, R10=a4, R8=a5, R9=a6; it calls the saved libkernel address and returns. It performs no explicit carry-flag test, errno assignment, or error conversion. A fixed three-argument resolver thunk can avoid the generic six-argument/stack case. [Forwarder assembly](https://github.com/ps5-payload-dev/sdk/blob/f7fd02e6e195902a449b5e664917be8c01888b34/crt/syscall.c#L23).

elfldr independently uses the same `getpid + 0x0a` convention and register layout in its own process-control machinery. This is corroborating source evidence, not permission to include that machinery in the adapter. [Loader syscall convention](https://github.com/ps5-payload-dev/elfldr/blob/54966675d3884ba9c773f0f52646f8f46b92cbbc/pt.c#L257).

## Resolver distinction and exact limits

`kernel_dynlib_dlsym` returns an address or zero, not the slot function's integer status plus output pointer. It encodes the name to a NID and traverses kernel dynlib structures, copying their symbol/string tables through kernel helpers. Consequently, `KERNEL_DLSYM`, its resolver, and the SDK termination detector cannot be extracted as ordinary user-process functionality. [Resolver implementation](https://github.com/ps5-payload-dev/sdk/blob/f7fd02e6e195902a449b5e664917be8c01888b34/crt/kernel.c#L1065), [name-to-NID wrapper](https://github.com/ps5-payload-dev/sdk/blob/f7fd02e6e195902a449b5e664917be8c01888b34/crt/kernel.c#L1121), [macro](https://github.com/ps5-payload-dev/sdk/blob/f7fd02e6e195902a449b5e664917be8c01888b34/crt/kernel.h#L22).

The pinned SDK declares number 591 as `SYS_sprx_dlsym`, but no invocation occurs in the fetched pinned CRT sources. A plausible ordinary adapter is a three-argument call `(591, handle, symbol_name, &address)` forwarded through the validated libkernel stub. **The pins alone do not prove its name/NID treatment, permission policy, error normalization, or availability in the actual spawned process.** There is no justified fallback to kernel symbol-table traversal if it fails. [SDK number definition](https://github.com/ps5-payload-dev/sdk/blob/f7fd02e6e195902a449b5e664917be8c01888b34/crt/syscall.h#L40).

The committed `sce_stubs/libkernel*.c` files contain export labels rather than executable implementations. Their generator emits labels. They cannot establish the actual `getpid` bytes, error branch, or `sceKernelDlsym` wrapper body. The exact pinned contract is the offset assumption `+0x0a`; a full target stub byte sequence remains unestablished. Do not silently turn that source assumption into a firmware fingerprint or accept any pointer whose self-resolution fails. [Generated libkernel labels](https://github.com/ps5-payload-dev/sdk/blob/f7fd02e6e195902a449b5e664917be8c01888b34/sce_stubs/libkernel_web.c#L606), [generator](https://github.com/ps5-payload-dev/sdk/blob/f7fd02e6e195902a449b5e664917be8c01888b34/sce_stubs/genstub.py#L31).

For direct resolver mode, require status `0` **and** a nonnull output, initialize that output to null before each call, and retain raw nonzero status without translating it to errno. A `getpid` stub called with resolver arguments returns a PID and does not populate the output; a positive PID is not a successful resolution. For a forwarded syscall, do not claim that its failure is always `-1`, negative errno, positive errno, or an SCE error. Those are different boundaries; the actual stub tail must establish which applies.

## Termination policy without kernel introspection

The SDK returns when its kernel resolver finds `sceKernelDlsym` at handle `0x2001`; otherwise it resolves libc `exit` at handle 2 and calls it with the result-slot value. That detector uses the excluded kernel resolver. The default initializer also calls kernel initialization and patch initialization. [Termination](https://github.com/ps5-payload-dev/sdk/blob/f7fd02e6e195902a449b5e664917be8c01888b34/crt/crt.c#L157), [initializer](https://github.com/ps5-payload-dev/sdk/blob/f7fd02e6e195902a449b5e664917be8c01888b34/crt/crt.c#L55).

The six fields contain no process-ownership/termination-policy tag. Resolver-versus-stub mode does not supply one. A module-handle heuristic cannot safely authorize exiting an arbitrary process. Use separate explicitly selected artifacts or an owned wrapper contract:

| Selected profile | Completion policy | Required evidence |
|---|---|---|
| Callable diagnostic | Store result if supplied; restore stack and preserved registers; return result | Owned caller fixture confirms returned status, result slot, and continuation |
| Diagnostic in its own spawned process | Store result; finish bounded report; invoke a confirmed own-process termination primitive | Exact launcher ownership evidence; fixture process exits and caller stays alive |
| Unknown launch profile | Unsupported; no hardware launch | Do not infer process ownership from first-slot contents |

For a freestanding spawned diagnostic, confirmed `_exit` or fixed syscall 1 avoids libc cleanup dependencies; this is a proposed adapter choice, while upstream uses libc `exit`. If termination cannot be established, mark that launch profile unsupported before hardware use. The loader's synthetic return address establishes a mechanical return path, not evidence that returning is the intended spawned-process lifecycle.

## Smallest safe design for the root implementation decision

1. Keep the present callable entry, report formatter and bounded writer. Read only argument offset 0 and result offset 40. Link neither default CRT nor kernel, patch, rtld, klog, arbitrary syscall APIs, or module-loading APIs.
2. Represent resolver mode and termination mode as two independent explicit profile decisions. A known true-resolver profile can use the supplied function directly. A known stub profile may use the source-backed `+0x0a` convention only after the actual loader contract and stub validity are established. Unknown pointers fail closed; the SDK equality heuristic alone is insufficient validation.
3. To preserve the existing four observations, propose one private, fixed-number 591 thunk plus the existing name allowlist (`getpid`, `getuid`, `geteuid`, `getpagesize`, `write`; a termination symbol only in the owned-spawn profile). Try handles 1 then `0x2001` with null-initialized outputs; accept only zero status and nonnull output. Treat other results as unavailable. This path stays experimental until ordinary 591 behavior is independently grounded and measured.
4. If 591 is unavailable, a smaller optional fixture profile could dispatch only ordinary process calls 20/24/25 and report write 4, plus termination 1 in an explicitly owned process. Mark page size unavailable rather than substituting the build's 16 KiB assumption as an observation. Getter error semantics must also be established before this profile can emit observed UIDs. The pinned SDK's FreeBSD-number header defines 1/4/20/24/25; it does not prove permission or error behavior on firmware 13.60. [Number definitions](https://github.com/ps5-payload-dev/sdk/blob/f7fd02e6e195902a449b5e664917be8c01888b34/include/freebsd/sys/syscall.h#L9).
5. Use standalone assembly with fixed numbers and a reviewed indirect transfer into the supplied libkernel stub; avoid copying the generic C variadic inline-assembly component wholesale. No direct `syscall` instruction need exist in diagnostic executable bytes. A tail transfer can avoid introducing another stack frame; verify its calling convention through owned assembly fixtures. This is a design recommendation, not a verified implementation.
6. Preserve the current direct-instruction prohibition. The existing symbol blacklist rejects `__crt_` and `syscall` names even though SDK `crt/syscall.c` performs indirect calls. Any bounded adapter exception needs an explicit root design and independent review; renaming symbols is not evidence of safe behavior. Check final disassembly and fixture call logs for the exact number/name allowlists. Byte-pattern validation constants placed in an executable segment can themselves trip the opcode scanner; avoid blanket exemptions.

Owned fixtures should cover resolver identity success/fallback/error/null output, fake positive-PID slot, valid/invalid stub selection, register preservation and stack alignment, bounded partial writes and failure, result storage on every failure, and separate callable continuation versus child-process exit. Include a denied/missing 591 fixture that proves no kernel/patch fallback occurs. Fixture results prove the adapter's response to those inputs; they do not establish the live PS5 resolver, permissions, stub tail or firmware identity.

## Decision still required

The root can proceed now with an explicit written adapter/profile design and local fixtures. It should not declare a stub-compatible native ELF ready until actual launch-chain identity, ordinary 591 contract or restricted fallback, actual stub/error behavior, and owned-process termination policy are resolved. Public-source compatibility with the reviewed SDK sources or elfldr v0.26 is insufficient evidence that either binary is installed.
