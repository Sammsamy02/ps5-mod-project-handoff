TEN OPEN REQUESTS: ONE CONTROLLER + NINE WORKERS

This scheduling limit comes from the user's supplied ZCode/Claude seat test, not
from a test performed by Codex. The observed cap was ten concurrently open
GLM-5.3-Flash/max requests across sessions. It was not ten starts per minute.
Brief oversubscription was observed but must not be treated as reliable capacity.
Other model sharing and teammate seat sharing were not tested. Reserve headroom
for any other active sessions. A worker's nested request consumes the same budget.

Controller / request 1
Own the product goal, current task graph, shared checkpoint, build composition,
hardware action queue and private publication. Read the final result of each
worker, combine only verified compatible source snapshots and resolve conflicts.
Do not spend most of the run narrating or coordinating while implementation stalls.
Maintain a table: worker, open request, owned files, prerequisite, actual output,
next action. Close completed requests before replacing them. Keep shared build
receipts stationary while composing. Do not permit an agent to launch a full
runtime rebuild from an obsolete stage snapshot merely because a path exists.

Worker 1 / request 2 — Native loading and live facts
Own a new dedicated live-loader-supplier component and its firmware profile.
Read native-runtime-startup/bootstrap, the current loader context and public
loader source already retained locally. The PRX load/SDK fix is complete; do not
repeat the log-only probe as the main task. Deliver an actual owning module facts
supplier, not stubs returning guessed base addresses. Establish what the chosen
native API returns, how it identifies a module and how ownership persists. Supply
a typed contract and the smallest actual runtime evidence required by that
contract. Coordinate any console action with the controller. Do not edit shared
ProgramFactory consumers until their owner accepts your interface.

Worker 2 / request 3 — Unreal build/layout facts
Own profiles and original-file analysis outputs for engine/build identity and
structure layouts. Read the Townfall static survey and supplied-layout/accessor
contracts. Reuse the unchanged original capture and existing serialized scanners.
Separate file offsets, mapped runtime offsets and callable addresses. Deliver
validated layout/build facts with origin and width, explicit unresolved fields
and generic rules that can identify other builds. Do not modify the original
capture, publish a fabricated successful engine map or hardcode Townfall values
inside common UE4SS code. This work can proceed independently of worker 1 until
the live correspondence step; final binding depends on worker 1.

Worker 3 / request 4 — UE4SS game-thread/Lua integration
Own the game-thread delivery adapter and focused actual Program/Lua integration
changes. Start with the current source port, activation owner, lifetime guards,
deadline/cancellation behavior and selected Tick route. Preserve the existing
conversion fallback and native FName ABI correction. Build the concrete call
path from valid supplied engine facts to reflection access and one Lua-mod
engine call. Require worker 1/2 outputs before claiming game execution. Do useful
local implementation while those prerequisites are missing, but never count a
host callback as a real Townfall game-thread callback. Item Spawner is the first
visible end-to-end UE4SS target; no per-mod AI edits are the product solution.

Worker 4 / request 5 — Windows service implementation
Own additional generic windows-services components, with disjoint files.
Implement the next observed family, starting with one-time initialization if
still missing. Use the real import census, exact documented library/name pairs
and typed Microsoft x64 adapters. Test context values, concurrency, error values,
retries, object storage widths and lifecycle retention. Reuse the existing thread
domain and last-error owner. Do not silently bind a guessed alias or return
success from an unimplemented API. A native PS5 object and a Win64 host check are
component evidence; target support remains a separate test.

Worker 5 / request 6 — PE/native C++ execution integration
Own new actual PE fixtures and package/execution integration tests, coordinating
interface changes with worker 4 and the controller. Preserve exact Win64 calls,
source/dependency owners and internal worker code pins. Exercise newly supported
services through Windows-format machine code, not only direct C unit calls.
Source-built native C++ PRX contracts and PE DLL execution are two distinct paths.
Inspect static TLS/CRT/unwind requirements from retained input examples and
propose the next bounded executable milestone. Do not overwrite the current
test alias or operate the console independently. The new 6d295f56 artifact is
ready for controller-managed target evidence.

Worker 6 / request 7 — Containers and deterministic adaptation
Own generic original-archive/container handlers and capability detection.
Retain PAK/IoStore/config preparation that already passed its evidence. Test
packing and extraction against saved original containers, explicit compression,
encryption/signing and generation limits. Keep one profile per build's facts,
not one hardcoded special case per mod. Inspect how Windows-cooked assets,
platform texture/shader variants and package paths differ before claiming a
conversion. Work with the existing archive and bundle owners rather than
creating another parallel installer. Any conversion requiring unknown engine
semantics remains an explicit gap rather than a guessed byte rewrite.

Worker 7 / request 8 — Installer, prerequisites and activation
Own the runtime service implementation and transactional install/activation
connection, using Claude's imported C components and the existing account/job
owners. Compose several selected mods, resolve prerequisites recursively with
bounds, honor FOMOD selections and conflicts, stage owned prepared output, commit
a reversible root change and preserve durable receipts. Keep original/downloaded
archives separate from installed files and loaded state. Retain crash recovery
and cancellation semantics. Provide a real modforge-service/1 implementation
instead of making the UI's spec-only capabilities appear enabled. Do not edit
Nexus auth state or credentials directly; use the existing owner interface.

Worker 8 / request 9 — Nexus app/backend readiness
Own the existing app/backend integration area only after coordination with worker
7. Audit current login/session, catalog, selection basket, download retention,
prerequisite metadata and install-record routes. Build concrete backend actions
and native launch glue where they do not depend on unfinished engine support.
Keep broad UI polish paused until engine/runtime milestones justify resuming it.
Use actual official Nexus account flows and service permissions, not scraping
passwords or inventing an authentication API. Ensure normal use happens on PS5,
with no Mac/PC required to resolve bundles or translate formats. If this role has
no independent useful implementation, close it and reuse the seat slot rather
than creating decorative screens to keep nine agents busy.

Worker 9 / request 10 — Integration, portability and evidence
Own disjoint verification/handoff scripts and final result review. Inspect whether
the chosen PS5 SDK imports are actually declared, whether native and Win64 public
layouts match, and whether build receipts bind current source bytes. Review
real engine/game results separately from host fixtures. Check rollback and
unsupported-case behavior where new writes are promoted. Reuse completed focused
checks and avoid broad retesting when no new change or unresolved issue warrants
it. Do not run large C++ builds concurrently with every worker's own build.
Give the controller exact actionable mismatches rather than vague caution.

SHARED RESOURCE RULES
Ten model requests are a seat budget, not ten compiler jobs. Limit heavy native
runtime rebuilds to a small coordinated number (usually one full composition and
one independent smaller build) so CPU, RAM and disk do not erase the parallelism
benefit. Use fresh named output directories; historical receipts and artifacts
are immutable. Source owners freeze their inputs before the controller hashes
and composes them. Do not have every agent update the same checkpoint, app.js,
LoaderContext.cpp or build.py. Parallelize across genuine independent components.

DEPENDENCY ORDER
Workers 1 and 2 feed 3. Worker 4 feeds 5. Worker 6 feeds 7. Worker 7 feeds 8.
Worker 9 reviews promoted milestones, while the controller integrates them.
Each worker starts by reading the relevant current component state, lists the
specific owned files, then implements the next concrete missing behavior.
Avoid sequentially allocating nine reviewers before one person writes code.
When the user is unavailable, leave a necessary manual launch pending and move
to an independent task. Never record an unperformed playtest as passed.
