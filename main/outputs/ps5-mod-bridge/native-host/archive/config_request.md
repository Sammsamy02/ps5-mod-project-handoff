# Config preparation requests

`config_request.c/.h` is an owning, allocation-free decoder for a separate scalar-config preparation route. It leaves `request.c/.h` and the existing archive-group request flow unchanged. A completed decode gives the caller a preparation description; all installation/runtime/game-acceptance flags remain zero.

The ordered `MBCFGREQ1` envelope contains `id`, `source`, `base`, `context`, `context_sha256`, `quarantine`, `output`, `receipt`, then `end`. All references are bounded flat filenames. Output names are derived from the 32-character lowercase hex ID (`q-ID`, `p-ID.pak`, `r-ID.json`, `claim-ID`); unsafe or case-insensitive colliding references refuse. `mb_config_request_ref_decode_v1` validates the complete envelope before the caller opens its context under an already admitted private inbox descriptor.

The ordered `MBCFGCTX1` context contains `source_bytes`, `source_sha256`, `base_bytes`, `base_sha256`, `target_token`, `role=scalar_ini`, `basename`, `max_member_bytes`, `target_entry`, `mount`, `path_hash_seed`, `section_count`, that number of `section` lines, then `end`. The caller computes SHA256 over the exact context bytes and supplies it to `mb_config_request_decode_v1`. This binds the context to the envelope; it does not authenticate a source or establish target compatibility. Target entry/mount are logical PAK metadata, never filesystem destinations. Selected member size/hash are discovered through completed archive intake rather than supplied by a mod-specific recipe.

Limits: 1 KiB envelope, 32 KiB context, 128 MiB raw source, 512 MiB original PAK, 1 MiB selected scalar member, 1 KiB logical paths, and 64 sections of at most 255 bytes. A caller may impose tighter inventory/expansion limits. All records use exact ordered printable ASCII with LF terminators; unknown/trailing fields and noncanonical numbers refuse. Known alias/span/oversize preflight failures leave output untouched, so callers must inspect the return before using an old output. Admitted parse failures clear positive fields.

The focused host control passed 24 assertions. The actual local request composition is retained in `.superpowers/native-dependency-spike/ps5-config-job-integration-2/`. It binds the materializer journal to an immutable descriptor and calls `pm_config_file_job_v1`; no per-mod content edits, pre-extracted files or preparation subprocess are inputs. That harness is a private-inbox host example, not an app download producer, resident queue, native target binary or crash-recovery installer.

## Programmatic request production

`config_request_producer.c/.h` creates both canonical records from an owning completed-source identity, the original PAK identity, profile fields and a request ID. It derives output/control references, hashes the exact context with Mbed SHA256 and roundtrips the records through the unchanged decoder before copying either output. There are no per-member golden facts or caller-selected output paths. It performs no I/O; the caller's `download_complete` value must come from a separately completed operation. Required lengths exclude NUL. Failed output buffers remain untouched, and size-query results grant no publication authority. Focused host controls passed 44 assertions.

The ordinary byte-stream sink in `private/file_sink.c/.h` can produce that source identity from received data. It borrows a fresh empty unpublished O_RDWR regular descriptor, uses a 64 KiB scratch buffer and incremental SHA256, and verifies byte count and readback after the caller syncs. A completed sink proves local file contents, not HTTP authentication, Nexus authorization or engine compatibility. Operational failures are terminal and retain partial private files; known argument/alias preflight writes nothing, so an active sink must be disposed explicitly after BAD_ARGUMENT. The caller owns all descriptors and publication.

The local `stream-config-request-composition-1/trial-1/receipt.json` proves unchanged 582-byte RAR input across four feeds→measured source identity→C-generated 326-byte request / 484-byte context→canonical 297,483,249-byte PAK. The final archive is byte-identical to the retained independently checked oracle. Neither source SHA/size nor request text is supplied by the host test runner. Base identity and profile data remain explicit inputs. No network, native target execution, game write or installation was involved.
