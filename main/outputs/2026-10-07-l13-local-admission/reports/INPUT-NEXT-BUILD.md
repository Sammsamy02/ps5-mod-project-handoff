# Input investigation and next-build recommendation

Date: 2026-10-07. Scope: local source analysis, existing local evidence, and public primary documentation. No console contact, upload, launch, executable change, or input source edit was performed. Read `AGENTS.md`, `POSTMORTEM.md`, and `PS5-MODDING-MISSION.md` before analysis. This report does not add an input fix to l13.

**Finding:** the retained provider already calls `scePadGetHandle` after `scePadOpen` returns `0x80920004`, but only on a delayed poll retry. In the latest retained l12 session, that retry never ran: Unreal initialization timed out before the update loop began. The current evidence establishes a deferred first open, not a failed current-revision borrow attempt. Keep l13 scoped to admission. For a later input-specific build, first measure the existing borrow path after admission; an engine-level key observer is the preferred alternate experiment if raw-pad borrowing fails. Neither path is yet console-proven.

## Current limits and diagnostic interpretation

- `pad_borrow_begin` is emitted **before thread creation**, so begin without returned means the attempt did not complete visibly. It cannot alone distinguish thread creation failure, SDK stall, binding/crash, or missing later capture. The source comment claiming that pair uniquely proves a firmware hang is too strong.
- No completion timeout, cancellation, or join protects the detached helper. `borrow_state`, result, selected tuple, and initialized flag are process/module globals, not a per-controller lifecycle. A failed completed borrow is never retried, and the cached result is not keyed to a later changed user tuple. Those are source limitations; no current-run failure from them was observed.
- `is_available()` means `handle >= 0`. A ReadState error does not invalidate the handle, so repeated read failures do not trigger acquisition retry. Disconnection clears baseline, but also keeps the handle. Borrowing itself does not prove correct state mirroring.
- `pad_first_state_read` proves one connected successful sample; it does not prove F7 delivery, current chord bits, or menu execution. `pad_key_edge=0x76` proves an event passed the source's allow/subscription filter, not that the game-thread queue drained.
- Changing L3+R3 to TOUCH_PAD still depends on the same unavailable handle and cannot repair acquisition. The retained [l12 INI:43](/TMP/l12-pad/PS5Pad.new.ini:43) already contains `L3+R3 = F7`; the old pad2 report's statement that no such file exists is obsolete.
- Earlier playbooks requiring handles strictly greater than zero disagree with the actual source, which accepts **zero**. Interpret a handle using the implemented/API contract, not the stale greater-than-zero checklist.

## Unreal-level input: credible alternate, with dependencies

Epic documents `APlayerController::IsInputKeyDown(FKey)` as a Blueprint-callable query of that controller's key state. The engine exposes `Gamepad_LeftThumbstick` and `Gamepad_RightThumbstick` key identifiers. This supports a design that observes the state already collected by the game's input pipeline, avoiding another `scePadOpen` acquisition. It does **not** prove Townfall currently exposes the needed reflected function/struct correctly, or that a usable local controller and callback exist at every menu/loading stage. [APlayerController API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/APlayerController), [EKeys API](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/InputCore/EKeys).

The smallest engine experiment is a game-thread observer: resolve a valid **local** PlayerController, validate the reflected `IsInputKeyDown` signature and `FKey` struct layout, query both thumbstick keys, and log only state transitions. Establish a baseline on controller/world changes and emit once on `both_down && !previous_both_down`. This tolerates L3-first or R3-first overlap without requiring their press edges in the same frame. Do not guess an FKey byte layout or assume a Lua table/string automatically marshals as FKey. The inspected port does not contain a ready dedicated FKey input bridge; generic reflection would need validation.

UE4SS documents `ExecuteInGameThread` as scheduling through ProcessEvent and `RegisterHook` as hooking an existing in-memory UFunction. Neither creates an independently running engine pump. In this PS5 fork, [LuaMod.cpp:4992](/WORKSPACE/.codex/worktrees/translation-core/what/outputs/2026-10-04-zcode-team/worker-l11-merge/staging/luamod-l11-merged/LuaMod.cpp:4992) searches Blueprint overrides of Actor ReceiveTick, AnimInstance BlueprintUpdateAnimation, and UserWidget Tick; [line5115](/WORKSPACE/.codex/worktrees/translation-core/what/outputs/2026-10-04-zcode-team/worker-l11-merge/staging/luamod-l11-merged/LuaMod.cpp:5115) explicitly says closures queue until a carrier arms. The drain at lines4733–4781 publishes/checks thread identity and processes the queued actions. A viable engine observer needs a proven, recurring game-thread carrier, including evidence it fires; enqueueing more closures cannot repair an absent carrier. A generic hook callback is not automatically proof of the correct calling thread. [UE4SS ExecuteInGameThread](https://docs.ue4ss.com/lua-api/global-functions/executeingamethread.html), [UE4SS RegisterHook](https://docs.ue4ss.com/lua-api/global-functions/registerhook.html).

`InputComponent` binding is another valid engine route, but a larger first integration: it adds delegate/binding ownership, component replacement, input-stack priority and cleanup obligations. Epic documents stack consumption and `bConsumeInput`/`bExecuteWhenPaused`; a non-consuming binding is appropriate for observing a mod chord without stealing normal game input. `BindKey` is a C++ template, not proof of a callable Lua UFunction. Its returned reference can be invalidated by another binding. Furthermore **FInputChord represents one key plus keyboard modifiers**, so it does not express two arbitrary gamepad buttons directly; use two tracked states or a validated Enhanced Input chord action. [Input overview](https://dev.epicgames.com/documentation/unreal-engine/input-overview-in-unreal-engine), [FInputBinding](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/FInputBinding), [BindKey](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/UInputComponent/BindKey), [FInputChord](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Slate/FInputChord).

These are engine APIs, not a universal binary ABI. Unreal version, platform layout, reflected metadata, local-player selection, legacy versus Enhanced Input, game customizations, UI focus, pause and travel remain profile-specific. A `FindFirstOf("PlayerController")` fallback, present in the current mod, is insufficient as a cross-game local-controller guarantee. Reusable mechanism plus validated per-game profile is the appropriate portability claim.

## Next build and longer-term decision

**l13:** retain all input sources unchanged. Its admission repair is prerequisite to observing the current borrow path. The next separately authorized console test should discriminate startup/admission, update-loop liveness, borrow, read, edge, game-thread drain, and visible menu in order. No console action is authorized by this report.

**First input-specific successor:** use the next admitted-run evidence to select one change. If the existing borrow returns a usable handle and current binding works, do not replace it merely because startup previously deferred. If it fails, stalls, or reads no useful state, prefer the small **Townfall-profile Unreal key-state observer** experiment over new pad-open argument guesses or a kernel dependency. Require a carrier-fire witness before interpreting its key samples. First prove left/right transitions and chord edges without toggling UI. If those pass, route the chord to the existing menu action in that same game-thread context, with exactly one active delivery backend. A two-key observer proves only the toggle path; the complete usable menu must also migrate or retain working UP/DOWN/CROSS/LEFT/RIGHT navigation. Do not call menu opening a completed input replacement.

If raw borrow diagnostics remain ambiguous after admission, the smallest raw-provider successor is observability only: log selected user/type/index, elapsed delay, helper-entered, raw signed completion, and a bounded late/no-completion status. Preserve delayed startup behavior and never close a borrowed handle. A thread-start witness inside the helper is needed to distinguish `pad_borrow_begin` from actual SDK-call entry. Avoid changing timeout behavior, argument tuples, backend, and game-thread carrier in the same diagnostic build.

**Longer term:** expose a reusable input source interface with explicit raw-pad and Unreal backends. Read Unreal objects only on the proven game thread; publish bounded plain input snapshots/events to the existing input owner if retaining Handler delivery. Keep chord baseline/release state per local controller/world, prevent dual backend delivery, handle controller destruction/travel/pause, and make backend selection and reflected names/layout validation per-game profile data. Add InputComponent or Enhanced Input bindings only where their lifecycle and ABI are validated. Kernel input remains a separately authorized, deferred capability; it is not required to investigate these user-space options.
