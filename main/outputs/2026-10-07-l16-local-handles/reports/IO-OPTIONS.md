# Post-startup file I/O for unmodified Lua mods — local investigation

Report only, 2026-10-07. No runtime implementation, mod edits, console contact, account contact, uploads, configuration changes, payload loads, or launches were performed. The user-approved l16 work is the bounded startup-opened probe-handle repair. This report describes broader options; it does not extend that approval.

## Recommendation

Keep l16 narrowly scoped to fully opened probe files. For broader pure-Lua mod file compatibility, use one runtime-owned logical filesystem with the existing immutable release snapshot as its lower layer and a separate writable copy-on-write layer. First establish whether the game has a usable post-startup writable root. If it does, persist that layer there. If late physical creation remains denied, evaluate a startup-opened journal/container or an outside-game file broker behind the same interface. A memory-only layer can support transient reads/writes, but must disclose that it does not provide persistence across launches.

Keep kstuff-assisted changes to game credentials/sandbox state deferred to Phase B. The present log does not establish that a kernel change is necessary. Neither a retained directory descriptor nor a finite set of preopened ordinary files gives arbitrary future filenames physical backing.

No option is yet console-proven as a general Lua I/O solution. “Unmodified Lua mod compatibility” should mean documented Lua operations over configured mod/config/data paths, with explicit errors for unsupported resources. Arbitrary Windows drive paths, native PC DLL modules, subprocess execution, and host-specific Lua extensions need separate compatibility work; file I/O alone cannot make every PC mod portable.

## Existing ownership and loader boundaries

`MakeActivatedUE4SSModSource` consumes the startup activation, moves it into a shared owner, and aliases its already preloaded bytes into `NativeFileBuffer` views. It supplies files without discovering engine addresses or doing new filesystem access. Every returned view retains the activation; the owner cannot be released while parsing or a file handle still borrows those bytes. See [activation adapter](/WORKSPACE/.codex/worktrees/translation-core/what/.superpowers/native-dependency-spike/native-coherent-runtime-1/source/bootstrap/activated_mod_source.cpp:18).

`NativeModSource` is a final class representing a bounded immutable snapshot, not a mutable filesystem. Keys are canonical UTF-8 logical names below `ue4ss/`. It rejects absolute paths, backslashes/colons, control characters, invalid UTF-8, empty components, `.` and `..`. It bounds the snapshot to 4,096 files, 8 MiB per file and 64 MiB total. `read()` returns an owned view or absence; there is no open/create/write/seek/rename/remove API. See [buffer contract](/WORKSPACE/.codex/worktrees/translation-core/what/.superpowers/native-dependency-spike/native-coherent-runtime-1/source/port/ue4ss/include/Platform/NativeModSource.hpp:10) and [validation implementation](/WORKSPACE/.codex/worktrees/translation-core/what/.superpowers/native-dependency-spike/native-coherent-runtime-1/source/port/ue4ss/src/Platform/NativeModSource.cpp:48).

The integrated `LuaMod.cpp` native branch keeps package.preload and its buffer searcher, replaces `loadfile`/`dofile`, and loads `main.lua` from a retained `NativeFileBuffer`. Relative file-loader names currently resolve under that mod's Scripts directory; the buffer module searcher checks Scripts and shared-module candidates. Standard Lua/C disk searchers are removed. This is a deliberate compatibility boundary, not proof of general `io` support. See [native loader setup](/WORKSPACE/.codex/worktrees/translation-core/what/outputs/2026-10-04-zcode-team/worker-l11-merge/staging/luamod-l11-merged/LuaMod.cpp:1179), [buffer file resolution](/WORKSPACE/.codex/worktrees/translation-core/what/outputs/2026-10-04-zcode-team/worker-l11-merge/staging/luamod-l11-merged/LuaMod.cpp:794), and [main-script loading](/WORKSPACE/.codex/worktrees/translation-core/what/outputs/2026-10-04-zcode-team/worker-l11-merge/staging/luamod-l11-merged/LuaMod.cpp:7315).

The stdio consumer adaptation is integrated according to the l15 transport ledger, but its `liolib.c` `io_open` still calls `fopen(filename, mode)` and returns Lua file errors on failure. The change avoids SDK FILE macros; it does not add a virtual writable layer. This is why successful buffer loading and general late physical `io.open` must remain separate claims. See [adapted Lua I/O](/WORKSPACE/.codex/worktrees/translation-core/what/.superpowers/native-dependency-spike/ue4ss-stdio-consumer-adaptation-1/patched/liolib.c:270) and [integration receipt](/WORKSPACE/.codex/worktrees/translation-core/what/outputs/2026-10-07-l15-full-build/receipts/prx-candidate-l15-2/driver/transport-ledger.composition6-mirror.json:5282).

## Options and tradeoffs

| Option | How an unmodified mod would use it | Main limits and risks | Assessment |
|---|---|---|---|
| Redirect to a sandbox-writable root | Runtime resolves the mod's logical relative paths into a configured, game-legal physical writable tree; Lua code remains unchanged. | No suitable late writable root has been proved here. File ownership, title isolation, cwd expectations, text/binary modes, rename/flush behavior and wrapper ABI still matter. A raw directory fd does not itself grant creation rights. | Prefer the simplest physical backend if a focused late-I/O matrix proves it. Do not guess a Sony mount path. |
| Virtual filesystem with immutable lower layer and writable upper layer | Lua file handles read release data from retained buffers; new data/config files and writes are represented in an upper layer. A virtual write to a release logical name creates a private copy and leaves release bytes/hash unchanged. | Must implement actual file semantics, not just replace `io.open`. Memory quotas, coherent concurrent handles, EOF/error behavior, persistence and lifetime accounting require work. A transient overlay is not a persistent filesystem. | Recommended reusable runtime architecture. Reuse the immutable owner's lifetime contract and add a separate mutable owner. |
| Startup-opened journal/container for VFS persistence | Arbitrary virtual filenames are stored as records in a bounded file opened read/write during startup; later reads/writes use the same handle. | Delayed read/write/seek/truncate/fsync are unproved. Requires a serialized format, crash recovery, capacity checks and atomic commit discipline. Reopening the file later recreates the original problem. Physical rename/remove cannot be assumed. | Worth evaluating after retained-handle behavior is proved. A finite preopen pool without a container only covers known files. |
| Privileged outside-game broker | Lua file requests use the same runtime filesystem interface; a separate authorized console process performs open/create/read/write/rename/remove and returns bytes or errors. It does not execute mods or call Unreal. | Transport availability after startup is unproved; neither a socket nor shared memory route is automatically allowed. Requires process/session identity, path confinement, protocol bounds, timeouts, cancellation, handle cleanup and durable flush acknowledgements. Blocking the game thread on broker I/O risks stalls; a broker crash must fail cleanly. | Most general persistence fallback without changing game credentials, but a substantial new service and separately authorized deployment. Avoid assuming FTP is a secure or suitable runtime RPC channel. |
| kstuff-assisted credential/sandbox access | A firmware-matched, reversible mechanism could make a physical backend usable when policy denies it. | Root credentials may still be insufficient for Sony sandbox policy; cause and offsets are unproved. Credential changes can race across threads, broaden the whole game and affect every title depending on kstuff. Kernel writes/recovery are higher risk than a file service. | Deferred Phase B only. No kernel change is justified or authorized by this report. |

The FreeBSD description distinguishes `openat` path resolution from a returned file descriptor and documents creation flags; it does not establish PS5 policy or grant a retained directory new privileges. The platform inference here remains conditional. [FreeBSD open/openat manual](https://man.freebsd.org/cgi/man.cgi?query=open&sektion=2)

The public kstuff-lite repository describes a `kekcall` path and checked kernel-memory operations. That is not evidence that this PS5 firmware permits safe file-policy changes. The local mission requires checking the existing interface first and using firmware-matched kstuff-lite rather than quarantined kstuffSharp/InstallerApp. [Upstream kstuff-lite](https://github.com/EchoStretch/kstuff-lite)

## Concrete runtime design requirements, not implementation

Preserve `NativeModSource` as the immutable lower layer. Add a separately owned virtual file service associated with the runtime/mod context, with logical handles carrying mode, cursor, closed/error state and lifetime. A lower-layer reader retains its `NativeFileBuffer`; a writer owns an upper-layer copy. Do not mutate the activation buffer or use its `string_view` as writable storage. Shutdown must stop users and settle/cancel I/O before destroying backend/session resources; Lua finalizers and errors must not bypass C++ cleanup.

Route `io.open` and filename-based implicit I/O through the same resolver as `loadfile`, `dofile` and the Lua module searcher, so read-after-write and newly created modules are coherent. A backend wrapper around physical `fopen` alone would leave the existing buffer-only loader unable to see new script/data files. Retain the original release manifest as the audit baseline and record upper-layer state separately.

The compatibility checklist is read/write/append/update modes, binary bytes, cursor/seek, line and numeric reads, write results, flush/close, implicit input/output, lines iterators, `io.type`, finalization and close behavior, temporary files, and normal error tuples. `os.rename`/`os.remove` and loader visibility must use the same path policy. Standard Lua permits customized module searchers. These are acceptance targets, not claims about the present runtime. [Lua 5.4 I/O and modules](https://www.lua.org/manual/5.4/manual.html#6.8)

Resolve PC-style path spelling at the runtime boundary before canonical internal validation: configured separators/root aliases, relative-base semantics, case handling and approved absolute aliases. Keep game/build roots in profiles and portable mechanism code independent of Townfall. Explicitly refuse paths outside configured roots and unsupported C-library loading/subprocesses; silently succeeding without persistence or silently falling back outside the mapped tree would mislead mods.

## Future evidence needed

These are proposed tests only; no console test was run for this report.

1. For l16, prove startup game-created read/write file opens, then a **fresh** delayed 32-byte source copy, complete same-handle readback and exact prefix match. Record raw return/errno for every open/write/read/seek/close operation. Test short transfer, EFAULT, consumed handle, timeout, refusal and cleanup. No cached-prefix or disk-only substitution may pass.
2. For broader I/O, compare startup and delayed execution on the same process using explicit APIs: `_openat`, public `fopen`/Lua `io.open`, and Sony-native calls. Separately test existing-file read, existing-file update and new-file creation at each approved candidate root. Use game-created files and record ownership/modes; do not confuse FTP-created permissions with game-created permissions.
3. Test a fully retained file handle after startup for ordinary safe-buffer write, seek, read, truncate if required, flush and close. Prove persistence in a later launch. The l16 memory-copy witness and ordinary Lua I/O have different purposes; neither replaces the other.
4. Conformance cases should exercise the semantic checklist, multiple handles, shared and per-mod paths, upper-layer changes seen by loaders, malformed/outside-root paths, quota exhaustion and restart recovery. Keep downloaded mod files immutable. Report failed/skipped cases explicitly.
5. If a broker is chosen, prove late transport access, timeouts/disconnect recovery, isolation between title/PID/session generations, durable writes and cleanup before calling it a persistent backend. Do not couple Lua file requests to engine calls.
