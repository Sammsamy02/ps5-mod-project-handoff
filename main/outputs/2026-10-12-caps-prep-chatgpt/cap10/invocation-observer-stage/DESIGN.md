# Same-invocation native observer proposal

Design only, for root review before code. Existing reviewed bridge-stage and real runtime remain unchanged. This would observe actual native calls inside a future genuine managed invocation; it supplies neither a Mono host nor proof of managed origin. Full managed host/GC/TLS/AOT/assembly/resolver prerequisites remain; B7 is independent.

## Existing concrete boundary

The pinned original candidate UE4SSProgram.cpp SHA121f2383e02e77e638dff31cd0e4b75fdd58df1715f77e7f3a1b6cacc01123da has namespace RC at104, real ready publication/callback mutex/shutdown gate at840–845 and actual atomic is_program_started getter2594–2600. Reviewed bridge-stage/stage_bridge.py inserts target-only TU-local TLS admission and the two real C definitions before init; its scope binds actual this and shutdown atomic only around the synchronous callback and restores previous binding on all exits. These definitions are the exact observation points. Probe.cs Run calls AbiVersion once first, then RuntimeProbe once with its supplied cookie; successful native replies are ABI1 and status0/echo cookie. ThrowForHostBoundaryTest has no native calls.

## Proposed internal native interface

An actual staged header would declare target-only C++ types/functions in RC::Cap10Observation, for a same-image native embedding host compiled with the same headers/toolchain:

- WindowToken: provider-local TLS identity (opaque const void*) plus uint64 serial. It is an association token, not a security capability or loaded-module reference.
- Observation: fixed-width phase/count/status/cookie/reply/ABI fields and failure bits, with no strings, containers, Mono or engine pointers. Counts saturate rather than wrap. It labels only native facts.
- bool begin_run(int32_t expected_cookie, WindowToken* token) noexcept;
- bool finish_run(WindowToken token, Observation* observed) noexcept;
- void abort_run(WindowToken token) noexcept;

Names are proposed, not existing runtime APIs. Valid caller-owned native output storage is required; null may be rejected but arbitrary pointer validation is not promised. Functions are internal link-time same-image interfaces, not added public C imports. Both actual PInvoke C symbols retain their existing ABI, statuses and noexcept. Future same-image resolver binds their exact addresses/names; no process lookup, export-table or __Internal resolution proof is inferred.

Store the complete active window BY VALUE in TU-local TLS. Never retain a host stack pointer. Keep nonwrapping serial state in that TLS; exhaustion permanently refuses new windows on that thread instead of reusing tokens. Token identity is the address of the provider-local TLS state: it distinguishes actual provider/thread instance for ordinary integration, while provider retention is mandatory to exclude unload/reload identity reuse. Metadata/runtime build IDs remain separate externally bound evidence.

## State and failure rules

begin_run requires nonzero fresh host cookie, real active callback admission, actual started state and no shutdown. It snapshots the exact admission-scope identity (address of the live native admission scope, not just program pointer). It starts at ExpectAbi, with zero entry/exit counts and no in-flight call. It refuses missing admission/readiness or output storage; failure does not publish a usable token. An already-active begin poisons the outer window and refuses the inner; no save/restore of observer windows is permitted. Freshness across invocations is the real host's recorded-cookie obligation, not implied by nonzero validation.

Actual ABI C entry records one entry only in ExpectAbi, records in-flight ABI, and on its real exit records ABI1 and one exit, advancing to ExpectProbe. Its existing return1 behavior outside observation is preserved; such calls produce no accepted evidence. Actual RuntimeProbe C entry must be next, once, with the expected cookie and matching current admission; its real exit records its actual status. Record reply only after the successful actual *reply=cookie store, from that same known value; failure leaves reply unchanged and records no valid reply. Null reply still produces existing -4, absent/shutdown/notstarted -3, caught C++ exception -5. Such failures poison the observed window. No invented successful reply or additional dereference of arbitrary reply pointers. Observation accounting itself is fixed-size/noexcept/allocation-free and has no user callbacks.

Unexpected order, duplicate entry/exit, reentrant/in-flight C call, cookie mismatch, changed admission, failure status or serial/count exhaustion poisons the window permanently. Every active-window real C entry/exit must check admission identity/readiness/shutdown, including ABI calls; current ABI return1 still identifies the contract when observation fails. Absent windows cannot yield accepted proof and no historic calls are accumulated. This fail-closed property concerns observation acceptance; it does not silently change the reviewed bridge's existing C return contract.

finish_run succeeds only for exact same TLS identity/serial/admission, ExpectComplete, ABI entries/exits1/1, probe entries/exits1/1, ABI1, probe status0, exact cookie/reply, no in-flight call, no poison, real started state and no shutdown. Consume the matching window exactly once whether accepted or rejected. Wrong token on this thread poisons the current window; wrong-thread/provider identity refuses without touching another thread's TLS. The future caller must treat any begin/finish refusal as invocation proof failure, not retry finish as if it never happened. Native output contains bounded observed facts on a matching consumed token; failure to match must leave output unusable/explicitly rejected. No result field alone may be called managed-execution success.

abort_run consumes/invalidates a matching window and is safe on normal host early-return cleanup. A wrong token cannot erase another owner's window; it poisons any local active window instead. A new admission scope poisons/cancels any prior observer window; its destructor cancels any remaining window BEFORE restoring the previous bridge admission. Observer state is never restored with prior admission state: nested callbacks cannot resurrect old proof. Thus a forgotten finish does not leave a dangling host pointer or admissible stale window. Normal host cleanup should still abort before callback return; asynchronous invocations are unsupported.

## Future real host integration sequence

Inside the genuine synchronous ready callback, with module/domain/image/thread/GC contracts already established: create token by begin_run immediately before the actual mono_runtime_invoke(Run...). Invoke the real method, check exc FIRST, then close/consume observation immediately after the actual invocation return, before unrelated native bridge calls. Accept overall proof only if native observation succeeds AND genuine no-exception boxed Int32 handling/rooting/copy yields0 AND actual loaded method/artifact association is retained. If invocation fails/throws at a native boundary, abort on the same thread; no helper-generated substitute return is accepted. The observer makes no Mono calls and does not solve the raw return/rooting gap documented in PUBLIC-SOURCE-FEASIBILITY.md.

For the deliberate managed exception, no Run window is opened; actual mono_runtime_invoke/exception class proof is supplied by the future host. This Run-only interface cannot attest zero native calls during Throw because absent-window calls are intentionally unrecorded; if the acceptance schema requires that negative observation, add a distinct expect-zero-call window in the reviewed design before implementation. Do not silently claim it from this proposed interface. Subsequent real fresh-cookie Run calls can each use their own window. Actual game continuation and owner stop/join/module teardown remain external proof requirements.

A direct native caller can produce this same two-call sequence. Therefore even perfect observed sequence/cookie/thread/provider facts DO NOT establish managed origin. Only genuine host invocation-boundary evidence plus actual artifact identity ties them to managed Run. Resolver callbacks or diagnostic direct calls must occur before begin/after finish and cannot be counted as PInvoke execution.

## Lifetime/readiness relation and smallest stage

Program validity follows existing real owner init-return/join contract while the callback mutex protects callback lifetime. Shutdown can become requested during the callback; every observed entry/exit and finish samples actual atomic state and rejects observed shutdown. This cannot prove no shutdown request occurs immediately after a final sample; owner retention, callback ordering and teardown exclusion remain required. No unsafe singleton lookup/program retention or new program/module ownership is invented. Provider image containing TLS/functions must remain loaded from before resolver registration and begin through all managed/native calls, finish/abort and callback cleanup; remove resolver roots/drain calls before unloading. TLS token/address is not that lease.

If approved, use ONE cumulative exact-hash transform from the original candidate, incorporating reviewed bridge plus observer and a genuine internal header. Validate full original hash and complete unique anchors before derived output. Keep existing bridge-stage immutable; never apply derived output. Emit only concise patch/header/stager/tests/receipts, not full runtime. Source tests can verify transformation, inverse, exact call-site instrumentation, failure guards and write refusals; they cannot execute C++/TLS/interleavings or establish target ABI/Mono invocation. One independent runtime-source review later; no implementation is authorized by this design note itself.

## Approved corrections before implementation

The design above is amended: token issuance uses a provider-local global std::atomic<uint64_t> CAS counter, permanently refusing after maximum value, plus current TLS address. Per-thread serial is forbidden: TLS addresses can be recycled after thread termination. Uniqueness is only within the retained loaded provider lifetime; module retention remains required. No OS thread IDs are invented. Active admission identity remains independently checked.

WindowKind explicitly distinguishes RunImports and NoNativeCalls. begin(kind,cookie,token), finish(token,observation), abort(token) are the concrete proposed names. RunImports requires nonzero fresh cookie and the exact pair. NoNativeCalls records/poisons any actual C entry, and finish requires zero entries/exits plus unchanged admission/readiness/shutdown conditions. It can therefore observe the negative native-call fact around a real Throw invocation, while the future host separately establishes the actual managed exception/class and origin. NoNativeCalls does not synthesize an exception or claim exception proof.
