The callback is the native **init caller thread**, not a claimed game thread. Existing source permits this probe because it reads atomic initialization state and echoes a scalar; it does not touch game objects. Future managed host must attach this actual thread before invoking and must remain synchronous within the admitted callback. Structural RAII nesting/restoration does not establish nested managed-host support. A new cookie/invocation identity prevents stale observations being reused but is not cryptographic attestation.

Actual bridge-stage definitions currently emit **no invocation observations/counters**. ## Retained Mono source anchors for the host boundary

Official pinned Mono commit0cbf0e290c31adb476f9de0fa44b1d8829affa40 remains the transition source; hashes in SOURCE-RECEIPT.json bind the inspected retained files. In `transition-audit/upstream/mono/metadata/object.c:3063–3112`, the genuine mono_runtime_invoke documents NULL receiver for static methods, pointers to value-type arguments, boxed value-type result, and unusable result if exception is returned. The implementation enters GC-unsafe mode, calls mono_runtime_try_invoke and converts runtime errors to managed exceptions when exc is nonnull. A null exc uses a different raising path and is inappropriate for this proof.

`object.c:7197–7200` implements mono_object_get_class; :7242–7247 implements mono_object_unbox and explicitly warns that non-valuetype input asserts. `upstream/mono/metadata/appdomain.h:179` declares mono_get_int32_class; `threads.h:43` declares mono_thread_attach. `object.h:358–373` describes real GC handles: strong handles prevent collection, pinning prevents movement for a short lifetime, get_target reacquires the managed object, free ends retention. These APIs are prerequisites, not proof that the absent target GC/TLS/context port implements them correctly.

`upstream/mono/mini/interp/interp.c:1906–1953` is the real interpreter runtime-invoke path; :3834–3843 dispatches the fast native-call branch through do_icall_wrapper and :3874 uses ves_pinvoke_method for the generic path. See transition audit for architecture-dependent ABI/context/AOT conditions. Observations must correspond to whichever genuine branch executes; interpreter mode configuration alone does not prove execution selected that branch.

Actual native lifetime/readiness anchors remain bridge-seam-audit: candidate UE4SSProgram.cpp:840–845 invokes the callback under its ready mutex, getter2594–2600 acquire-loads actual started state, request_shutdown holds that mutex and sets shutdown. ## Concrete next prep recommendation for root

Retain the metadata gate as preflight; do not expand it into a purported IL execution verifier. Add this negative-scope experiment to capability status/acceptance wording. Before a future target proof, design a small **real-call observation** component at the two genuine C bridge entry/exit seams and the genuine host runtime_invoke boundary. It should bind invocation ID/thread/cookie/provider identity and bounded event/counter state, preserve failures and distinguish attempts from successful returns. Snapshots must reset/bind around the actual Run call; direct host diagnostics must not count as managed calls. A controlled resolver may instrument its true native-call adapter, but name resolution itself is not execution. The future exact host source and its binding path must be available before that adapter can be concrete.

No new host logs are claimed or invented here, no runtime/bridge code changed, and no observation implementation staged. A pure fake-ready host would not resolve this gap. The existing reviewed bridge can be a native prerequisite independently of Mono, while all HOST-PLAN blockers remain. This evidence adds no gate to B7 or other console work.
