## Concrete source-only component design for root review

A small **embedding-side** helper can call these actual pinned APIs directly, using the same configured Mono headers/runtime image. It receives already resolved genuine Run/Throw methods and exact expected Int32/InvalidOperationException classes whose owning assembly/domain/corlib remain retained. The helper must verify the methods/signatures belong to the admitted artifact before use (or require that proven owner setup); name/arity alone is insufficient. No public PRX ABI containing guessed Mono pointers is proposed.

1. Preconditions: real runtime initialized; actual current ready-callback thread attached and in the retained domain; no concurrent domain unload, detach, provider unload or Mono shutdown; real target TLS/native-stack/register capture and SGen native-root scanning admitted. The reviewed bridge callback-only scope is active. These are future host/port obligations, not booleans supplied by a dummy host.
2. Use the actual public GC enter/exit pair around the entire operation with one live stack marker and retained cookie. A future implementation may wrap this exact pair with local cleanup for its own early returns; it must not fabricate a GC implementation. No blocking application work inside the region. No claim that catch(...) handles Mono fatal aborts, OS faults, or asynchronous runtime teardown.
3. Perform actual mono_runtime_invoke(Run,NULL,params,&exc), with params[0] pointing to the native int32 cookie and exc initialized NULL. Keep returned raw result and exception in compiler-visible native stack storage until ownership is established. In a port with the evidenced conservative native-stack/context scanning, those roots span nested polls/GC during handle creation. This is the concrete initial-rooting condition; unsafe mode alone is not the guarantee. Native compiler/port proof remains required. Do not substitute an unregistered heap location or assume volatile alone registers a root.
4. Check exc before result. If no exception and nonnull result, create a short-lived pinned strong handle with the actual public API, reacquire target, require exact expected Int32 class, unbox and copy exactly int32, then free. If exception, retain it safely, ignore result and report failure. Track acquired ownership separately; no guessed zero-failure test. Resolve expected classes before raw-return handling where possible.
5. Invoke the actual ThrowForHostBoundaryTest(NULL,NULL,&exc) under the same scope. Require a nonnull safely retained exception of the exact expected System.InvalidOperationException class. Never inspect a returned value on exception, stringify messages, or invoke arbitrary managed accessors. Release every acquired handle; restore the actual entry cookie on every ordinary native exit. Do not initialize/cleanup runtime or detach an owner thread.

This design is feasible **conditional on the named genuine port contract**, rather than unconditionally safe based on available declarations. An independently staged source helper can explicitly carry those preconditions and call real Mono; it cannot close the missing target port, native-root scanning, actual assembly load association, or managed execution proof. If root requires a helper safe across unknown collectors/platforms with no such admission, this bounded source set is insufficient: use of the internal handle-stack mechanism would need additional genuine source/API integration, not a made-up owner-root callback. No additional fetch is authorized here.

## Observation remains a separate missing seam

The reviewed bridge has callback admission but no per-invocation observer. The future helper must open the actual same-thread/cookie/provider invocation window immediately around the real Run call; actual ABI-version and RuntimeProbe C entry/exit paths must record their real outcomes into it. Both imports, order and cookie reply must be observed for that invocation. This is a required future integration change, not an existing API. Metadata admission and a boxed Run return0 do not prove either native import executed. Throw must yield the actual managed exception; subsequent real Run/native calls and later game continuation/owner teardown remain required evidence.
