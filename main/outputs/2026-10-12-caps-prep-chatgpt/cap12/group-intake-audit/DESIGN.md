# Group intake relationship (Mac-only source/design)

This audits the step after manifest-v1; it adds no parser/planner and reads no real payload or large TOC. Pinned MIT retoc revision is d034ade1ae8117d4786eaf6b0418d4cf48474d7f. source-receipt.json binds local/source URLs, hashes and line references. Two additional public files, iostore.rs and iostore_writer.rs, are retained here with LICENSE.

The manifest's raw12-byte group ID is already the on-disk key. retoc's internal FIoChunkId adds bookkeeping bits0x40 and0x80, then get_raw removes them and selects the version-specific type byte (lib.rs:859–911). ShaderCode is raw9 when TOC version exceeds PerfectHash, raw12 for older versions (:1262–1337); PerfectHash is enum value4 (:1164–1174). For the current v8-only intake, require raw type9 and exact complete12-byte equality with the TOC row. Do not add bookkeeping bits, mask them away to admit an internal ID, change12 to9, or match only the first8/11bytes. Cross-version conversion is outside this proposed profile.

read_raw refers to raw-ID lookup, not raw physical bytes: it delegates through ordinary read to Toc::read (iostore.rs:381–395). That path handles container transport blocks/decryption/decompression and returns logical chunk bytes (lib.rs:640–710). In the shader writer, the final group buffer length becomes compressed_size, and that buffer is passed to write_chunk_raw (shader_library.rs:1156–1173). The generic writer records data.len() as TOC logical length (iostore_writer.rs:48–83). Thus expected type9 TOC logical length is manifest compressed_size, not manifest uncompressed_size, physical block bytes, or a shader span size.

| Layer/value | Meaning and next check |
|---|---|
| TOC physical block stored length/method | Container transport representation. Existing intake supports stored blocks only; unsupported transport compression still refuses. |
| Type9 logical bytes | The complete group buffer after transport decode. Require logical length=manifest compressed_size, source SHA and actual BLAKE3-20 against the pinned v8 TOC. |
| Manifest compressed_size=uncompressed_size | Group-level stored profile. Same admitted logical bytes can serve as the uncompressed group, bounded to that size. |
| Manifest sizes differ | Group-level compression, independent of transport compression. Current metadata-only step must stop at CODEC_REQUIRED; codec identity is not supplied by this header. |
| Packed shader offset / derived end | Locations in the uncompressed group only. They cannot directly select ranges in compressed type9 bytes. |

The writer derives group identity using SHA1 over each member's full stored20-byte shader hash followed by its u32LE uncompressed size, in group sequence, then the exact UTF8 shader-format string. The raw chunk ID keeps the first11digest bytes and version-specific type (shader_library.rs:1029–1057; lib.rs:885–889). Actual code bytes are not hashed in that derivation. The IO writer separately BLAKE3-hashes group-buffer bytes, retaining20bytes for TOC metadata (iostore_writer.rs:62–78; lib.rs:1033–1039,354–367). Stored full shader hashes are copied from the source library; this code does not establish which bytes or normalization originally produced them. Neither the group ID, TOC BLAKE3-20 nor stored shader hash can substitute for either other value.

A group-ID metadata recomputation would need an independently bound exact shader-format string and ordered member sizes. The manifest contains no such format string. Its group arrays plus offset-derived spans can supply candidate member sizes only under the writer-compatible contiguous layout: first offset0, member-array order agrees with increasing offsets, positive spans, final end equals uncompressed_size. manifest-v1 deliberately accepts disordered member arrays and reports a nonzero prefix; those cases must not silently be promoted to this writer-derived identity profile. If exact format/order/size attribution is missing, report ID_DERIVATION_UNCHECKED. Matching a truncated metadata digest would still prove neither code-byte integrity nor full shader-code identity.

A future small metadata planner has adequate source support for these steps:

1. Require a nonempty explicit selection of map/group IDs, pinned manifest-v1 result, original intake receipt and source-format/code hashes. Bind selected manifest output to its source payload/hash/chunk; preferably revalidate the bounded type8 .bin through manifest-v1 rather than trusting editable derived JSON. Keep target-version applicability conditional.
2. Resolve selected maps through explicit index arrays to shader/group indices. Preserve raw group IDs and both size fields; validate all existing manifest bounds. Never use legacy first-appearance numbering or object+216 keys to select a group.
3. Use only a hash-pinned saved catalogue for discovery. Require exact raw group ID and explicit owner TOC hash/container/row; a missing captured row is INPUT_REQUIRED, not global absence. Ambiguous owners require explicit owner selection, not the first container. Compare catalogue logical length with compressed_size. Report expected uncompressed size independently. No large TOC or payload read is necessary to produce requirements.
4. Emit requirements including manifest hash/group index/member indices, raw ID, owner TOC hash/container/row, logical range/length, TOC IoHash, physical block coverage/methods, group sizes and limits. Catalogue geometry is derived discovery evidence; admission still requires the original pinned TOC's full format/lookup checks and actual reconstructed whole-chunk hash in the existing intake utility.
5. A future supplied group .bin must be whole logical bytes from a verified intake receipt: exact source/TOC/id/type/length/SHA/BLAKE3 checks. Group-compressed bytes remain opaque. Stored groups may permit bounded metadata span inspection later, but full stored-shader-hash verification awaits an independent hash definition; do not assume plain SHA1 of each span.

Proposed planner limits: keep current manifest4MiB, derived JSON/output8MiB, explicit selections≤16, selected logical group bytes≤8MiB total and≤4MiB each; use the existing reader's vector/reference caps. Read only bounded saved metadata and explicitly supplied inputs. No UCAS acquisition, group decompression, codec probing, payload writes or original modifications. For fixtures, distinguish stored transport/compressed group; raw09 versus internalC9 versus old0C; compressed-size/logical-length mismatch; ambiguous owner; missing row; identical member metadata with different hypothetical code bytes; missing exact format and disordered/prefixed membership. This is a proposed small suite, not tests run this turn.

Enough evidence exists to implement this requirement planner, conditional on a real verified manifest. The immediate missing input remains the actual type8 payload/intake receipt. Group code decoding and shader integrity require further evidence; no native shader or compatibility result is established here.
