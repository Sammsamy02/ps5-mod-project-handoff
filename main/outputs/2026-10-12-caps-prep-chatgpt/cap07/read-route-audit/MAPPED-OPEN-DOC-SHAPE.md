# Official mapped-open API shape cross-check

Primary documentation only; no binary inspection, source copying, build or runtime execution. Binary observations below were supplied by scan_load_crash/root and were not independently reproduced here.

Reported UTOC route: 1754560 → 139d80 → 139890; b8ed0/b8a70 yields platform-file chain top. Call at 1398f1 uses [top vptr+f0], hidden-result RDI, receiver RSI, pathname RDX, ECX=0. FPak +f0 target 84cb0 adapts to same receiver +f8 at 84ce2; FPak +f8 target 1770bb0 conditionally forwards [this+8]+f8 at 1770ca3. UCAS instead uses a global factory +18. Those routes must remain distinct.

Current [IPlatformFile docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Core/IPlatformFile) display 5.8. They expose mapped-open Ex with filename, read-option flags and maximum size, returning an aggregate FOpenMappedResult; Ex2 uses mapped-option flags. [Core typedef docs](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Core?lang=en-US) identify that result as a value-or-error containing unique mapped-handle ownership. Hidden-result plus receiver/path/flags therefore fits a mapped-open family shape. MaximumSize is an additional parameter: the supplied register summary does not establish its value or forwarding. Do not infer it from ECX=0.

This is not unique identification: the same IPlatformFile page includes an aggregate-returning OpenRead overload taking filename and flags. Hidden-result plus filename/zero flags alone cannot distinguish it from mapped open. [Older 5.5 indexed official documentation](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Core/GenericPlatform/IPlatformFile?application_version=5.5) instead exposes legacy mapped open as a pointer return with filename alone; that direct pointer shape does not itself explain the reported hidden-result call.

[FPakPlatformFile docs](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/PakFile/FPakPlatformFile) establish platform-file inheritance, mapped-open overrides and a LowerLevel pointer. This makes wrapper adaptation/conditional lower-level forwarding plausible. Public docs do not locate LowerLevel at +8 or map methods to +f0/+f8; the assembly evidence, not these docs, owns those offsets.

[IMappedFileHandle docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Core/IMappedFileHandle) show a separate region-map operation taking offset/length/flags and returning a region pointer. A path-taking platform-file call should not be relabeled as that handle-level operation from the word mapped alone.

Exact 5.6 version-query pages were inaccessible through the browsing tool. Current [5.8 release notes](https://dev.epicgames.com/documentation/unreal-engine/unreal-engine-5-8-release-notes) explicitly discuss adding Ex2 and maximum-size behavior, demonstrating version drift. No 5.6 slot index, exact name, return-object layout, ABI, mapped-open implementation, hook safety or UCAS equivalence is proved. Retain +f0/+f8 as observed unnamed slots; mapped-open remains a candidate requiring target-specific argument/result and behavior evidence.
