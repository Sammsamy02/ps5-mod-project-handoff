# Inventory-backed Lua modules

`module_loader.h` installs a shared `require` function over an immutable caller-owned inventory of module names and Lua source bytes. It opens no paths and never searches the filesystem, loads native libraries, or edits mod scripts. Fresh module execution receives its name and archive member, with bounded caching, dependency depth and calls. This is a Lua module loader, not the game API or a Windows DLL translator.

Install once into a fresh Lua state with a fresh context. Keep the context, inventory, metadata strings and source bytes alive until the state and its coroutines are closed. The caller supplies the restricted VM, allocator/instruction limits and approved module inventory. This leaf does not enable filesystem, process, network or debug libraries. It uses Lua 5.4 headers and the caller's Lua implementation.

`invalid_object.h` provides the portable null-value subset of UE4SS UObject semantics: `CreateInvalidObject`, `IsValid` (false), `GetAddress` (zero), `GetFullName` (nil), `GetWorld` (another null object), `type` and equality. It cannot construct a valid game object. Unknown reflection/property operations and writes raise an explicit error. Install once per state; its context must outlive the state and coroutines.

`input_registry.h` adds real registry-backed `RegisterKeyBind` callbacks for caller-supplied key-down events. It admits 64 bindings and three held modifier keys, suppresses repeat events, defers callback-created bindings until the next event, and records callback errors while continuing existing bindings. It reads no device. The zeroed caller context must outlive its single serialized Lua state; dispose references before closing that state.

`async_queue.h` supplies `ExecuteAsync(function)`, `ExecuteWithDelay(ms, function)` and `LoopAsync(ms, function)` through a caller-pumped monotonic queue. It admits 64 pending actions and at most 16 callbacks per pump, defers registrations made during a pump, and cancels looping callbacks on a true return or error. This serialized queue does not create worker threads or deliver game-thread events. Positive delays are capped at 24 hours. Loop rescheduling uses the time supplied to the pump, so it does not reproduce upstream post-callback clock sampling. Close the queue before `lua_close`.

The host experiments compiled these sources against the pinned LuaRaw 5.4.7 library. Focused controls exercised module/null semantics, key callbacks and queue timing/cancellation. Unchanged UEHelpers initializes. Unchanged stamina registers its scheduler, but its activation flag remains false. The unchanged menu registers four key bindings; a caller-supplied Backspace event reaches its callback and fails at missing `ExecuteInGameThread`. With both new modules installed, menu startup also encounters its `ExecuteAsync(ms, callback)` call, which is outside the pinned upstream single-function signature. Minimap still lacks its game-thread scheduler. These are partial runtime prerequisites; no game effects or native console execution were demonstrated.

Private experiments `lua-inventory-require-1`, `ue4ss-null-value-1`, `ue4ss-portable-input-1` and `ue4ss-portable-async-1` retain build recipes and execution receipts. Callback source promotion is byte-identical to the tested files. These sources are not wired to a console game runtime; actual Unreal objects, reflection, hooks, device events and game-thread execution remain absent. The null-value and callback behavior is based on the official UE4SS API and pinned upstream implementation. This layer does not translate Windows DLLs.

The unchanged Townfall Item Spawner was also loaded against these shared modules. It registered six key bindings. Dispatching its F7 binding through `mb_input_dispatch` failed at line 695 because `ExecuteInGameThread` is absent. No menu or actor was created, and no console test was performed. `item-spawner-runtime-trial-1/receipt.json` records the original script digest and actual callback error. Its visible action additionally needs live objects, reflected properties/functions, UMG construction, world tracing and actor spawning.

The intended reusable runtime keeps Lua mod sources unchanged and implements their UE4SS API against a supported engine build. The current host callback queue cannot stand in for the game thread: upstream [ExecuteInGameThread](https://docs.ue4ss.com/dev/lua-api/global-functions/executeingamethread.html) uses an engine execution hook. Engine/build adapters, object lifetimes and argument conversion remain missing here. Native C++ DLL mods require an additional port or binary-compatibility layer; support for Lua calls does not cover them. Upstream itself documents [game-specific configurations](https://docs.ue4ss.com/dev/custom-game-configs.html). A shared runtime is the architecture objective, not evidence that every UE4SS mod or game is supported.

`owned_binding.h` provides a separate reusable owned-data binding. Its `lba_` API retains the earlier Int32 method and masked Boolean property contracts, adds typed object-reference property transactions, and supplies provider-backed `IsValid` and instance/generation equality. A reference property can return another locked receiver userdata or a canonical null userdata. Null fields can be chained and queried with `:IsValid()`; null is distinct from Lua nil. Assignments accept the same binding instance's receiver or nil for reference properties, and exact Lua Booleans for Boolean properties. Unknown fields never become local userdata fields.

All identities are provider-owned IDs and generations, never engine addresses. Each trusted property callback performs one bounded transaction over its own storage, checks current identities/property generations/permissions and leaves storage unchanged on failure. Validity returns exact current/invalid status; provider faults raise an error. The caller supplies a restricted Lua 5.4.7 state and must keep provider contexts alive until its state and coroutines close. Install inside a protected call. Reference resolution takes precedence over Boolean fields and methods; `IsValid` is reserved. Existing unresolved top-level lookup returns nil, so naming the lookup `StaticFindObject` does not implement that full UE4SS API.

This leaf supplies value binding over owned data. It has no engine object discovery, GC membership, reflection lookup, game-thread execution, UMG or device provider and is not connected to the app's game runtime. An eventual engine provider needs a separate established ABI/lifetime/thread contract; these callbacks cannot silently become raw engine-memory callbacks. The reference/null surface follows pinned upstream [object properties](https://github.com/UE4SS-RE/RE-UE4SS/blob/e3ba1016562d6c0868c410d0a71e88bfcdbf691b/UE4SS/src/LuaType/LuaUObject.cpp#L410), while instance/generation identity checks are this owned component's explicit subset. Native compilation is distinct from execution or mod compatibility.

`owned_binding_verify.py` builds the committed test sources against explicit read-only `--lua-include` and `--lua-library` inputs, enforcing the retained LuaRaw 5.4.7 header/archive digests. Supply a fresh `--output-dir` beneath `.superpowers/native-dependency-spike/owned-lua-reference-binding-1`. `host` executes real Lua controls and the prior Boolean/Int32 regression. `host --sanitize` instruments the adapter/tests with ASan/UBSan; the retained Lua archive remains uninstrumented and Darwin LeakSanitizer is unavailable. The bounded Lua allocator separately checks cleanup at close. `native` requires explicit `--ps5-sdk`, `--llvm-config` and `--resource-dir`, links the same source into PS5 test ELFs, checks dynamic layout/import membership and retains the seven public C APIs. It never executes those ELFs. `red` accepts the pinned earlier Boolean adapter through `--red-source` and an include-only private transformation, demonstrating missing reference behavior while the legacy controls pass.
