## 1. WHY batch-2 was assembler-refused (exact mechanism)

The batch-3 bridge assembler (`assemble_staged_pair_v2.py`, vendored
unmodified under `worker-emit-final-pair/vendored/worker-layout-batch3/bridge/`)
applies TWO gates per class:

- **GATE A — predicate inventory** (`width_contract.py:PREDICATE_REQUIREMENTS`):
  a family is emittable only when EVERY probe in its conjunctive chain has a
  `Validated` verdict record from a real run:
  - `FUObjectItem`: `guobject_array` + `uobject_item_chain`
  - `UObjectBase` / `UStruct` / `UClass`: those two + `ustruct_chain`
  - `FField` / `FProperty`: all of the above + `ffield_variant` settled to
    `UE5_FField` (a validated `UE4_UProperty` REFUSES the SET-5_06 table)
  - `UFunction`: no Validated-class predicate can exist (batch2's
    `probe_ufunction` is Inconclusive-classifier only) — permanently refused.
- **GATE B — width authority**: each member additionally needs a non-null
  width in the compiled contract (widths-1 `coverage.json` + widths-2
  `coverage-delta.json`; actual PS5 SDK fixture compile, "constants extracted
  from own fixture ELF; not runtime execution"). A member without one is
  skipped (`skipped_no_width`) even when its class passes GATE A.

The REAL verdicts file (`worker-emit-final-pair/input/verdicts-live-gua.json`)
contains exactly ONE record: `guobject_array = Validated, layout A` at GUA
`0x97ba110` (= 0x400000 + 0x93ba110, single-load-bias, checkpoint
`zcode_v3_MAPPING_BREAKTHROUGH`), digest `97a16867…25072`. `uobject_item_chain`,
`ustruct_chain`, `ffield_variant` are ABSENT — and absent means refused, never
inferred. Hence the full-scope re-run refuses all six batch-2 families at
GATE A (receipt: `emission-batch2-attempt/emission-receipt.json`).

**Why are they absent? Because the reads have never run.** The validated GUA
evidence stops at the 96-byte array-header window: worker-anchor-validation's
live probe read `gua_read` (96 B at 0x97ba110, layout-discerning words w0..w3)
plus a same-value writeback — it never dereferenced
`Objects** = 0x13800220a0`. A grep over ALL controller console records
(`outputs/2026-10-04-zcode-controller/console/*.jsonl`) finds `0x13800220a0`
in NONE of them: no chunk-table read, no FUObjectItem read, no UObjectBase
read, no FField walk has ever executed on target. The task-brief hint that a
"FField chain [was] walked during validation" is NOT supported by any retained
record — worker-rung3-reflection-prep's audit agrees (no class names in any
snapshot record; the GUA validation read only array-header words,
`worker-anchor-validation/REPORT.md:75`). Additionally
`0x13800220a0` readability is UNDECIDED: the recovered vmmap is provably
incomplete and the address falls in a gap (`not_covered_current_map`,
worker-batch2-live-prep §2) — an in-process vmmap re-walk must precede any
read (worker-rung3-chunk-probe's `rc3_vmmap_walk_min`; a full fresh walk is
already demonstrated live by igf5's mapscan: 10,026 records retained,
trusted=1).

**Gate integrity (proven, not assumed):** feeding UNTRUSTED fabricated
`ustruct_chain=Validated` + `ffield_variant=UE5_FField` verdicts while
`uobject_item_chain` is still absent produces byte-identical output with every
batch-2 family still refused (`negative-controls/partial-chain-out/` vs
`emission-batch2-attempt/`). The conjunctive chain cannot be shortened from
below; only real R1-R5 evidence widens it.
