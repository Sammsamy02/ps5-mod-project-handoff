## Direct answers to the two coordinator questions

**1. Serialization — YES, established as fact.** Plugins run one at a time in ini
order; the wait point for each module_start is `pt_call` → `waitpid_timeout(…,30000)`
(pinned main.c:280, reached via inject_prx main.c:447 inside the per-plugin loop
main.c:776-820). The shellcode's SIGTRAP fires only after `call r15` returns
(main.c:93-96), so ploader waits specifically for module_start's RETURN, capped at
30 s. After a timeout ploader does NOT wait for completion (no join): it detaches and
proceeds, while the module keeps executing on the hijacked game thread. Net: the
entry's ~5-6 min did NOT serialize 1:1 into ploader (only ~30 s of ploader wait), but
it DID occupy a game thread for the full duration — the menu delay and the ploader
wait are different costs of the same blocking design.

**2. Launch-10 projection under the 2-plugin config (sha 1216aab6…)** — transfers at
boot: zero (ploader has no network code; 8084/2121 are staging-time channels only).
Missing-file timeouts: zero (both files present; and ploader's missing-file path is an
instant `access()` failure anyway, never a timeout). Fixed ploader sleeps: readiness
wait ≥1.6 s per plugin (mode 2: 20×50 ms stable ticks + 600 ms settle), 50 ms poll,
attach ≤~0.3-7 s. Composition module_start (VMMAP walk 10,019 + lease registration +
refusal) remains THE unmeasured stage: projected total mod-attributable wait is
**~5-10 s + C_comp (≤30 s unless it exceeds the pt_call cap)** — roughly 10-70× below
launch-9's mod-attributable cost. Detail: LATENCY-ANALYSIS §4.

## Two honest corrections to working hypotheses (mine included)

- **No missing-file retry storm exists within one ploader invocation.** A failed
  plugin leaves the title un-injected, but each pid is processed exactly once per
  invocation (pinned main.c:755-764 `known`-list one-shot). The loop merely idles to
  the 120 s cap. Re-attempts require a new ploader invocation. Missing files cost
  ~0 s in the injector itself (instant `access()` fail, main.c:423-425) plus ~2 s of
  wasted readiness+attach each.
- **Launch-9 contained exactly ONE entry harness run, not two.** The +133 KB delta
  spans the tail of block 35 plus block 36, but the session-eve baseline byte position
  (2,213,030) lands ~23 lines INTO block 35 (marker at 2,210,392) — block 35 was
  already running when the baseline was captured, so it belongs to the session-eve
  run. Also the measured delta is 130,726 B (the task text's 133,450 includes that
  boundary strip). Mid-task I reported "two entry runs in launch-9"; that was wrong.

## Patches (PATCHES/, proposal-only, apply in order)

Generated by scripted transformation of the pinned source and verified:
`patch -p1` applies all four cleanly in series and the result is byte-identical to
the transformed target (full compile requires PS5 SDK headers, not available here).

1. `01-deadfile-earlyskip.diff` — skip missing files before readiness+attach (~2 s
   per missing entry per invocation; removes FAIL-toast noise).
2. `02-hoist-readiness.diff` — one readiness wait per title instead of per plugin
   (~1.6 s × (n−1) per invocation; ~11 s on an 8-plugin ini, ~1.6 s on the 2-plugin).
3. `03-steplog.diff` — append-stamped `/data/plugins/ploader.log`; makes composition's
   module_start dt (the last unknown) measurable next launch without touching plugins.
4. `04-quiescent-exit.diff` — exit after the game was processed and 15 s pass with no
   new process, instead of idling to the 120 s cap; never triggers before the game is
   first seen, so late-game-start behavior is preserved.

Deliberately not proposed: lowering the 30 s `pt_call` cap (would FAIL more
slow-but-working modules — measure first via 03), trimming the mode-2 stability gate,
and any entry/composition PRX change from this worker (entry source is NOT in-tree —
OURS-SIDE-NOTE.md specifies the behavioral changes R2/R2a/R2b for its owners, with the
observer's `nanosleep(&remaining,&remaining)` remainder pattern at
worker-aligned-entry-observer/source/probe/probe.c:177 as the in-repo precedent).
